# 2026-09-24 · 子项目工程能力图谱与接缝路线

- 状态：proposed
- 决策层级：架构探索；不构成产品、数据模型或发布决策
- 本次范围：P1 文档化。只建立工程能力图谱、术语和接缝路线；不修改应用代码、profile、DSH Desktop 或 Lute Shell。

## 要解决什么问题

Magpie-Horch 的受管包已经覆盖研究、技能、任务、团队、设置、主题、更新等多个方向，但它们不能被简单看成一个已经打通的产品。

现在真正需要先回答的，是三件事：

1. 每个子项目在工程层面承担什么能力，运行在哪个宿主上。
2. 源码、profile、bundle 和宿主之间，哪些是已观察到的声明态，哪些仍需实机证明。
3. 哪些交接点最容易造成“看起来接上了、实际没有生效”的问题，应该先用什么小切片验证。

本 Note 只处理工程拓扑。已有的产品能力研究和产品方向属于独立草案；本轮不覆盖，也不改写它们。

## 决定

以 [机器可读能力图谱](../../../architecture/subproject-capability-graph.json) 作为本轮工程拓扑的索引，以 [受管包目录墙](../../../catalog/packages.md) 作为包清单与治理字段的唯一来源。

先把复杂工程拆成五层，再按接缝推进，而不是按页面或包名逐个“拼起来”：

    仓库治理与门禁
            ↓
    能力包、平台包、契约包
            ↓
    profile 的 file 依赖与 bundle 注册
            ↓
    宿主：DSH Desktop 或 Lute Shell
            ↓
    用户可见的表面与端到端价值流

当前建议把 DSH Desktop 视为第一宿主：它已有明确的 desktop profile 装配路径。Lute Shell 保持为独立宿主路线，先做兼容性矩阵，不能因为同在一个仓库就默认可替代 DSH Desktop。

## 五个优先接缝

| 优先级 | 接缝 | 为什么先做 | 最小下一步 |
| --- | --- | --- | --- |
| S0 | 运行时装配 | 源码、file 依赖、bundle、宿主加载常被混为一件事 | 每个关系卡分开记录 declared、installed、bundled、live |
| S0 | 服务消费 | 可选服务、inject 和消费者失败处理的漏检会直接造成静默失效 | 用 service-consumption 检测盲区做 Red/Green 小试点 |
| S1 | 工作对象身份 | Task Board、Agent Team、LoopX、DeepResearch、Qoder 目前各有工作状态 | 等产品 D3 确定一个价值流后再定义统一身份 |
| S1 | 宿主可移植性 | DSH Desktop 与 Lute Shell 的依赖、装配、验收不等价 | 建立能力级兼容性矩阵，不做默认迁移 |
| S2 | slot 与 renderer | 加性 slot 和整块 shadow 的升级风险不同 | 每次表面改动先写清 slot、owner、回退点和验证方式 |

## 分阶段任务

### P1：建立共同语言和索引

本次完成的交付物：

- 机器可读图谱：包、宿主、profile 声明态、关系假设和接缝。
- 术语表：受管包、宿主、运行时装配、接缝、声明态。
- 架构总览入口：让后续开发在改代码前能找到这张图。

### P2：接缝关系卡

为五个接缝各建一张短卡。每张卡必须有：owner、代码入口、上游/下游、数据边界、契约、失败方式、回退方法、自动化与实机验证读数。关系卡是取证工作，不是立即改造。

### P3：一个最小代码试点

只选择 S0 的服务消费检测盲区。先补能稳定失败的测试，再补最小实现让它变绿；通过相关门禁后再考虑扩大。这样能同时验证“图谱是否指导开发”和“门禁是否能守住接缝”。

### P4：一个用户价值流

等产品 D3 决定主线后，只选一个跨模块场景，例如“提出任务到研究结果可追溯”。此时才设计统一 work item 的映射、生命周期、权限和审计边界。不要把所有面板的数据一次性合并。

### P5：分片交付

文档、检测器代码、profile 变更和 DSH Desktop 实机验收分别提交、分别审查。一个本地 profile 声明或一个截图都不能代替完整交付。

## 不做什么

- 不把 30 个受管包强行归并成一个大包。
- 不把当前 profile 声明写成“功能已经上线”。
- 不把 Lute Shell 当作 DSH Desktop 的无成本替身。
- 不在工作对象身份未确定前建设统一数据库或迁移存量数据。
- 不触碰本工作区已有的并行改动，尤其不将表面改动与本轮图谱混合提交。

## 考虑过但暂不采用的路线

| 路线 | 暂不采用原因 |
| --- | --- |
| 先按 UI 页面重构 | 页面只显示局部能力，无法先解决运行时装配与服务契约的根问题。 |
| 先全量统一数据模型 | 当前尚无经过产品确认的主价值流，过早统一会把假设固化为迁移成本。 |
| 直接迁移到 Lute Shell | 需要先证明能力、依赖、发布和验收的宿主兼容性，当前证据不足。 |
| 只维护一份人工表格 | 不能被工具读取或随关系卡持续校验，易重新失真。 |

## 后果与验收边界

这份图谱降低了后续开发的定位成本：开发者能先判断改动属于哪个层、经过哪些接缝、需要什么证据。它不会自行解耦代码，也不会改变任何运行时行为。

P1 的完成标准是：JSON 可解析、链接可达、术语不与架构页冲突，并且明确区分声明态和实机验收。P2 之后，才有资格对具体接缝提出代码改动。
