# 40 条工程技能并入 AI 全栈线：归位、图标、与一条跑在实现前面的文档

- 日期：2026-09-15
- 生命周期：implemented
- 分类：capability
- 对应 ADR：[ADR-0089](../../../adr/ADR-0089.md)
- 相关：[ADR-0085](../../../adr/ADR-0085.md)（归位 ≠ 接线）、
  [ADR-0086](../../../adr/ADR-0086.md)（第零步独立成层）、
  [ADR-0052](../../../adr/ADR-0052.md)（第三方技能入库 SOP §12）

## Problem

方案决策②的 40 条工程技能（Matt Pocock 技能集）要并入 AI 全栈线。前四步
（结构体检 → 四件套 → 正文汉译 → 安装 + 来源留底）走 §12.9 既有路径即可，
**后三步从未在这个规模上跑过**，而每一条都有一种"绿着错"的形态：

1. **归位的证据没有来源。** 归位判据 J2 要求 `evidence.from_skill` 是技能原文的连续子串，
   原文来自 `manifest/skill-evidence-corpus.json`。本批 40 条**一条都不在语料里**
   （语料停在 T0 那批 251 条）。校验器对覆盖不到的证据记「不可复核」并单独计数——
   整批判定于是变成一句无法回答的话：结论对，但没法证明。

2. **40 个创作决定没有落点。** 40 个头像要在本机资产
   `~/.dsh/skills/lute-brand-icons/` 里新增 40 条 `sk-fs-<name>` 条目。
   既有 `assign_lute_icons.py` 缺条目时 `SystemExit` 点名（对的），但它只能报缺、不能补。
   徽章选型（肤色/发型/衬衫/领口/徽章图形）会**只活在本机**，重跑管线只能靠记忆复现。

3. **文档跑在实现前面。** SOP §12.5 在 2026-09-14 宣布把 `no_role_kind` 扩到 7 类，
   但只改了文档：校验器 `NO_ROLE_KINDS`、`test/role-map.spec.mjs`、manifest 用例**一处都没动**。
   照文档判就会撞红，而 `J4-NO-ROLE-KIND` 的措辞把责任指向判定人。
   本批 40 条绝大多数正是「工程能力」那一类——**两个独立执行者各自踩到并独立上报**。

4. **会腐烂的数字还在长。** `verify-fullstack.mjs` 曾硬编码「30/30」，SOP 自己标注「易漏」。
   本批要把它改成 70，正是它会再次腐烂的时刻。

## Decision

**一、证据语料先于判定，覆盖率必须能被报出来。**
新增 `packages/capabilities/dsh-overseas-skills/scripts/build-evidence-corpus.mjs`：
把目录里尚未收录的技能正文补进语料。既有 251 条**逐字节不动**——它们抓自另一份源头
（Accio 导入时的正文），本机已无那份原文；用「当前已装技能」重算等于悄悄换掉判据基准，
而没有任何输出会提示这件事。两条守卫：`--check` 供门禁；写盘前证明「零改动往返逐字节相同」
（该文件是 `indent=1` + 末尾换行，不符即拒绝写盘，否则一次补齐会炸出全文件 diff）。
判据因此从「我记得补过语料」变成「语料覆盖 = 目录里每一条」。

**二、判定与合并分离，且判据只有一份。**
40 条判定分四批并行产出**片段**（`/tmp/fs40-roles/frag-{P,Q,R,S}.json`），由
`scripts/apply-role-fragments.py` 单点合并——子代理不得直接写归位表（四路写同一文件 =
静默覆盖）。自检器 `check-fragment.py` **直接 import 正式校验器的纯函数**
（`validate` / `skill_text` / `role_text` / `check_quote_form`），把片段叠加到真表上再跑一遍。
不复制判据，是因为本仓库最熟悉的失效形态就是「两个读取点口径不一致」：
自检绿灯、正式红灯，或更糟——自检绿灯、正式判定因覆盖率不足整批变成「不可复核」而没人注意。
合并器同时**重算** `coverage` 四个派生量与 `_meta.purpose` 的线别条数：
手改一次要同改五处，漏一处的表现是「门禁报一个和本次改动看不出关系的错」。

**三、无岗是一等结论。**
本批 40 条新增 **8 个挂载 / 32 条无岗**；全栈线 70 条里只有 16 条挂岗。
无岗条目必须给分型 + 一段能独立读懂的理由，理由要点名**最近候选岗位**并说明为什么对不上，
并主动否掉近邻（例：`observability → AGT-046 溯源监测` 是假朋友，链路追踪不是数据血缘溯源）。
**挂岗率不是考核量**——把它当考核量，判定就会开始找理由挂上去。

**四、文档不许承诺没被守住的东西。**
§12.5 的分型表加**状态列**：生效四类与「🕓 未生效」三类分列，写明照旧表判会撞红、
以及真正启用需同改哪三处（校验器 `NO_ROLE_KINDS` / 测试分型集合 / **既有 68 条无岗条目的重判**）。
并新增门禁测试：SOP 标为生效的分型必须与校验器 `NO_ROLE_KINDS` 逐字相等、
标为未生效的必须不在其中、且**文档举了例子的分型必须真在 manifest 里用过**。
把「知道」变成「拦住」——文档与实现之间的漂移从此由测试守。

**五、创作决定进仓库。**
新增 `scripts/add-fs-brand-icons.py`：40 行 `sk-fs-<name>` 按 id 归入 lute-brand-icons
`catalog.js` 的既有块（保持字母序、只在预览通过后 `--write`），**徽章选型表随脚本进仓库**。

**六、计数从映射推导。** `verify-fullstack.mjs` 的 `TOTAL` 改读映射条数。

**证据语句都是原文连续子串，不是概括。** 例：
`api-designer → AGT-047「接口契约」`，`from_skill` = 「接口：资源建模、端点与 OpenAPI 3.1 契约」。

**负控（证明仪器会红，不是假绿）**：新增的文档↔校验器对账测试做了三次变异——
① 校验器悄悄接受 `DEV_ENGINEERING`（文档说未生效）→ 判红并打印两侧分型列表；
② SOP 把一个真在用的分型标成「未生效」→ 判红；
③ 抹掉 manifest 里某分型的唯一用例（文档举了例却没人用）→ 判红并点名该分型。
三次均如实变红，还原后复绿。

**四批自检的独立负控**：批 S 另造 4 处缺陷（伪造 `from_skill`、非法分型、两态混淆 ×2）
验证 `check-fragment.py` 会红，实测 `判据失败 4 / 退出码 1`。

## Alternatives considered

- **让子代理直接改 `role-assignments.json`**：四路并行写同一文件，冲突与静默覆盖都拦不住；
  覆盖率与 `_meta` 还会在四次写之间互相打架。否决。
- **自检器各写一份判据**：两个读取点口径不一致。否决——直接 import 正式判据。
- **语料按「当前已装技能」全量重算**：会整体位移 251 条既有证据的基准，且无人会知道。否决。
- **直接实现 7 类分型**：会改变页面在场景组头聚合显示的分组（`buildOrgTree` 按
  `no_role_kind` 分组、客户端把分型原文打印出来），且需重判既有 68 条无岗条目。
  产品可见的分组变化，未获明确决定前不做——**本次只把文档改成不再承诺它**。
- **把 `observability-and-instrumentation` 挂 AGT-049「运行监测」**：有正当先例
  （`analytics → AGT-046 数据管道 medium`，埋点判为管道前端实现），批次 R 一度挂了。
  但 §12.5 的分型表**按名**把它列为「不服务出海业务的某一岗」，而 AGT-049 的监测对象是
  **Agent 平台任务的运行状态**（产物「运行状态与恢复证据」）、本技能的埋点对象是通用生产代码，
  两者之间需要一层重定向——正是 §12.5 划的那条线。按「按名裁定 > 类推先例」改判无岗，
  并把反方口径原文记进 `no_role_reason` 备查。

## Consequences

- **两处 🟡 不是缺陷，但也不能算通过。** `handoff/AGT-049` 与
  `incident-retrospective/AGT-049` 的 `responsibility` 留空、`note` 写明「三条责任名都不字面成立」。
  校验器把它归为「诚实标注，不判失败」，但**复核覆盖因此是 1012/1014 而不是 100%**——
  这个数字要照实报，不得说成「全部通过」。
- **顺带刷新（非本次意图，但必须说明）**：跑 `assign_lute_icons.py` 会重新导出
  `category-icons-gn.json` / `skill-icons-gn.json`，而这两份仓库清单此前是**陈旧导出**
  （内容与 lute-brand-icons 当前 catalog 不一致：`gn-cat-gn-data` 的徽章已由柱状图改为仪表盘、
  `sk-gn-chart-gen` 的衬衫已由 `G` 改为 `GD`）。枚数与键序不变，本提交一并对齐。
- **未取得读数**：SOP 第 4 项运行层验收（`/api/dsh-overseas-skills/fullstack-list` 的 fs 组计数）
  **仍是旧值 30**——宿主进程内存持有 catalog，生效需重启 DSH；本会话若重启会被中断，
  故**未运行**，不写成通过。重启后各组期望条目数（由 `fullstack-mapping.json` 推导，可直接对账）：
  clarify 7 / spec 7 / architecture 10 / implement 5 / quality 12 / infra 17 / collab 7 / writing 5 = **70**。
- **已知未修（须用户决定，另一次提交）**：lute-brand-icons 的 `lib/generator.js`
  把**衬衫名**当颜色传进 `shoulders()`（`shoulders(shirt, …)`，而紧邻的 `COLLARS`
  用的是 `${W}`/`${G}` 值），于是 `fill="W"` / `fill="GD"` 都不是合法颜色值，
  **全部 310 枚图标的肩带渲染成纯黑**。实测：`sk-fs-tdd` 栅格化后肩带带取样 `(0,0,0)`，
  既有 270 枚同此。修法一行（加衬衫色表并传值），但它会让 270 枚已验收图标外观整体改变，
  属品牌呈现变更，未擅自改。
- **仍然开着**：`postgres` 的 24 处 `references/` 外链指向
  `raw.githubusercontent.com/planetscale/database-skills`，而同名文件包里都有（22/22 命中），
  离线可用性因此无谓依赖上游；`postgres` 正文还带着上游的托管商推荐块（PlanetScale）。
  两者都是内容策略，未动。
