# 发布链的最后一环：入库版本必须有分发面，跳过的版本必须被记录

> 决策：[ADR-0076](../../../adr/ADR-0076.md) · 分类：contract · 生命周期：implemented

## Problem

### 前四环全齐，第五环从来没有过

2026-09-13 收尾对账，把发布链逐环比了一遍：

| 环节 | 家 | 状态 |
| --- | --- | --- |
| 产物 | `packaging/release/<版本>/` + 仓库外归档 + `uchg` | 齐（ADR-0057 / ADR-0067） |
| 入库清单 | `release/<版本>.sha256`（进 git） | 齐（ADR-0058） |
| tag | `v<版本>` | 齐：v2.0.1 / v2.2.0 / v2.3.0 / v2.3.1 / v2.3.3 |
| 代码 | `origin` + `codeup` | 齐 |
| **分发面** | **GitHub Releases** | **缺** |

实测读数：`gh release list` 最新是 **v2.0.0（2026-09-10）**，而仓库根 `README.md` 正告诉客户
「从 Releases 下载」。也就是说**客户按文档操作拿到的是一份早三个版本的包**。

而实际分发渠道是 IM：2.3.1 的产物是从飞书收到的副本找回的（`com.apple.quarantine: …;Feishu;`）。
四个版本（2.0.1 / 2.2.0 / 2.3.0 / 2.3.1）从未在任何公开分发面出现过。

### 没有任何一环会问「发了没有」

这条缺口不是「忘了」——**没有任何机制会问这个问题**：清单机制只保证「字节能找回」，
tag 只保证「这串字节对应哪份源码」。两者都在仓库内部，而缺口在仓库**之外**（客户拿不拿得到）。
所以它既不在门禁的射程里，也不在任何一篇 Note 的「后果」里。

这正是总账 P-04「写了但从没跑到」与 P-08「用纪律守只有机制能守住的东西」的合流形态：
流水线的每一环都有脚本产出，**唯独最后一环从来没有脚本、没有命令、没有检查项**。

### 顺带对出：2.3.2 有清单、有产物、没有 tag

`release/2.3.2.sha256` 在 git 里（提交 `0ca9886`），`packaging/release/2.3.2/` 的 DMG 与
仓库外归档都在，SHA256 `7756564e…` 本次复核与清单一致。但它**没有 tag**。

查它的来历：15:10 切出，随后发现载荷里「用户需授权第三项：输入监控」的说法是错的
（实际只需两项，`kTCCServiceListenEvent` 一行记录都没有），17:45 重切为 2.3.3。
也就是说它在**通过发布判据之前**就被取代了，tag 那一步被跳过——**读起来像是有意的，不是漏打**。

于是「补齐发布历史」立刻撞上一个口径问题：2.3.2 补不补 tag？

### 发布前必须复核的两件事，以及扫描的实际发现

DMG 内含 profile 快照，而 GitHub 仓库是**公开**的（`gh repo view` → `visibility: PUBLIC`）。
把 640 MB × 5 的二进制推上公开分发面之前，先做两件事：

1. **哈希复核**：六个版本的 `shasum -a 256 -c SHA256SUMS` **全部 OK**（2.0.1 / 2.2.0 / 2.3.0 /
   2.3.1 / 2.3.2 / 2.3.3），与 `release/<版本>.sha256` 逐位一致。
2. **载荷敏感内容扫描**：把 `profile.tar.gz` / `skills-presets.tar.gz` / `aeis-portable.tar.gz` /
   `DSH Desktop.app.tar.gz` 解流后按凭证形态扫（`sk-` / `ghp_` / `AKIA` / 私钥头 / `Bearer`）。
   两处命中，**都定位到了文件才判**：
   - `Bearer eyJhbGciOiJub25lIi…`（payload `{"sub":"admin","role":"admin"}`）→
     `node_modules/@dhicoc/dsh-reverse-skill/skills/pentest-tools/**` 的**文档样例**（渗透测试技能的
     攻击载荷参考），不是凭证。
   - `AKIA5GDQACQCAKIA5PDQ` → `dsh-univer-office/artifacts/**/index-lf6BtP49.js`，取上下文看是
     **base64 编码的 WASM 字节码**里的巧合字节序列（`5HDQQLIApFDQEgC0EEcUUNAQJAIApB…`），
     不是 AWS key。

   结论：**载荷内无凭证**。这条结论不是「看起来没问题」，是能点出文件与上下文的。

## Decision

见 [ADR-0076](../../../adr/ADR-0076.md)，五条：Releases 是每个入库版本的发布面；`--latest` 只给最新；
**没有 tag 就不是发布版，2.3.2 不补 tag 也不发**；发布前必答哈希与敏感扫描两问；
把判据做成门禁 `release-published` 而不是纪律。

门禁的射程（`scripts/gates/release-publish-scope.mjs`，纯函数 + 9 条反向自测）取**两个家都在 git 里的
交集**：既有 `release/<版本>.sha256`、又有 `v<版本>` tag。取交集是刻意的——
只有清单没有 tag 的（2.3.2）与只有 tag 没有清单的（2.0.1，早于清单机制）都自动出局，
**不需要再维护一张「已评审不发」的例外表**（那会是一份会腐烂的清单，且是同一事实的第二个家）。

拿修复前的真实形状喂给这个纯函数，它给出：

```
inScope:           2.2.0 2.3.0 2.3.1 2.3.3
missing:           2.2.0 2.3.0 2.3.1 2.3.3     ← 四个版本一个都没发
untaggedManifests: 2.3.2                        ← 只进读数，不进违规
```

## Alternatives considered

- **甲：只发 2.3.3。** 否决：客户按 `README.md` 下载到的仍是 2.0.0。
- **乙：给 2.3.2 补 tag 并一起发布。** 否决：见决策 3——发布历史要的是**可核对的记录**，
  不是**连续的数字**；补 tag 会把一份已知带错的载荷说成发布版，且 tag 时间晚于构建时间。
- **丙：不发 DMG 附件，只写哈希。** 否决：ADR-0002 已定 DMG 走 Releases 附件。
- **丁：不加门禁，把「记得发 Releases」写进 SOP。** 否决：P-08。
- **戊：门禁射程取「所有 `v*` tag」。** 否决：`v0.1.0` 会永久判红——与 ADR-0075 修掉的
  `patch-anchors` 永久红同形（判据单调增长 × 历史堆积）。这条被写进了反向自测
  （「只有 tag 没有清单的版本同样出局，且不得变成永久红」）。

## Consequences

- **正面**：客户按 `README.md` 能拿到最新版；每个入库版本的字节有了公开可校验的家；
  「入库了但没发布」从此是一条会自己报错的读数。
- **负面**：约 3.2 GB 附件进入 Releases 存储；公开即可能被抓取——故敏感扫描是**前置**的。
- **后续动作**：
  1. `docs/sop/dmg-release.md` §6 从 4 步扩到 6 步：加「推送两条远端」「发布到 GitHub Releases
     （附 `--latest=false` 规则与 draft 语义）」「发布前必答两问」。
  2. 复发故障总账加 P-13。
  3. 未动的两条口径：`v2.0.1` 早于清单机制、没有 `release/2.0.1.sha256`（`release-verify.sh`
     已如实报为「未登记（早于清单机制）」）；`verify-patches-v2.sh` 的默认 `STAGE_VERSION`
     仍陈旧（在出货载荷里，改了就会与已装配的 2.3.3 不同源，随下一版改）。
