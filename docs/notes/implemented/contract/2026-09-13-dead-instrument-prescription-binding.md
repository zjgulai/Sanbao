# 已证伪的仪器不得再被开成判据：一条读数为空的命令，与它的四个家

> 决策：[ADR-0080](../../../adr/ADR-0080.md) · 分类：contract · 生命周期：implemented

## Problem

### 症状：一条「本机无运行中的 DSH 实例」的检查项，读的是空

`docs/sop/dmg-release.md` §0 的发布前检查清单里，有一条让操作者确认「本机没有 DSH 在跑」。
它的判据是一条 `pgrep -f` 命令。**在 DSH 主进程确实在跑的时候，它返回 0 条。**

这不是「有人写错了命令」那么简单：这条检查项守的是白屏红线（运行中替换 app bundle →
宿主 HMR 热更 → 生产 renderer 无完整热替换 runtime → 整屏白屏，2026-09-13 实测）。
复核者照着清单敲一遍、看到空输出、得出「没有实例在跑」，然后按 SOP 往下走——
**在运行中替换 app bundle**。红灯没有被无视，红灯**从来没有亮过**。

### 定位：先钉死射程，再谈对错

判据换成 `ps -Ao pid=,comm=`（可执行文件全路径）后，靶子立刻现形：

```
$ ps -Ao pid=,comm=
87357 /Applications/DSH Desktop.app/Contents/MacOS/DSH Desktop
```

但「读得到」不等于「原来是错的」——要证明原来那条**确实**是死仪器，得把它的失效范围钉死，
否则无法排除「当时恰好没在跑」。于是做了一次阳性对照：

| 量法 | 靶子 | 读数 |
| --- | --- | --- |
| `ps -Ao pid=,comm=` | DSH 主进程（真在跑） | `87357 /Applications/DSH Desktop.app/Contents/MacOS/DSH Desktop` |
| `pgrep -f '/Applications/DSH Desktop.app/Contents/MacOS/'` | 同一个进程 | **0 条，exit=1** |
| `pgrep -f 'Contents/MacOS/'` | 同一时刻 | 222 条（**不含**主进程） |
| `pgrep -f '<tmp>/MyFake.app/Contents/MacOS/'` | 把 `/bin/sleep` 拷贝成 `…/MacOS/DSH Desktop` 并启动 | **命中**（pid 99354）；杀掉后 0 条 |

最后两行是这次定位的关键：**`pgrep -f` 对普通 CLI 进程是好的**（同一条模式当场命中拷贝进程），
它盲的是**这个** Electron 主进程。所以失效不是「pgrep 不好用」这种可辩解的话，而是
「在这台机器上，用这条命令判断这个 app 在不在跑，永远是空」。

原因没有查明，也不影响决策——我们不需要解释它，只需要不再用它。

### 真正贵的不是这一条命令，是它有四个家

同一条事实（`pgrep -f` 看不见那个 GUI 主进程，连「原因不明」都写了）**早在 2026-09-12 就写在
`packaging/scripts/first-launch-test.sh` 的注释里**。它没有变成任何机制，于是同一条判据又在三处
各写了一遍：

| 家 | 形态 |
| --- | --- |
| `packaging/installer/install.sh` 0b 步 | 就地 `pgrep -f`（白屏红线的第一道闸） |
| `packaging/scripts/first-launch-test.sh` | `ps -ax -o command=` + `grep -v grep`（**已经修过**，注释里写着为什么） |
| `packaging/scripts/refresh-app-brand.sh` | 又一份就地实现（同一个失效、同一段解释） |
| `docs/sop/dmg-release.md` §0 | **给人敲的那一份**——唯一被这次真正发现的那一份 |

本次修的是**最后一个**。前三个里，安装器那处是我当天早些时候顺手修的（并因此以为「已经修好了」），
清单照旧是一条死仪器——**这正是 P-07 的原形，而且漏掉的那个正好是操作者会照着敲的那份**。

所以本条的决策不是「把这条命令改对」，而是：**同一条事实只能有一个家，且每个消费者都调它、
不重写它**（下面 Decision 1）；以及**「知道」必须变成「拦住」**——把死仪器登记成机器可读的簿子，
由门禁逐行核对判据面（Decision 4）。只改那三行，下一个人照样会在第五个地方再写一遍。

## Decision

1. **「在不在跑」收成一家**：`packaging/scripts/dsh-running.sh`，随包分发到载荷 `tools/`。
   安装器 0b 步与首启验收的就地实现**删除**，改为调它；品牌重放脚本也改用它（随 ADR-0081 落库）。
2. **退出码 0 / 1 / 2 / 4，其中 4 = 判不了**，调用方必须**中止**而不是当成「没有在跑」。
   安装器为此新增一条硬失败：`ps` 读不出进程表时**拒绝安装**——宁可不装，也不在运行中替换 app bundle。
3. **安装器侧另加一条自测**：`installer-running-guard-test.sh` 按字节抽出安装器的 0b 块配桩运行，
   钉住 T1 放行 / T2 退不出去则中止 / T3 缺判据则中止 / T4 判不了则中止，外加恒真桩突变。
   （不跑整个安装器：那会替换开发机上真正的 `/Applications/DSH Desktop.app`。桩里 `osascript`
   必须打桩，否则测试会拿开发机上正在跑的 DSH 去满足断言。）
4. **死仪器登记簿 + 门禁 `dead-instrument`**：射程＝git 索引里的 `*.md` / `*.sh` / `*.bash`；
   判据面＝清单行（含续行）+ 围栏代码块 + 脚本里去掉注释后仍有内容的行；`「…」` 引用不算使用。
   读数常显分母；空登记簿 / 字段不全 / 取不到射程 / 判据面抽出 0 行**一律判红**。

## Alternatives considered

- **只改 SOP 那一行。** 否决：这正是背景里那个形状——四处同源判据，改一处，其余继续静默。而且
  「改哪一处」取决于谁先看到哪一份，这不是一条能依赖的运气。
- **在注释里指向 `dsh-running.sh`，保留就地实现。** 否决：`first-launch-test.sh` 已经证明过
  「注释里写清楚了」不产生任何机制。四种消费者各持一份实现时，下一个改动仍然只会落到一处。
- **靠评审记得。** 否决：本次事故本身就是一个反例——`first-launch-test.sh` 的注释写得比谁都清楚。
- **让门禁扫全文档（含散文）。** 否决：机器分不出叙述与规定。一条正确叙述（「`pgrep -f` 看不见
  这个进程」）会立刻变假红，而假红会让人关掉这条判据（P-02）。代价写进了模块注释的
  「本项不检查什么」：把死仪器写进散文里的操作步骤，本项看不见。
- **只登记不判据**（把两条死仪器写进总账的 P-02 条目里）。否决：总账的组织单位是**根因**，
  不是仪器；把仪器混进去会让「下一个人该先做什么」变得不可检索。登记簿是清单，门禁是机制。

## Consequences

- **判据面第一次被机器扫过**：465 个文件 / 8443 行判据面 / 2 种已证伪仪器，读数常显分母。
- **SOP §0 的那一项改为指向判据**，不再复述命令——「写进清单的命令必须真的读得出东西」
  从此由门禁核对。
- **本次实现当场被本仓库已有的判据咬了一口**：门禁 `shell-var-multibyte`（ADR-0064）报出
  我新写的三处 `$VAR` 紧跟全角括号（bash 会把多字节字节并入变量名，`set -u` 下直接中断）。
  三处已改 `${VAR}`。这条判据存在的原因与作用被再次证明——「机制」比「知道」可靠，就在眼前。
- **本 ADR 自己也被拦过一次，它的自测被拦过第二次**：ADR 引用缺陷原文的围栏代码块被
  `dead-instrument` 判红三处（围栏是「照着敲」的面），改写成 `「…」` 引用形式后通过；
  而 `dsh-running-test.sh` 里那行「顺手再量一次死仪器的读数」（原本是给 ADR 当对照取证用的）
  同样被判红——**它没法写成引用形式**，于是删掉：想复核那条读数就读登记簿的 `reading`，
  不要在判据面上跑它。这条约定因此有了两个自证用例，代价也照实写进了 ADR 的「负向」一节。
- **代价**：`dead-instrument` 是模式匹配，不理解上下文，用对了也会判红（要写成引用形式）；
  散文不在射程内；未入库的草稿不扫（`git add` 之后才进射程）。
- **代价**：`dsh-running.sh` 只在 macOS 上验过，依赖 `ps -Ao comm=` 给出未截断的全路径。

**诚实划界（判不出的部分）**

- **`pgrep -f` 为什么对这个进程盲，未查明。** 记录的是可复现的读数，不是机制（P-01）。
  自测 R7 每次都会把 `pgrep -f` 的对照读数打出来：它哪天开始能看见这个进程，说明 macOS 变了，
  届时本 ADR 的读数需要重取。
- **判据只回答「有没有」，不回答「是不是同一个 app」**（不比签名身份与版本）。
- **散文里的死仪器判不出**，不假装被拦住了（P-03）。
