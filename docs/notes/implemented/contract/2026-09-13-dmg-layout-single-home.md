# 交付形态是产物的属性，不是文档的属性：SOP §5 三处形态断言与它们的唯一事实之家

> 决策：[ADR-0077](../../../adr/ADR-0077.md) · 分类：contract · 生命周期：implemented

## Problem

### 一次「复核 SOP 是否与实物相符」的例行动作，翻出同一版里三处错

2026-09-13 复核 2.3.3 实物时，把 `docs/sop/dmg-release.md` 的 §5（终验）逐条对着磁盘跑了一遍。
三条命令，三处不成立——**而且是同一个根因的三张脸**：

| 位置 | SOP 写的 | 实物 | 后果 |
| --- | --- | --- | --- |
| §5.1 | `codesign --verify … "packaging/release/$VERSION/DSH Desktop.app"` | 该目录下只有 DMG + `SHA256SUMS` / `VERSION` / `manifest.json`，**没有解开的 app** | 命令当场失败，复核无法进行 |
| §5.2 | `# 应看到 DSH Desktop.app 与 Applications 快捷方式` | 卷根是 `DSH Desktop.app.tar.gz` + `install.sh` + `LUTE Setup.app` + 四个 tarball；**没有 `.app`，没有快捷方式** | 复核者会判定「DMG 做错了」，而实物是对的 |
| §5.4 步骤 1 | 「把 DMG 里的 app 拖到 `/Applications`」 | 2.3.3 的交付形态是**离线安装器载荷**，没有可拖拽的 app | 用户会去找一个不存在的东西 |

三处都不是笔误，而是**同一个根因**：那些句子是**上一版交付形态**的快照，而 2.3.3 换了形态
（从可拖拽安装盘改为离线安装器载荷）。文档里的快照不会因为产物形态变了而自己报错。

### 为什么所有门禁都是绿的

因为**没有任何判据把「文档断言的清单」与「产物真实的清单」比过一次**。
门禁量的是：补丁锚点在不在、TCC 判据说不说「不」、文档之间的链接可不可达、
出货白名单有没有被绕过——全都在量**别的**东西。

### 更坏的一层：这条事实本来有家，而且那个家是对的

`packaging/INSTALL-GUIDE.md` §2 的入口表**准确描述了 2.3.3 的卷内清单**——它甚至专门写了
「只有下面两个是可点的安装入口，其余全是载荷」，并逐行说明每个文件是什么、该怎么用。

于是这是一次 **P-07（一条事实多个家，只改了其中一个）**：
「卷里有什么」有两个家，用户向的那个（安装手册）跟着形态改了，工程向的那个（SOP）没有。
**而漏掉的那个，正好是复核者会读的那个**（P-01）。

### 顺带查出的第四点：那个「对的家」也不全

把入口表与卷内清单逐名对照，发现卷上有一个 `completeness.json`，入口表**从未登记**它。
它不是一个误入的临时文件——`assemble.sh` 第 650 行显式断言它必须写进 payload
（`[ -f "$PAYLOAD/completeness.json" ] || exit 1`），`smoke-test.sh` 拿它比对 bundle/技能/预设清单。
也就是说：**表是描述交付面的，而它是交付面的一部分，却在表外**。用户打开 DMG 会看到一个
手册说不清是什么的文件。

## Decision

### 一、把「卷里有什么」收成单一家，SOP 不再复述清单

`docs/sop/dmg-release.md` §5.2 改为**指向** `packaging/INSTALL-GUIDE.md` 第 2 节，不写「应看到 X 与 Y」。
一句「应看到……」的真假由产物决定，而它住在文档里，没人会去比——去掉这类句子，
比让它保持正确便宜得多。

### 二、给这条事实装一副牙：门禁 `dmg-layout-doc`

新增 `scripts/gates/dmg-layout.mjs`（纯函数）+ `scripts/gates/dmg-layout.test.mjs`（15 个用例，
含恒真桩突变），注册为门禁 `dmg-layout-doc` 与 `dmg-layout-doc-selftest`。判据分两半：

**静态半（永远可判，不依赖任何产物在场）**

- **R1 单一家**：SOP 必须链接 `packaging/INSTALL-GUIDE.md`，不得就地复述一份清单。
- **R2 形态断言**：SOP 不得断言**拖拽式交付形态**（卷根有 `.app`、有 `Applications` 快捷方式、
  「把 app 拖到 `/Applications`」）。这一条是**廉价但精确**的——它拦的是一种**已经发生过**的写法，
  不是全称保证。诚实写明：全称保证由动态半在产物在场时给出。

**动态半（需要产物在场，否则整项报 `skip`——不是 `ok`）**

- **R3 未登记条目**：卷上每个顶层条目都必须在入口表里出现。
- **R4 幽灵条目**：入口表里每个条目都必须真实存在于卷上。
- **R5 入口可点**：标为「✅ 可点」的每一行必须真实存在。

### 三、射程跟着 git 走，不跟着磁盘走（沿用 ADR-0075 / P-11）

`selectLayoutTargets` 把**已打 tag 的版本**排除出扫描面，并在读数里点名「谁退出了、为什么」。
理由是具体的：下一版往载荷里加一个文件、手册随之更新，所有还挂载着的旧卷就会**永久**判红，
而那条红与「手册和当前载荷对不上」在输出上不可区分——清理挂载于是成了让它变绿的唯一手段。
默认错误方向选**多量**：读不到 tag（浅克隆）时全部纳入，卷名解析不出版本号时也纳入。

### 四、把「对的家」补全，而不是把错的家删掉

`completeness.json` 补进安装手册第 2 节的入口表，并把「大约十个文件」改成
**「下表就是卷内文件的完整清单」**——既然门禁现在逐名守着这张表，它就可以承诺自己是完整的。

## Alternatives considered

- **只改 SOP 三处措辞，不加门禁**：这正是 P-03（「知道」没有变成「拦住」）。
  查 git 之后，这件事的性质比「复发」更难看：SOP 是 **2026-09-13 同一次提交**（`11d9d9f`）
  写下的，而**同一份文件 §2 的「预期产物」已经写着载荷是
  `staging/$VERSION/payload/DSH Desktop.app.tar.gz`**——§5 与 §2 从写下那一刻起就自相矛盾。
  也就是说 §5 那三条命令**一次都没有被执行过**（跑一次 `ls -A` 就会看到十三个 tarball）。
  一次都没跑过的东西，靠提醒不会变得会跑。靠人记得不是工程解。
- **把禁用短语表做成判据的全部**：黑名单挡得住已经写过的句子，挡不住下一句新的。
  所以它只占静态半的一条，且模块注释里明写它「廉价但精确、不是全称保证」。
- **让静态半也去解析 SOP 里所有 `packaging/…` 路径并逐一验存在（想覆盖 §5.1）**：
  被否决。`$VERSION` 展开成哪一版取决于人，而 `packaging/release/.staging.XXXXXX`
  这类**故意**不存在的路径会让通用路径判据满是误报——会误报的校验很快会被关掉（P-02）。
  §5.1 由人工修正，并且**在模块注释里明写它判不出**，不假装它被拦住了。
- **把动态半的射程放宽到「所有挂载卷」**：能立刻让 2.3.3 被量到，但下一版就会产生永久红
  （见决策三）。射程的真值由打扫卫生决定是 P-11 本身。
- **在 SOP 里保留一份「卷应为 N 个文件」的数字**：数字比清单更容易过期，且同样没有判据。

## Consequences

- `pnpm run gate:full` 新增两项（`dmg-layout-doc`、`dmg-layout-doc-selftest`），
  自测 15 个用例含恒真桩突变（用 2026-09-13 的**缺陷原文**当输入）。
- 安装手册第 2 节从「大约十个文件」变成可承诺的**完整清单**，且多登记了 `completeness.json`。
- SOP §5.1 / §5.2 / §5.4 三处改为与 2.3.3 实物一致的安装器形态，每处都留下了
  「原来写的是什么、为什么会错」的原址说明。
- 复发故障总账新增 **P-14**（交付形态是产物的属性，却按文档的属性维护）。
- **遗留一**：本机当前既无未打 tag 的 payload、挂载的 2.3.3 卷也已打 tag，
  因此动态半此刻报 `skip`——**本次没有校验任何卷内清单**。这不是缺陷，是射程如实；
  下一次装配（或任何未打 tag 的版本挂载）会自动把它纳入射程。
- **遗留二**：§5.1 那一类的「SOP 里写着一个不存在的路径」仍无判据（见备选方案）。
  它靠人工复核，本 Note 明写这一点，避免它看起来像被守住了。
