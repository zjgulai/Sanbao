# 注入式侧边栏导航行的行轴收成一条：同列同行轴，且清单本身即判据

- 日期：2026-09-13
- 状态：implemented
- 对应 ADR：[ADR-0079](../../../adr/ADR-0079.md)
- 相关：ADR-0009（一份事实一个家——本条修的是「这条事实根本没有家」）、ADR-0069（清单本身即判据的形态）、
  ADR-0075（射程为空必须报出来而不是报通过）、ADR-0078（同一场会话里的另一半：那条修的是「改完怎么生效」，
  本条修的是「改完两处一致不一致」）、总账 P-07 / P-02

## Problem

DSH 的侧边栏 shell 不对外暴露可注册的 slot，所以 `dsh-skill-center-local` 与 `dsh-role-matrix-local`
各自用 DOM 注入，把一行导航插进「新建会话」按钮与工作区浏览区之间。**注入逻辑是共享的**
（`sidebar-entry-core.ts`，两包各持一份同步副本），**但样式不是**：每一行自带一个 CSS module，
只经共享核心取 `.entry` / `.entryIcon` / `.entryLabel` 三个类名。

于是「一行侧边栏导航行长什么样」这条事实**住了两个家，而没有一处是清单**。两行并排、同一形态，
两套宽度约定各自演化：

| | 改前 | 出处 |
|---|---|---|
| 岗位矩阵 | `width: calc(100% - 8px)` + `margin: 2px 4px` + `padding: 6px 8px` + 默认 content-box | `role-matrix.module.css` |
| 技能中心 | `box-sizing: border-box` + `width: 100%` + `padding: 0 10px` | `skill-panel.module.css` |

2026-09-13 重启后（装载点字节已确认）AX 几何实测：

```
岗位矩阵  x=68  w=248  标签 x=108
技能中心  x=64  w=256  标签 x=106      ← 原生侧边栏行轴（会话行 / 工作区区同为 64…320）
```

两行左右缘各差 4px、悬停高亮块差 8px。

**这是当天已经修过一次的同一个缺陷的另一半。** 当天先修的是「技能中心的文字居中」——
`text-align` 是继承属性，`<button>` 的 UA 默认 `center` 一路继承到 `flex:1` 的标签 span，
而同族的岗位矩阵声明了 `left`。修法是在 `skill-panel.module.css` 里补了 `text-align: left`
并写下注释「同一形态两处不一致，属 P-07」。**那条注释说对了根因，却只修了半件事**：
居中修好了，几何那半原样留着——因为**没有任何机制要求两处一致**，只有「记得一起改」这条纪律
（P-08：用纪律守只有机制能守住的东西）。

还有一件**取证错误**在动工前被量出来并当场推翻：本条最初把「深度研究」与导航两行并成一组，
称「三个注入行三种几何」，并据此提出把三者统一到 64…320。核对底部区域后发现
深度研究走的是官方 `sidebar.footer.action` **slot**（不是 DOM 注入），父容器与导航行不是同一个，
实测 62…314，**与同节的原生「知识库」逐像素重合**（`.badge` 的 `width: calc(100% + 4px)` +
`margin: 0 -2px` 正是为此而写，AX 里 `.layer` 64…312、图标 x=70 完全对得上）。
把它拽到 64…320 会让它**背离**自己那一节的原生行。分组错了，结论就会反。

## Decision

1. **先修几何，且用构造证明而不是算**：把 `role-matrix.module.css` 的 `.entry` 改成与
   `skill-panel.module.css` 的 `.entry` **逐属性一致**（`box-sizing: border-box` / `width: 100%` /
   `margin: 2px 0` / `padding: 0 10px` / `height: 36px`）。两行是同一个父节点下的同一个 `<button>`、
   经同一个共享核心取同样的类名——**只要这几条规则相同，几何就必然相同**。构建产物逐属性对照确认
   只余 4 处差异（`color` 的 fallback 拼法、`font: inherit`、2px 纵向 margin、`nowrap` 住在
   `.entryLabel` 而非 `.entry`），**没有一处落在水平轴上**。纵向 2px margin 有意保留以维持既有行距。

2. **把它变成机制**：新增门禁 `sidebar-row-axis`（`scripts/gates/sidebar-row-axis.mjs`）+
   反向自测 `sidebar-row-axis-selftest`（13 条，`node --test`）。判据三层：
   - **发现**：扫 `packages/*/*/src/client/sidebar-entry.ts` 里声明了 `rowAttribute: 'data-dsh-*-entry'` 的包。
   - **登记**：发现的每一行都必须在 `REGISTRY` 里；登记项指向不存在入口也判红（清单不许腐烂）；
     `position` 与清单不符判红（列归属变了）。
   - **同列同行轴**：同一 `column` 的水平轴元组（`box-sizing` / `width` / 水平 `margin` / 水平 `padding`）
     必须等于 `COLUMNS[column].axis`。**期望值是声明出来的，不是「拿第一行当基准」**——后者在第一行
     本身就错时会恒绿。

3. **诚实划界写进模块注释**：本项只读**声明文本**，不读渲染结果；`split` 列（新应用那行）的几何由
   共享核心 `applySplitGeometry()` 运行时算，CSS 不决定落点，只登记不断言；底部 `footer.action` 槽
   的行**不纳入**——它们与原生行一致才是对的，纳入会判红一个正确实现。

## Alternatives considered

- **抽出一段跨包共享的 CSS**（把 `.entry` 规则收成单一住处，从根本上取消「两个家」）。
  最彻底，但两个包各有品牌色、徽章与 hover 细节，真要共用就得先引入一个共享样式包，
  而共享包在 `file:` 装配下又是一份需要同步的副本——**用一个新副本取消两个旧副本是净亏**。
  且共享核心的做法已经是「同步副本」，同一条路再走一遍不会更安全。故改为**用门禁守一致性**，
  把「家」的数量留给架构决定，把「一致」这件事机器化。
- **只靠注释与纪律**。这正是当天已经失败过一次的做法：注释准确记录了根因，几何照旧漂移。
  P-08 的判词是「用纪律守只有机制能守住的东西」。
- **把 AX 探针做成门禁**（真去量渲染后的框）。最接近真相，但门禁跑在无 GUI 的环境里，
  且需要应用正在运行——把判据绑在「机器上恰好开着 GUI」上会让它时红时绿，比静态判据更坏。
  静态判据守**声明一致**，渲染一致由 AX 探针在验收时量并记进读数，两者分工写清楚了。
- **统一时把深度研究也拽进来**（本条的初始方案）。已由取证推翻，见 `## Problem` 末段。

## Consequences

**正面**

- 两行现在落在同一条轴上，且**这是构造性的**：只要门禁绿，它们就不可能再差开。
- 门禁的射程是**打印出来的**：`已登记 3 个注入行、2 列；其中 2 行断言了行轴（sidebar-nav）`。
  射程为空判红而不是报通过（ADR-0075）。
- 端到端验过它咬人：把真实的 `role-matrix.module.css` 改回缺陷形状后，判据当场报出三条违规
  （`width='calc(100% - 8px)'` / `marginInline='4px'` / `paddingInline='8px'`），随后逐字节还原
  （sha256 前后相同）。**不是只有 fixture 会说「不」。**
- 新增注入行再也无法静默逃逸：不登记就红。

**负面 / 代价**

- 门禁读的是声明文本，**挡不住「声明一致但渲染不一致」**（例如父容器自身变了）。这条边界写在
  模块注释里，不假装它被拦住了。
- `REGISTRY` 是一份需要人工维护的清单；新增注入行要记得加一行——不过这正是设计意图：
  让「忘了」变成一个红灯，而不是一个安静的选项。

**后续动作**

- 门禁 `sidebar-row-axis` 已登记进总账 P-07 的「已落地机制」。
- 几何一致性在**重启后**才生效（ADR-0078：客户端 bundle 只有重启一条路径）；本条的全部实测读数
  均已按该前提取得。
