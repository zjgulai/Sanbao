# ADR-0152 · 更新器骨架只做「检查 + 提示」（版本口径 / 八态判定 / 不下载不安装）

- 状态：accepted（2026-09-21）
- 决策者：用户（lute）——「自动更新路线下一轮先做结构两步」的排期裁决（DA-10），
  「更新器骨架」的范围由计划 §5「现在」行给定
- 决策记录：[Note](../notes/implemented/contract/2026-09-21-updater-skeleton.md)
- 相关：ADR-0151（feed 派生契约——本包消费的输入）、ADR-0061（本机装配走 profile 本地，不进仓库出货物）、
  ADR-0068 / ADR-0063（签名身份与 TCC 代价——D1 边界的由来）、
  ADR-0056（产物不可删除——将来「回到上一版」依赖它）、
  计划 `docs/plans/2026-09-13-auto-update-route.md` §5

## 背景

计划 §5 把自动更新拆成八步，其中「现在」行第二步是**更新器骨架：只做「检查 + 提示有新版」**。
它的价值在于人工交付阶段就有读数（用户/维护者能知道有没有新版），且与签名身份无关——
不提前做依赖 Developer ID 的部分。

现状：feed 契约（ADR-0151）已落地，但没有消费方；「现在有没有新版」这个问题在应用里问不出来。
骨架要回答这个问题，就必须先定三件事：**版本从哪读、判定有几种结论、边界画在哪**。

## 决策

**D1：边界——只检查、只报告；不下载、不写盘、不安装。** 包内不得出现任何下载 dmg、
写临时目录、调用 `install.sh` 的代码路径。理由不是「没时间」，是**顺序**：身份没换、公证没做之前，
自动装下来的包会撞 Gatekeeper，用户看到「更新完打不开」——比不自动更新更坏（计划 §5 原话）。
自动安装（⑤）与 Ed25519 校验（⑦）分别等 Developer ID 与私钥管理决策。

**D2：本机版本口径 = app `Info.plist` 的 `CFBundleVersion` 后缀。** 装机产物写的是
`2.0.10-lute.2.5.0`（上游 Electron 版本 `-lute.` LUTE 版本），取出 `2.5.0` 参与比较；
**没有 `-lute.` 后缀是具名状态 `current-not-lute`**（上游构建，不是「解析失败」）。
读 plist 用 XML 文本解析而不是 `plutil` 子进程：测试在 Linux CI 上跑，子进程依赖会把
「读不出」与「这台机器没有这个工具」混成一个读数；二进制 plist 明确报 `二进制 plist` 而不是猜。

**D3：判定是八态状态机，不是布尔值。** `update-available` / `up-to-date` / `feed-behind` /
`channel-mismatch` / `feed-unreadable` / `feed-invalid` / `current-unreadable` / `current-not-lute`。
**读不到（网络不通、HTTP 非 2xx、不是 JSON、形状不合法）绝不允许折叠成「已是最新」**（P-15）——
把失败当好消息是这个契约唯一真正的危险形态。`feed-behind`（feed 里的版本比本机旧）单列，因为
「feed 没跟上」与「本机是未发布的本地构建」都需要人看见。工具名 `upd_check`，只读，返回状态 + 消息 +
可核对字段（dmg / sha256 / min_os / 发布说明）；启动检查延后 20 秒执行、离线只写日志。

**D4：feed 判据的消费侧实现随包走，与生产侧靠用例对钉。** 装载点（profile 的 `node_modules`）上没有
仓库脚本可 import，所以 `lib/feed.js` 自带一份形状校验与版本比较；它必须与
`scripts/lib/update-feed.mjs` 同源——由用例对钉**生产侧派生出来的 feed 的键序**（不是某个内部常量），
并用同一张突变表验证两份判据结论一致。任何一侧改契约而另一侧没跟上，用例即红。

**D5：装配走 profile 本地（ADR-0061），不进仓库出货物。** `luteOrigin: self / lutePublish: false`；
本机在 `~/.dsh/profiles/desktop` 里以 `file:./vendor/packages/platform/dsh-update-local` 声明并列入
`dsh.profile.bundles`。重启应用后生效；卸载 = 删声明 + 删 vendor/装载点两处副本。

## 备选方案

- **直接做「下载 + 校验 + 调 install.sh」**（把 ⑤ 提前）：否决。Developer ID 未采购时这条路
  只会在用户机器上制造 Gatekeeper 失败；而且换身份时这段代码要重验一遍（§0 的代价）。
- **用 Electron 官方更新通道（`electron-updater` + `app-update.yml`）**：否决（计划 §2 已定）：
  它整包更新 app，但**不更新 profile / 技能 / 灵枢**，而后者才是 LUTE 的出货面；且安装语义会与人工路径分家。
- **判定返回布尔值（有新版本 true/false）**：否决。「读不到」「通道不符」「本机是上游构建」都是
  真实且互不相同的状态，压成布尔值必然把其中一种当成「没有新版」。
- **版本从 profile 的 `package.json` 或仓库 tag 读**：否决。它们是**构建期**事实；用户机器上
  真正在跑的是 app 本体，唯一权威读数是它的 `CFBundleVersion`。
- **把 feed 判据抽成共享源、两侧都 import**：否决（本轮）。两侧运行环境不同（生产侧在仓库里跑，
  消费侧随包物化进 profile），共享源要么让 profile 依赖仓库路径，要么在构建期注入；
  用交叉钉用例守住同源，成本更低且判定更直接。

## 后果

- 正面：人工交付阶段出现了「有没有新版」的可核对读数；将来接 ⑤ 时输入契约（feed）与判定状态机
  都已就位；边界写进 README 与 ADR，后面的人不会顺手把安装路径塞进来。
- 代价（如实保留）：现在真 Releases 上还没有 `latest.json` 附件（机制后第一版才有），
  所以实机读数是 `feed-unreadable（HTTP 404）`；这就是「读不到不等于最新」的第一现场。
  骨架不含重试与缓存，网络抖动会如实报 `unreachable`。
- 后续：③④（Developer ID + 公证 + TCC 重授）→ ⑤（接上安装，走同一个 `install.sh`）→
  ⑥（通道与回滚，依赖 ADR-0056 的产物不可删除）→ ⑦（Ed25519 签名，feed 的 schema 变更）。
