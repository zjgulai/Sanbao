# ADR-0121 · 对象库不得承载凭据与超大对象（SEC-RT-011）

- 状态：accepted（2026-09-18）
- 决策者：用户（lute）
- 决策记录：[Note](../notes/implemented/security/2026-09-18-object-store-hygiene-gate.md)
- 相关：ADR-0009（一份事实只有一个家）、ADR-0014（门禁是硬门槛）、ADR-0094（门禁统一结果规范）、ADR-0102（分母由对象完整集合推出）、ADR-0120（SEC-RT-010 主门禁，本 ADR 把登记表从 10 项扩到 11 项）

## 背景

2026-09-18 的代码与包债务审计中，实测到 `.git` 为 3.9 GB，其中：

1. **一个 2.6 GiB 的 pack 内只有 1 个对象** —— blob `ddab355b…`，未压缩 **6,800,745,472 字节**，路径解析为 `packaging/backup/pre-2.0.10-migration/dsh-home-snapshot.tar`。逐位比对确认它**与磁盘上的副本 sha256 完全相同**（`ffe972d3…`），而该 tar 内含 `.dsh/.credentials.yaml`（与磁盘上当时正在用的那份**逐字节相同**，`77d27c62…`）、`.dsh/.credentials.yaml.bak-vod-aigc-20260915-211414`、`.dsh/ext-bridge-token`。也就是说**活凭证躺在对象库里**，直接违反 `~/.dsh/AGENTS.md` 的第一条红线（凭据只进 DSH 凭据服务、不进仓库）。
2. 另有 **183 MB 的 Mach-O**（`5987db81…`）与 1.2 GB 的 app 树、319 MB 的上游 DMG，共 1289 个路径**不在仓库跟踪集内**——它们只存在于对象库。
3. 两个 `tmp_pack_*`（402 MB + 315 MB）是被中断的 repack 残骸，`git count-objects` 自己把它记为 `garbage`，而 `git gc` **因默认 2 周的 `pruneExpire` 删不掉它**，实测在仓库里躺了一天。

根因不是「谁手滑了」，而是三处静默：

- **`.gitignore` 没有覆盖 `packaging/backup/`**，而 `packaging/backup/README.md` 是已跟踪文件——目录是活的，放什么进去都能被 `git add`。
- **codex 的 checkpoint 机制对 git index 做 `git write-tree`**，产生的是**裸 tree 而不是 commit**（这正是 `git log --find-object` 找不到它、`git status` 不提示任何异常的原因）。任何被 `git add` 过的东西都会因此静默进入对象库，**没有尺寸筛查，没有密级筛查**。
- **没有任何门禁看对象的体积或垃圾包**。`.gitignore` 只管「能不能被 add」，对象库一旦写进去就没有第二道闸。

三处静默合起来，让一次 `git add` 把 6.8 GB 的凭据快照永久写进了对象库，而全部门禁保持绿色。这是本仓库最熟悉的那一类缺陷：**知道没有变成拦住**。

## 决策

1. **新增门禁 `object-store-hygiene`（SEC-RT-011）**，三条判据：
   - **单对象未压缩体积上限 50 MiB**。超限判红，并在读数里同时打出 sha、体积与**是否被任何 ref 可达**——可达性决定处置方式（可达的要先改引用，不可达的 gc 即可回收）。阈值取 50 MiB 而非更低，是因为仓库里合法的最大资产是 `packaging/vendor/python-standalone/cpython-3.14.7+20260825-aarch64-apple-darwin-install_only.tar.gz`（26.66 MB，被 `main` 与全部 tag 可达，`reloc-aeis.sh` 按名引用），它必须放行；而 6.8 GB 的 tar 与 183 MB 的 Mach-O 必须拦下。
   - **对象库总量上限 1 GiB**（loose + pack + 垃圾）。单对象阈值可以被「拆成多块」绕过，这条是第二张网。
   - **垃圾包必须为 0**。`tmp_pack_*` 不判红就会被当成「对象库本来就大」。
2. **判据面必须常显分母**（扫描了多少对象、超限几个、总量多少、垃圾几个），扫描面为空或 `git count-objects` 取不到一律判红——「一个都没扫」与「都扫过且干净」必须分开（ADR-0102）。
3. **`.gitignore` 收窄排除 `packaging/backup/` 下的体积型二进制**（`*.tar` / `*.tar.gz` / `*.tgz` / `*.dmg` / `*.zip` / `*.pkg` / `*.app/`）。刻意**不**整目录排除：那会让已跟踪的 `packaging/backup/README.md` 变成 tracked+ignored 漂移（ADR-0013）。
4. **登记为 SEC-RT-011 并纳入 `security-contract-master` 主门禁的分母**。为此修正主门禁的一个真实缺陷：`expected` 原本被钉死在必需项数（10），导致**新增第 11 条契约时主门禁自己判 schema invalid**（`expected must equal checked + skipped + failed`）。分母改为「登记项数 + 缺失必需项数」，登记表恢复可扩展。
5. **本 ADR 的处置动作**（一次性，已完成）：先救出唯一不存在盘外副本的 `packages/capabilities/dsh-overseas-skills/check-fragment.py`（4156 B，当时磁盘没有、git 未跟踪、只在对象库里），再删除 4 条 `refs/codex/turn-diffs/checkpoints/**` 与含该 tar 的 pack、清理 518 个 codex 独有 loose 对象与 2 个 `tmp_pack_*`。结果：`.git` 3.9 GB → 80 MB，`git cat-file -e ddab355b…` 失败，`git fsck --connectivity-only` 退出码 0，HEAD / 分支 / 14 个 tag / 远端跟踪 ref 全部未变。

## 备选方案

1. **靠纪律**：在 SOP 里写「不要把大文件放进 `packaging/backup/`」。
   否决：这正是本次事件已经证明无效的那一类——`.gitignore` 与门禁都没拦住，纪律更不会。而且写进 SOP 就成了第四条「同一条事实的副本」（ADR-0009）。
2. **只加 `.gitignore`，不加门禁**。
   否决：`.gitignore` 管的是「能不能被 add」，管不了「已经进去了」。对象库没有第二道闸时，一次 `git add` 之后没有任何环节会发现。
3. **门禁去读对象内容、判断里面有没有凭据**。
   否决：那需要一份「什么算凭据」的清单，而清单本身会腐烂；体积是一个**不需要词汇表**的代理量。代价是 6.8 GB 的凭据快照与 6.8 GB 的正当资产同罪——这不完美，但它是机器能稳定判的那一半。本 ADR 明确写出这个射程缺口，不用「已覆盖」把它盖过去。
4. **`filter-repo` 重写历史、彻底清除该 blob**。
   否决（本版）：该 blob 不可从任何分支/tag 到达（逐个 `rev-list --objects` 验证过，零命中），因此不需要重写历史；而重写历史要 force push 双远端（codeup + github），代价远大于收益。留作独立立项。
5. **跑 `git gc --prune=now` 一次性清理**。
   否决（本次执行时点）：`--prune=now` 会把**另一个会话刚 `git add` 但尚未进入 index 的 loose 对象**当成不可达而删掉——当时该会话正在活跃写入。改用定点移除（按对象计，删 `pack`/`.idx` 两个文件），并发面上零竞争。

## 后果

**正面**

- 对象库里不再有活凭证；此类缺陷从「靠人记得」变成「门禁拦得住」。
- `.git` 3.9 GB → 80 MB，clone / gc / 备份对象的体积回到与源码相称的量级。
- 主门禁的分母不再钉死，登记表可扩展——这是 SEC-RT 系列继续增长的前提。
- 判据用**真实读数**当反向自测输入（6.8 GB tar / 183 MB Mach-O 判红、26.66 MB 合法 tgz 放行、`Infinity` 突变后必须漏过），阈值不是口味。

**负面 / 已知缺口（显式登记，不并进「已覆盖」）**

- **本项不读内容**：6.8 GB 的凭据快照与 6.8 GB 的正当资产在本项里同罪。
- **本项只看当前对象库**：已被 gc 掉的历史不在射程内。
- **本项不联网**：本机干净不等于远端干净。本次审计中 `git ls-remote` 两端均需凭据、调用超时，**巨物是否曾推送远端为 Unknown**；可给的只是推论——该 blob 不可从任何 ref 到达，故常规 `git push <分支/tag>` 不会带上它，但 `git push --mirror` 会。
- **凭证是否需要轮换**：对象库中的是活凭证，但从未离开本机且不可达自任何 ref。用户判定为**不需要轮换**；本 ADR 记录该判断的依据与它的推论性质。
- **codex checkpoint 的 `write-tree` 行为未改**：任何被 `git add` 的东西仍会静默进入对象库。本 ADR 只在**体积**这一维设了闸，密级那一维没有机制。
- **`packaging/backup/` 仍在白名单内**：本次只排除了体积型二进制，文档类文件仍可入库（有意为之，见决策 3）。

**后续动作**

- `packages/capabilities/dsh-overseas-skills/check-fragment.py` 已救回工作树，但**尚未入库**——它是一份「归位片段自检器」，直接 import 正式判据 `validate_assignments.py` 的纯函数（ADR-0009 的做法），应当补进仓库并接入调用点。
- 审计发现的 4 条 `refs/codex` 删除后，codex 对那 4 轮（09-16 18:26 / 09-17 09:45 / 16:21 / 16:39）的 undo 能力已失去。旧 ref 名与 SHA 留档于 `/tmp/codex-refs-backup-20260918-021049.txt`。
