# ADR-0286 · 第 7 步 registry 准入接线：三重绑定、裁决失败语义与派生规则单一家

- 状态：accepted（2026-10-10）
- 日期：2026-10-10
- 决策者：用户（lute：裁决失败语义表、绑定强度、并行车道）＋ agent（取证与实施）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-10-session-prompt-registry-admission.md)
- 相关：[ADR-0285](ADR-0285.md)（首方快照与重发链）、[ADR-0284](ADR-0284.md)（评估时点=observedAt）、[ADR-0171](ADR-0171.md)（Registry 治理）、[ADR-0282](ADR-0282.md)（target 步）

## 背景

第 7 步「发布与收录」半已由 ADR-0285 落成：首方 approved 条目随发布快照装载、runtime inventory 证据携带其 `registrySnapshotDigest`、requirement/descriptor 的 7 键 capability 面绑定同一快照。准入口（`resolveRegistry`）仍 absent，链路诚实停在 registry 前。ADR-0285 落地时沉淀出三份现成材料：`capabilityOperationsProjection` 与两个摘要派生（`registryDescriptorDigest`/`adapterMappingDigest`）已存在于 runtime inventory 生产者；证据已携带快照代摘要；requirement 声明的两个摘要与快照条目重算值逐字节相等（已实测 `0b6e398d…`）。遗留裁决：失败语义（「未配置」与「拒绝」的产品面）、绑定强度（机制守还是发布纪律守）。

## 决策

1. **D1 端口与三重绑定**：新端口 `createSessionPromptRegistryPort`（`src/main/session-prompt-registry.ts`），消费与 inventory 同一 provider 实例的封存快照、requirement bundle 与最后可信观测；评估时点为证据 `observedAt`（与 ADR-0284 D4 同一纪律）。回答前硬校验三件事：①快照代——`contentDigestOf(snapshotId)` === 证据 `registrySnapshotDigest`；②声明一致——requirement 声明的 `registryDescriptorDigest`/`adapterMappingDigest` === 按同一条规则从快照条目重算；③审批态——approved + verified 且在证据时点生效窗内。任一失配 → `unavailable`。
2. **D2 失败语义（用户裁决）**：无映射、多映射（歧义）、candidate、provider 读取/内核 parse 失败、窗口外、声明失配一律 `unavailable`——「还没配」不得冒充「拒绝」；**只有显式 disabled / revoked 才答 `denied`**。成功值为 `mappingRef = mapping:${snapshotId}:${adapterMappingDigest}`（与 `targetRef` 同族自绑定形态）。
3. **D3 派生规则单一家**：`capabilityOperationsProjection` 与两个摘要派生抽入 `src/main/capability-entry-derivation.ts`，runtime inventory 生产者与 registry 准入口共用；抽取必须逐字节保持既有 descriptor 摘要（由既有 golden 与 spec 证明——移动即红）。
4. **D4 接线**：options-gated 合并，三输入（requirementBundle + capabilityRegistry provider + runtimeInventoryObservation）齐备才出现；`index.ts` 传 `bundledRegistry` 同一实例——准入不得开第二个 registry 来源。
5. **D5 门禁**：route-authority 新增 registry 事实组（gated 接线、同实例、禁第二来源、内核 parse、代绑定、歧义拒答、denied 唯一性、声明交叉校验、mappingRef 形态、派生单一家）＋六条具名突变；note 句把 registry 从 absent 名单移出（「stops at the absent preflight / persistence steps」）。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 全部失败答 unavailable（denied 面完全留待撤销运营批） | 否决（用户裁决）：显式撤销与未配置在产品面不可区分，治理动作失去表达。 |
| 只做结构性同源（同 provider 实例），不做声明一致重算 | 否决（用户裁决）：requirement × registry 失配只能靠发布纪律守；重算规则已存在且逐字节可测，机制成本≈零。 |
| 准入开独立 registry 读取 seam | 否决：两个事实家；快照代绑定将不可证。 |
| mappingRef 只带 adapter 标识 | 否决：不带快照代与摘要的 ref 无法自证所依据的映射；与 targetRef 族不一致。 |

## 后果

- 十步链真实推进到第 7 步：窗口内 `session.send` 现在通过 caller→context→candidate→identity→target→compatibility→registry，诚实停在 preflight；路由级仍 `protected-effect-unavailable`（信封不含 stage，测试保持 stage-agnostic）。
- 派生规则抽出后两消费者共用一个 forma；在仓规则由门禁与既有 golden 双重钉住。
- 未闭：preflight / persistence / dispatch（第 8–10 步）、撤销运营真实化（disabled/revoked 的发布流程）、Host 生命周期失效接线（ADR-0284 登记项）。
