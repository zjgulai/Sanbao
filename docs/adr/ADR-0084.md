# ADR-0084 · 出货 preset 的行级闭合判据：判据的事实来自**出货面**，不是开发机此刻的状态

- 状态：accepted
- 日期：2026-09-14
- 决策者：用户（lute）+ agent
- 决策记录：[Note](../notes/implemented/contract/2026-09-14-preset-row-closure-vs-dev-machine-state.md)
- 相关：ADR-0056（出货 preset 不烘焙外部产品行；本机产品走本机装配）、ADR-0061（KOL Hunter 本机装配层）、
  ADR-0073（预设**目录**级白名单）、ADR-0074（技能级白名单）、ADR-0009（一份事实只有一个家）、
  ADR-0015（非机械改动必须留痕）、总账 P-02（仪器假绿）、P-08（用纪律守边界）、P-10（射程由本机状态决定）

## 背景

客户在第二台机器上装完 2.4.0 后打开 DSH，**`结伴 · 达人与联盟合作`（`agt-033`）这个 preset 加载失败**。

实测成因（读数在 Note 里逐条列出）：出货的 `skills-presets.tar.gz` 里，
`presets/agt-033/agent.cordis.yml:168` 带着一行

```yaml
# 本机装配：深链星探 KOL Hunter（ADR-0061）
- id: product-kol-hunter
  name: 'dsh-kol-hunter-local'
```

而同一份载荷的出货 profile **没有**这个包（依赖与 bundle 都被剥掉了，这是 ADR-0056 的要求；
`dsh.profile.bundles` 里没有它，`node_modules` 里也没有目录）。行还在、包没了 → 该 preset 里
这条行解析不到 → 整个 preset 加载失败。

**更值得修的是「为什么没被拦住」。** 已有的两道判据都是**反向特征**：

- `select-presets.mjs`（ADR-0073）管的是「哪些**目录**出货」——`agt-033` 本来就该出货，
  它在这道判据的射程外；
- `strip-local-products.mjs` 管的是「**本机挂的外部产品**」：先在暂存 profile 的 `file:` 依赖里
  算出「外部产品名」集合，再拿这个名字去删补丁行。

第二条在**依赖还在**时会命中。但 2.4.0 装配的那一刻（09-14 11:2x），本机 profile 里那条依赖与
bundle 早已被 09-13 的安装抹掉，只剩 preset 里这一行。于是 `extNames` 为空，脚本**如实**报告
「✓ 出货面没有本机装配的外部产品」——那一行大摇大摆出了门。

同一份 preset、同一台机器、两种本机状态，判据给出**相反的结论**（两行命令的实测输出见 Note）。
判据的真值不该由开发机此刻的状态决定。

## 决策

**新增行级判据 `check-preset-rows.mjs`：出货副本里每一条插件行的 `name`，必须在出货面里解析得到。**

- **事实来源换成出货面**：解析面 = 出货 profile 的 `node_modules` ∪ app 内嵌的 `node_modules`
  ∪ `packaging/local-only-preset-rows.json` 里显式登记的 `builtins`。判据不再问「本机挂没挂外部产品」，
  而问「出货那个东西里有没有这个包」——这是**产物**的性质，不是开发机的性质。
- **已登记的本机装配行：登记即权威**。`localOnly` 里登记的行从**出货副本**剥掉（连同紧贴其上的
  注释），并逐个打印读数；**哪怕本机此刻真的装了这个包也照样剥**——「本机装没装」正是上一版判据
  失效的原因。本机 `~/.dsh/.agent-presets` 下的原件不动。
- **未登记又解析不到的行 → 装配中止**，点名到「文件 + 行 + 包名」，并给出两条出路
  （登记为本机装配 / 把该包装进出货面）。
- **看不见就不能报「没问题」**：解析面不存在、登记处不存在、登记缺 `why` ——一律 `exit 2` 响亮失败。
  过期的登记只告警不判红（失效方向是安全的，与 ADR-0073 的 `exclude` 同一条规则）。
- 判据挂在 `assemble.sh` 的 **tar 之前**（判的就是即将打包的那份字节），自测挂在门禁
  `preset-rows-resolvable-selftest`。

这是 ADR-0073 / ADR-0074 那套语法的**第三层**：目录级 → 技能级 → **行级**。三层的形状一致：
出货面由显式表态决定；未登记 = 没人表过态 = 停下来问；已评审的例外必须写理由，且写在**一个**地方。

## 备选方案

1. **把 `dsh-kol-hunter-local` 重新烘焙进出货面**（让那一行能解析）。
   否决：这正好复活 ADR-0056 要解决的机器路径问题——客户机没有 `/Users/lute/project/KOL-Hunter`，
   装了包也没用，而且等于把一个本机产品塞给客户。
2. **把本机装配行从 `~/.dsh/.agent-presets/agt-033/agent.cordis.yml` 里搬走**（本机不再需要那一行）。
   否决：那一行在本机是**有用的**（ADR-0061：L2 产品技能随 preset 加载）。为了出货而搬走本机正在用的
   装配，与 ADR-0073 拒绝「把 bobo-cto 移走」是同一个理由。
3. **补丁 `strip-local-products.mjs`，让它别依赖本机依赖。**
   否决方向不对：那条判据的语义是「外部产品」，它的输入天生是本机 profile。要修的是**问题本身**——
   「这一行能不能被解析」是出货面的性质，所以新判据自己算出货面，而不是让旧判据去猜本机。
4. **只加一条「出货 preset 不许出现 `dsh-kol-hunter-local`」的黑名单。**
   否决：那是**第二份事实**（ADR-0009），产品一改就漂移，而且只防这一个包名；下一条别的行悬空时
   照样静默出门。判据要是闭合的，不是点名的。
5. **让 install.sh 覆盖已装的 preset 文件，用「下一版覆盖」来收场（本次未做）。**
   留作已知缺口：`install.sh` 第 5/6 步对 presets 用的是 `cp -Rn`（不覆盖已有），
   所以**已经装上 2.4.0 的机器，即使下一版的 preset 是干净的也收不到修正**。这条要么改安装器语义
   （产品自带的 preset 属于产品内容，升级时应更新；用户自建的 preset 不动），要么走人工修复。
   本次先把「不再发出坏字节」锁死，并给出人工修复的一条命令。

## 后果

**正面**

- 「出货面里解析不到的行」从**静默**变成**中止 + 点名**：判据在真实的 2.4.0 字节上实测
  51 个预设 / 1582 条行 → 恰好 1 条违规（`agt-033:168`），零误报。
- 判据不再随开发机状态漂移：自测里同一份字节、只换解析面的一对用例（S2 判红 / S5 判绿）钉住了这一点。
- 900+ 行里三种 name 形态（裸包名、`包/入口` 子路径、`__DSH_HOME__` 占位符路径）都覆盖到了；
  解析取**包名**、不校验入口子路径（边界写在脚本头部，不猜）。

**负面 / 待办**

- 解析面是**目录存在性**，不是 Node 的模块解析算法：不查 `exports`/`main`，也不查「目录名 ≠
  包内声明名」的情形。后者会被判成「不存在」→ 响亮失败 → 由人决定，不会静默放行。
- `install.sh` 的 `cp -Rn` 让已装机器收不到修正（备选方案第五条）。这是同一个根因的另一半，
  需要单独一次决策。
- 本机开发机的 `agt-033` 仍是「preset 行在、包不在」的状态（KOL Hunter 的依赖与 bundle 在
  09-13 的安装里丢了）。出货面已不再受它影响，但本机要用 KOL Hunter 仍需按 ADR-0061 重新装配。
