# ADR-0076 · 发布链的最后一环：入库版本必须有分发面，跳过的版本必须被记录

- 状态：accepted
- 日期：2026-09-13
- 决策者：用户（lute）+ agent
- 决策记录：[Note](../notes/implemented/contract/2026-09-13-release-published-surface.md)
- 相关：ADR-0002（DMG 发布走 Releases 附件 + `release/` 哈希清单——本 ADR 第一次把它**完整**执行到位）、ADR-0001（发布渠道需同时覆盖 codeup 与 GitHub）、ADR-0057（产物丢了要找回不要重做）、ADR-0058（入库清单先于 tag 落库；**tag 是「这是发布版」的唯一家**）、ADR-0067（已发布产物不可删除）、ADR-0075（判据的射程；本 ADR 沿用「射程从 git 里的家推导、射程为空必须报跳过」）

## 背景

2026-09-13 收尾时对账，发现发布链**前四环全齐、第五环从来没有过**：

| 环节 | 家 | 状态 |
| --- | --- | --- |
| 产物 | `packaging/release/<版本>/` + 仓库外归档 + `uchg` | 齐（ADR-0057/0067） |
| 入库清单 | `release/<版本>.sha256`（进 git） | 齐（ADR-0058） |
| tag | `v<版本>` | 齐（2.0.1 / 2.2.0 / 2.3.0 / 2.3.1 / 2.3.3） |
| 代码 | `origin` + `codeup` | 齐 |
| **分发面** | **GitHub Releases** | **缺** |

实测读数：`gh release list` 最新是 **v2.0.0**（2026-09-10），而仓库根 `README.md` 正告诉客户
「从 Releases 下载」。也就是说**客户按文档操作拿到的是一份早三个版本的包**，而新版本的分发实际走的是
IM（2.3.1 的产物是从飞书收到的副本找回的，带 `com.apple.quarantine: …;Feishu;`）。
四个版本（2.0.1 / 2.2.0 / 2.3.0 / 2.3.1）从未在任何公开分发面出现过。

这条缺口**没有任何机制能发现**：清单机制只保证「字节能找回」，tag 只保证「这串字节对应哪份源码」，
两者都不会问「有没有把它送到客户拿得到的地方」。

同一次对账还暴露一个口径问题：**v2.3.2 有入库清单（提交 `0ca9886`）与已归档锁定的产物，却没有 tag**。
它的来历是——15:10 切出，随后发现载荷里「用户需授权第三项：输入监控」的说法是错的（实际只需两项），
17:45 重切为 2.3.3。它在**通过发布判据之前**就被取代了，tag 那一步被跳过。

## 决策

**1. GitHub Releases 是每个「入库且已打 tag」版本的分发面，不只是最新版。**
本次补齐 v2.0.1 / v2.2.0 / v2.3.0 / v2.3.1 / v2.3.3，每个 Release 带 DMG + `SHA256SUMS`，
notes 写明构建号、源提交、profile 快照、SHA256 与**该版的已知缺口**（未修的白屏问题、错误的授权说法、
不可重建的字节）——是一份**构建记录**，不是逐版公告。

**2. `Latest` 只给最新的入库版本。** 历史版本一律 `--latest=false`，不得因创建时间较晚而顶成 Latest
（否则客户从 Releases 首页拿到的是旧包）。

**3. 没有 tag 就不是发布版：v2.3.2 不补 tag、不发 Release。** 它的缺席是**被记录的事实**
（写在 v2.3.3 的 release notes 与 `CHANGELOG.md`），不是缺口。补 tag 等于把一份
**已知带错的载荷**作为可下载版本公开，且 tag 时间会晚于构建时间。

**4. 发布前必须复核两件事**：产物哈希 vs 入库清单（`shasum -a 256 -c`）、载荷敏感内容扫描
（凭证、密钥、token——DMG 里含 profile 快照，而仓库是**公开**的）。

**5. 判据落成门禁而不是纪律。** 新增 `packaging/scripts/release-publish-status.mjs` 与门禁
`release-published`（`full` 模式）：**射程 = 既有 `release/<版本>.sha256` 清单、又有 `v<版本>` tag 的版本**
（两边都在 git 里，符合 ADR-0075 的「射程从家推导」）；对这些版本逐个查 GitHub Release 是否存在且**非 draft**。
`gh` 不可用或未认证时报 `skip` 并说明——**跳过不算通过**。射程取合取是刻意的：只有清单没有 tag 的
版本（如 2.3.2）自动出局，不需要再维护一张「已评审不发」的表。

## 备选方案

- **甲：只发 2.3.3。** 否决：客户按 `README.md` 下载到的仍是 2.0.0，断层没消除，而且它正是
  「发布史上留一个说不清的缺口」——本次要消除的就是这个。
- **乙：给 2.3.2 补 tag 并一起发布。** 否决：见决策 3。发布历史要的是**可核对的记录**，
  不是**连续的数字**；补 tag 会把一份已知带错的载荷说成发布版。
- **丙：不发 DMG 附件，只在 Releases 里写哈希。** 否决：ADR-0002 已定 DMG 走 Releases 附件；
  不发附件等于没有分发面，与本次要修的东西同形。
- **丁：不加门禁，把「记得发 Releases」写进 SOP。** 否决：这正是 P-08
  「用纪律守只有机制能守住的东西」。缺口的成因不是「忘了」，而是**没有任何一环会问这个问题**。
- **戊：门禁射程取「所有 `v*` tag」。** 否决：`v0.1.0` 是早期实验、且早于清单机制，
  对它永远判红——与 ADR-0075 修掉的 `patch-anchors` 永久红同形（锚点清单单调增长 × 历史产物累积）。

## 后果

- **正面**：客户按 `README.md` 能拿到最新版；每个入库版本的字节有了公开可校验的家；
  「入库了但没发布」从此是一条会自己报错的读数，而不是要靠人回想的事。
- **负面**：约 3.2 GB 附件进入 Releases 存储；一经公开即可能被抓取——故决策 4 的敏感内容扫描是**前置**的，
  不是可选的。本次扫描结论：载荷内无凭证；两处疑似命中（`alg:none` 的 JWT、`AKIA…`）经定位分别是
  渗透测试技能包里的**文档样例**与 **base64 编码的 WASM 字节码**里的巧合序列。
- **后续动作**：
  1. `docs/sop/dmg-release.md` §6 把「发布到 GitHub Releases」写成与「打 tag」并列的编号步骤，
     附可直接执行的命令（含 `--latest=false` 规则）。
  2. 复发故障总账加 P-13。
  3. 2.0.1 早于清单机制、没有 `release/2.0.1.sha256`；`release-verify.sh` 已如实报为
     「未登记（早于清单机制）」并把它算作不允许删除的历史发布版本——本 ADR 不动这条口径。
