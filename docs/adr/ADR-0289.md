# ADR-0289 · 第 10 步 dispatch：契约三态、共享再核验、廉价端口重跑与端到端闭合

- 状态：accepted（2026-10-11）
- 日期：2026-10-11
- 决策者：用户（lute：同意下一批顺位与票据/loop）＋ agent（取证与实施）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-11-session-prompt-dispatch-step.md)
- 相关：[ADR-0288](ADR-0288.md)（persistence 步）、[ADR-0287](ADR-0287.md)、[ADR-0249](ADR-0249.md)（十步链）、[ADR-0174](ADR-0174.md)（Application Service 边界）

## 背景

第 9 步闭链后链路停在 dispatch 前。侦察确认：真实操作面 = 既有 `sessionSend` 通道（accepted / deferred / refused 三态，renderer 已按 `protected-effect-outcome-unknown` 禁重试）；admission 契约的 dispatch 结果只有 `receipt | outcome-unknown`，无法把通道三态带回路由；边界文档 item 10 要求派发前再核验并「重新核验 Registry mapping 与 availability preflight」。本批同时暴露两处真实缺陷：① ADR-0288 的 `evidence` 在内核逐字段重建 fact 时被丢弃——端口直测与文本 pin 都看不见，**第 10 步端到端 spec 首先抓到**（真实 sends 会在 persist 处全部 fail closed）；② 我自己的共享再核验把 `frame.generation` 与 `contextGeneration` 相比（fixture 恰好同值掩盖），正确不变量是 `fresh frame.generation === fresh snapshot.frameGeneration`。

## 决策

1. **D1 契约三态（dispatched 结果）**：`ProtectedEffectDispatchResult` = `receipt{receiptRef, detail?}`（detail = 闭集 `SessionCoreDispatchDetail`：`session-send-accepted{sessionId,requestId,mode}` / `session-send-deferred{itemId}`）｜`refused{code}`（适配器自身的确定拒绝）｜`not-dispatched`（调用前守卫拒绝，效果确未发生）｜`outcome-unknown`。内核：malformed detail → 保守 unknown；`refused` 透传码；`not-dispatched` 映射回**可重试**的 admission `unavailable(dispatch)`——绝不冒充 outcome-unknown（那会错误地禁止重试）。admission 顶层新增 `refused` 变体与 dispatched 的可选 `detail`。
2. **D2 共享再核验 + 廉价端口重跑 + 归一化**：抽 `session-prompt-reverify.ts`（steps 9/10 单一家：context 等值、identity session、frame **fresh-vs-fresh** 不变量、store 重读 revisionDigest、current、live runtime-effective）；dispatch 端口在同实例上重跑 target/registry/preflight 三个真实端口并要求 ref 逐字节相等（identity/policy 重跑因 dispatch 请求不携带其事实、且全量重跑需重观测——均留登记票）。sessionSend 调用位于全部守卫之后（门禁按文本序钉住）；accepted/deferred → receipt+detail；通道确定拒绝 → refused 码；抛错 → outcome-unknown；调用前一切漂移 → not-dispatched。**v1 不写域收口**（见 D5）。
3. **D3 路由映射**：composition 把 dispatched+detail 映射为 `accepted{...}` / `deferred{itemId}`；有 receipt 无 detail 或非 dispatched 失败 → 既有保守路径（后者码 = `protected-effect-outcome-unknown`）。renderer 的 outcome-unknown 禁重试规则保持不变。
4. **D4 seam 证据存续修复（ADR-0288 回归）**：内核 compatibility 事实重建补 `evidence` 透传；dispatch spec 的内核级断言钉住 persist 实际收到证据；门禁新增 pin + 具名突变（丢证据即红）。
5. **D5 v1 边界**：attempt 在派发后保持 active——同一 matter 的第二次 send 在 persist 处 `active-attempt` fail closed（端到端测试明证）；回合收口流（artifact/receipt/failAttempt 由回合终态驱动）登记为后续票。frame 复核不变量修正见背景②，随共享助手落地。
6. **D6 门禁**：新增 dispatch 事实组（接线、seam 证据存续、detail 守卫、refused 码、not-dispatched 可重试、路由映射、共享再核验、三端口 ref 相等、调用后置、归一化、无域收口写）+ 七条具名突变；persist/reverify 的 pin 迁移到新家；三端口 pin 随之前的 constructor 提升改为调用形态。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 不扩契约，把三态编进 receiptRef 字符串 | 否决：契约滥用；renderer 需要结构化字段。 |
| 调用前守卫失败映射 outcome-unknown | 否决：效果确未发生，unknown 会禁止安全重试——不诚实且伤 UX。 |
| dispatch 端口自带三端口第二实现 | 否决：双实现必漂移；提升为同实例共享。 |
| 全量重跑 Identity/Compatibility 再派发 | 否决（本批）：身份事实不在 dispatch 请求内；compat 重跑需 50–200s 重观测——留 host-lifecycle 票。 |
| v1 同批落域收口（failAttempt/recordReceipt） | 否决：域 receipt 语义是人工评审回执而非通道 ack；收口语义（尤其 accepted 路径）需独立侦察与裁决——登记后续票。 |

## 后果

- **十步链首次真实闭合**：端到端测试走完 1–10 步——路由返回 `accepted{sessionId, requestId, mode}`（通道身份来自真实适配面）；第二次 send 因 attempt 未收口在 persist 处 fail closed（诚实记录）。
- 两处真实缺陷（上一批 seam 丢证据；frame 不变量比对错误）被端到端与共享助手修复，并各有断言与门禁 pin。
- 未闭：回合收口流（重复 send 前置）、WT-02B.3 授权证据、Host 生命周期失效、撤销运营、产品侧「进入 revision」流（R1 报告已呈报，含三条路径与七项裁决）。
