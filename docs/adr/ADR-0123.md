# ADR-0123 · 2.5.0 收口次序、清场射程与并发读数纪律

- 状态：accepted（2026-09-18）
- 日期：2026-09-18
- 决策者：用户（lute，「以上全部授权」+「我依然要一个深度解耦和干净项目产品」「v2.0.10 必须要成为一个完美的版本」）+ agent（射程与判据设计）
- 决策记录：[Note](../notes/implemented/process/2026-09-18-agent-readable-adr-ledger.md)
- 相关：ADR-0057（发布语义：原子就位 + 同号守卫，禁止同号重制）、ADR-0058（发布清单入库，清单是「我们承诺过什么」的家）、ADR-0067（**已发布的产物不允许被删除**：仓库外归档 + uchg + 门禁核对 + 找回命令）、ADR-0056（机器路径只减不增 / 靠人记得不是工程解）、ADR-0014（门禁硬门槛）、ADR-0121（对象库卫生）、ADR-0122（决策账本）

## 背景

用户要求对全仓做一次 MECE 深查（bug / 文档债务 / 工程债务 / 无用垃圾 / 深耦合 / 无用代码 / 无用备份），统筹打包后给出完整方案，且「一切不利于管理和打包 dmg 发布的，都需要做果断的处理」。

深查产出 7 类共 60+ 条，随后按用户授权执行了第一批处置。**执行过程中推翻了自己的一条结论**，这条推翻了整个清场方案的量级估计，因此必须留痕：

> MECE 清单把 `packaging/release/` 的 9 个历史版本 DMG（约 5.7 GB）归类为「无用垃圾 J1」，
> 并据此提出「release 7.2 G 迁出」。**这个归类是错的。**

推翻它的取证（三条，全部是读数）：

| 读数 | 命令 | 结果 |
| --- | --- | --- |
| 产物被 `uchg` 锁定 | `ls -lO packaging/release/*/*.dmg` | **9/9 带 `uchg`**——ADR-0067 决策 2 设计的「把误删变成必须表过态才可能发生」 |
| 缺席即判红 | `packaging/scripts/release-verify.sh:105-109` | 版本目录在、dmg 不在 → `FAIL=$((FAIL+1))`，即门禁 `release-artifacts-intact` 判红 |
| 用户已裁决 | `docs/adr/ADR-0067.md` 决策段 | 「**不允许删除发布的版本和历史发布的版本**」（用户裁决原文） |

也就是说，`packaging/release/<版本>/` 的两份副本是**设计出来的**：仓库侧那份是构建面与门禁的对照物（ADR-0067 决策 3「只做归档、不做仓库内副本：构建侧看不到产物、门禁无从对照」被明确否决过），仓库外那份是 `git clean -xdf` 与重新克隆都碰不到的不变量仓库。**把它当垃圾清掉，等于把 ADR-0067 整篇推翻，并让门禁在清完的那一刻变红。**

同一批处置还实测到两条与「读数可信度」直接相关的事实：

- **`.git` 里 716.63 MiB 的两个 `tmp_pack_*` 是垃圾**（`git count-objects -v` 自己记为 `garbage`），已定点删除；对象库 3.9 G → 80 M。这条**经得起复核**，与上面的 release 判定不矛盾——差别在于「它被任何 ref 可达吗、它是我们承诺过的字节吗」。
- **门禁在并发写入下会给出假红**：`repo-attest-selftest` 断言「门禁运行期间仓库零差异」，而另一个会话在 01:32–01:34 往 `.scratch/appearance-revamp/border-audit/` 新建文件，该判据因此判红；01:18 与 01:32 两次 `pnpm run gate` 分别读到 `failed=3` 与 `failed=1`，**同一份代码给出不同终值**。

## 决策

1. **已发布的产物一律不在清场射程内。** `packaging/release/<版本>/`（`uchg` 锁定）与仓库外归档 `~/Library/Application Support/LUTE/releases/<版本>/` 是 ADR-0067 的不变量，**不迁出、不删除、不改名**。撤销 MECE 清单里的 J1 归类。清场只处理「不被任何 ref 承诺过、也不构成证据面」的东西。
2. **清场射程三分，三分必须显式**：
   - **受保护**（不动）：已发布产物与归档、`.dsh-types/`、`dsh-rootoutlet-heal/`、`.dsh-root-brand-preview/`、`.ua/`、`dsh-patches/archive/**` 的 `.orig`（测试真值）。
   - **可删**（纯产物/备份，删前只需确认无引用）：对象库垃圾包、日志、`*.bak-*`、过期整档。
   - **需先证明**（物理删除前必须逐字节证明盘外有同一副本）：任何体积型二进制、任何「只在对象库存在」的路径。2026-09-18 的教训：删 codex ref 前若不先查「有没有只存在于对象库的文件」，会连带毁掉 `dsh-overseas-skills/check-fragment.py`（磁盘没有、git 未跟踪、只在对象库里）。
3. **2.5.0 的收口次序是「先清债、再定版本号」**（即 F1 的 C 选项）。理由：清债批次会改动 `packaging/` 与出货面（`assemble.sh`、补丁锚、机器路径基线），**现在定号等于定两次**。在清债完成前不重打同号、不升号、不打 tag。
4. **收口作业必须等并发写入停止。** 判据不是「感觉安静了」，而是读数：`git status` 的条目数在两分钟内不变、`.git/index` 的 mtime 不变、项目会话目录下 `session.v3.jsonl.zstd` 的 mtime 不变。
5. **门禁终值只在无并发写入时取，并记录取证时刻。** 并发下的红灯标为「并发假红」并**不得计入绿**；同时**不得因为它假就把它记成通过**——两种掩盖等价。`repo-attest-selftest` 的并发敏感性本身登记为待处理项（它断言的是「运行期间零差异」，在多人/多会话仓库里这是一个关于**环境**而非**代码**的断言）。
6. **「无用垃圾」这一类结论必须先过一遍「它被谁承诺过」再进清单。** 一条路径只要出现在 `release/*.sha256`、`uchg` 标志、门禁射程或 ADR 决策里，它就不是垃圾，而是**证据面**。这条写进清场流程：先查承诺，再查引用，最后才查体积。

## 备选方案

- **甲：按原 MECE 清单把 release 7.2 G 迁出。** 否决（已被取证推翻）。它会同时触发三件事：违反 ADR-0067 的用户裁决、让 `release-artifacts-intact` 判红、把「构建侧看不到产物」重新引入（ADR-0067 明确否决过该方案）。
- **乙：把仓库侧副本删掉、只留归档。** 否决。同上，且 ADR-0067 决策 3 的原文就是针对这一支：「只做归档、不做仓库内副本：构建侧看不到产物、门禁无从对照，等于把核对推给人」。
- **丙：先定版本号（重打同号或升 2.5.1），再清债。** 否决。清债会改动出货面与 `packaging/`，先定号意味着产物、tag、清单三者会在清债后再次分家——而「出货字节 = tag 字节 = CHANGELOG 条目 = DMG 清单」正是用户要的那条链。另：重打同号违反 ADR-0057 决策 6（同一版本号重做出的是另一串字节，不是那一版）。
- **丁：不区分并发假红与真红，一律按红灯处理。** 否决。那会让「门禁在并发下给假红」这件事无法与真实缺陷区分，最终所有人学会忽略红灯——比假红本身更坏。反之「一律按绿处理」会把真实缺陷洗掉。选定做法是**标注 + 不计绿**。
- **戊：把 release 产物加进 `.gitignore` 就不再管。** 否决。它们本来就被 `packaging/.gitignore:3` 忽略（`git ls-files packaging/release` = 0），忽略与保护是两件事：保护来自 `uchg` + 门禁核对，不是来自 git。

## 后果

- 正面：清场方案的真实可回收量从「虚高的 7.2 G + 若干」回到**可复核**的量级——已实测回收的只有对象库 3.7 G（3.9 G → 80 M，含 716.63 MiB 垃圾包与含活凭证的 6.8 GB 快照）。其余条目逐条待证。
- 正面：把「这条路径被谁承诺过」写进清场流程，堵住的是**这一类**误判，而不是这一个案例。
- 负面/代价：`packaging/release/` 会一直占约 5.7 GB。这是 ADR-0067 的既定代价，不是本 ADR 新增的。
- 负面/代价：决策 5 让门禁终值多了一条人工前置条件（确认无并发写入）。在单人机器上它便宜；一旦有第二个常态写入者，`repo-attest` 这一类的环境敏感断言需要重新设计——本 ADR **不假装解决它**，只登记为待处理项。
- 后续动作：ADR-0122 落地决策账本，让本轮的决策结果对 agent 可读；`repo-attest` 的并发敏感性单独立项。
