# ADR-0199 · 能力面只读投影：已配置／已启用／可用三态分开，基座自由文本不上屏

- 状态：accepted（2026-10-02）
- 日期：2026-10-02
- 决策者：用户（lute：授权接线 UI/UX 与后端，读侧按既有投影模式推进）+ agent（取证与实施）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-02-capability-readonly-projection.md)
- 相关：[ADR-0174](ADR-0174.md)（Application Service 唯一编排入口）、[ADR-0168](ADR-0168.md)（Host live inventory 观测）、[ADR-0171](ADR-0171.md)（Capability Registry 先治理后接线）、[ADR-0184](ADR-0184.md)（`/.sage/*` 恒由 main 终止）、[ADR-0198](ADR-0198.md)（host 侧消费与登记）

## 背景

接线工单 030（能力目录、市场与 Agent 配置只读）要回答三个**不同**的问题：哪些能力被**配置**了、哪些真的**启用**了、哪些**可用**。三者混淆是这一族页面最常见的失真：目录里存在当成可用、装上了当成启用、`broken` 行被写成"已停用"。

取证结果：

- 运行时**已经**提供一份真观测：protocol v5 的 `ready` 事件携带 `runtimeEffective`（`defaultPresetId` + `presets[{id,isDefault,broken?}]`），由 main 持有（`ShellHostProcess.readRuntimeEffective()`，本已供 inventory provider 使用）。这是"已配置 + 已启用"两个维度的真实事实源。
- "可用（外部能力/市场）"在生产里**没有** provider：C2C 的正式 seam 未开（ADR-0169/0170），Registry 只有治理内核（ADR-0171）。因此这一维只能是"未接线 + 原因"，绝不能渲染成"已停用"或空目录。
- 基座给的 `broken` 是**自由文本**（≤512 字符，可能含机器路径）。产品面按既有纪律（凭证/路径不上屏）不能原样透出。

## 决策

1. **D1 分类在 main，界面只映射**：`appservice/composition.ts` 把观测一次分类成 `CapabilityStatus{source, observed, reason, agentPresets[], external}`；`observed=false` 时**不带行**，只带原因码。界面按码查自己的静态文案表。
2. **D2 三态各自成词**：行内 `state ∈ {enabled, configured-not-enabled}`；`external` 恒为 `{state:'not-wired', reason:'capability-registry-unavailable'}`。任何位置不得把 `configured-not-enabled` 说成"已停用"，不得把 `not-wired` 说成"不可用"。
3. **D3 基座自由文本不上屏**：`broken` 的文本被就地丢弃，只映射成机器码 `preset-failed-to-activate`。理由与 001 同源：文案由界面自己的表给出，路径/秘密无从搭车（有断言：序列化后的投影不含 `/Users`、`secret`、基座原句）。
4. **D4 生产接线与再校验**：`main/index.ts` 把 `host.readRuntimeEffective()` 接进 app-service；该 reader 的返回类型是 `unknown`，故在接缝处**用 `isRuntimeEffectiveObservation` 重校验生产者自己的字节**（P-56），不合格即当作未读出，而不是把可疑对象分类。
5. **D5 写面无入口**：安装／启用／停用／撤销首版一律没有控件；面板里只有说明句。渲染行由脚本建 DOM，脚本的 `fetch` 目标只允许那三个已知路径常量或转发变量（有断言）。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 直接透出基座 `broken` 文本 | 否决：自由文本可能含机器路径，且把"文案"变成第二个真源（P-07/P-57 同族）。 |
| 把"市场/目录"渲染成空列表 | 否决：空列表读起来像"确实没有"，而事实是"没有来源可读"——正是本票要防的失真。 |
| 现在就给能力面接一个 Registry provider | 否决：正式 seam 未开（ADR-0169/0170/0171），先造 provider 等于用占位冒充权威。 |
| 让 renderer 自己从 `runtimeEffective` 原文里判断三态 | 否决：同一分类会散到界面（001 已立过的规矩：分类在 main）。 |

## 后果

- 能力面第一次有了**真数据**：Agent preset 名册与"未启用"行直接来自运行时观测；同时它对"外部能力"这件事诚实地说"未接线"，而不是留白。
- `CapabilityStatus` 成为第 4 个投影槽（继 `service` / `matter` / `runtime` 之后），`/.sage/state` 的消费者据此渲染；`matter` 槽仍是 fixture-only，两槽的诚实读法不同、不得混同。
- 风险：`runtimeEffective` 的生命周期绑在 Host 世代上（invalidation 后清零），所以界面会在宿主被判定失效时回到"未核验"——这是正确行为，但要求后续票在 UI 上区分"未核验"与"没有已配置项"（本票文案已分开）。
