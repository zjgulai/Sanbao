## 背景

LUTE 的出货面建在 `anywhere-labs/dsh-desktop` 的 fork 上，壳内嵌 harness submodule 提供 AI
运行时。上游约每月 1-2 次破坏性更新，每次要重锚 38 个补丁（12 壳层 + ~15 运行时层 + 品牌/判定
项）、迁移 15+ 处脚本硬编码路径，单次 2-4 周、年累计 8-24 周（spec §1）。根因是产品代码与上游
壳层的**打包实现细节**（ASAR/no-ASAR、chunk 哈希文件名、dist 路径常量）耦合，而这些细节每次
上游构建都会变。

用户的核心诉求是「只要 harness 的 AI 运行时核心能力，不要其桌面壳的实现细节」，spec 五题收敛出
**自建薄壳 + npm 版本依赖 + 渐进式绞杀**：LUTE 拥有 `apps/lute-shell/`，运行时从
`@deepseek-ai/dsh-*` 装，新旧壳并存到 P5 才退役旧壳。

P0 spike（[17 号报告](../research/17-thin-shell-spike.md)）已证明「npm 装 harness + 纯 Node 独立
boot」走得通，但留了两个必须先答的问题：

1. **宿主进程无处可取**。上游宿主入口在 harness submodule 的 `apps/desktop-host/`，而它没有发布
   到 npm——实测 `pnpm view @deepseek-ai/dsh-desktop-host versions` 返回 `ERR_PNPM_FETCH_404`。
   所以「消费 npm 上的宿主」这条路根本不存在，宿主必须自己持有。
2. **spike 的 `layers: 0` 归因错了**。17 号报告 §3 归给「缺完整 pnpm workspace / `.pnpm` store
   结构」。P1 实测证明真因是 profile 自己的 `package.json` 缺 `dsh.profile.bundles`：
   `loadProfileDirectory` 只从这个字段推 layers
   （`vendor/dsh-desktop/deepseek-harness/packages/boot/app-boot/src/profile.ts:781`），与
   workspace 结构无关。17 号报告 §3 已就地追加更正行，原文保留（当时的判断痕迹是历史记录）。

另有一条来自本仓自身的约束：2026-09 的黑屏事故（总账 P-52）确立了「挂死类故障必须先有不经过
故障现场的观测通道」。这条教训直接判掉了「把 AI 运行时放进 Electron 主进程」这个最省事的形态。

## 决策

**D1 宿主传输走子进程 + FD3/FD4 上的 DSH3 v3 帧协议。** 薄壳自己持有宿主入口
（`apps/lute-shell/src/host/`，移植上游 `apps/desktop-host/src/index.ts` 的 boot 与三路分发：
assets / api-gateway / remote-stream），Electron 侧用 `src/main/host-process.ts` 移植上游
`apps/desktop/src/host-process.ts` 的请求泵、背压与三段拆机阶梯（IPC shutdown + destroy 请求管道
→ 10 s → SIGTERM → 5 s → SIGKILL → 5 s → 抛错）。协议常量与上游 `wire.ts` 逐值对齐，并由
`lute-shell-pin` 门禁钉住不漂移。

**D2 profile 用「仓库 seed + 运行时物化到 `~/.dsh/profiles/lute-shell/`」。** 仓库里只存 5 个
seed 文件（`package.json` / `pnpm-workspace.yaml` / `pnpm-lock.yaml` / `cordis.yml` /
`cordis.patch.yml`），`pnpm run materialize` 把它们与构建出的宿主运行时拷进 profile 目录并在原地
跑真 `pnpm install`。seed 的 13 个 `@deepseek-ai/*` 依赖全部精确 pin，`pnpm-lock.yaml` 入库。

**D3 宿主运行时就位在 `<profile>/lute-host/`，使其裸导入解析到 profile 唯一一份 hoisted
node_modules。** 物化把 `lib/protocol.js`、`lib/host/*.js`（6 个文件）与
`config/shell.cordis.patch.yml` 拷进 profile 内的 `lute-host/`，宿主入口固定为
`<profile>/lute-host/host/index.js`，由父进程以 `ELECTRON_RUN_AS_NODE=1`（或
`LUTE_SHELL_NODE_BINARY` 指定的系统 node）启动，环境经凭证擦洗。

**D4 门禁只加静态 `lute-shell-pin`，不把 `apps/` 纳入 package collector。** 八条守卫：两侧
`@deepseek-ai/*` 非空且精确、两侧同名包同版本、两个 workspace 文件带未发布包的 override、7 个
协议常量不漂移于 submodule 参照、治理三字段取 `self`/`lute`/`false`、seed `cordis.patch.yml`
用户层剥注释后恰为 `[]`、12 个 test fixture 保持被 git 跟踪、壳 `devDependencies.electron` 精确
且与 `vendor/dsh-desktop/dsh-plugin-desktop` 的同名 pin 相等（参照缺失时跳过并进 note）。

## 备选方案

| 方案 | 为什么未采用 |
|---|---|
| 主进程内 boot（Electron main 直接 `await boot(...)`） | AI 运行时与 UI 同生共死：任一侧重挂即整窗黑，且**没有旁路**——P-52 的教训是观测通道必须先于挂死建立，进程内形态下不存在「不经过故障现场」的观测点。省下的是 390 行移植（`src/main/host-process.ts` 实测行数），付出的是整类挂死故障不可诊断 |
| harness 自带 HTTP 服务面（`loadURL('http://127.0.0.1:…')`） | 走浏览器客户端路径，而本机诊断手册（`dsh-desktop-diagnostics`）登记的两个已知客户端故障都在这条路上（`connection invalid server-response failure`、`settings are unavailable in this browser`）；另引入本地端口占用、来源栅栏、CSP 三个面。上游自己也是用 FD3/FD4 管道连宿主，不是 HTTP |
| 消费 npm 上的宿主包 | 不存在这个包：`@deepseek-ai/dsh-desktop-host` 实测 404（背景 1）。这条被现实否掉，不是被论证否掉 |
| profile 直接放仓库内（连同 `node_modules`） | 仓库沾 274 MB 依赖树与本机绝对路径；lockfile 的可移植性审计（`link:`/`file:`/绝对路径均 0 条）白做；与上游 profile 形态不同构，P4 打包要重新设计落点 |
| 物化用 symlink 代替真 `pnpm install`（P0 spike 的做法） | symlink 形态下 `nodeLinker: hoisted` 不成立，裸导入解析不到唯一一份 cordis，D3 的单一实例前提直接失效。（spike 拿到的 `layers: 0` 本身另有真因，见背景 2） |
| 把 `apps/` 纳入 package collector | collector 的分组语义是「五组能力」，`gen-catalog` 按组生成目录墙；`apps/` 不是能力组，纳入即改索引语义（ADR-0011）。本期用独立判定器覆盖同一批事实，P2 起再评估收编 |
| 不写独立门禁，靠 typecheck 兜住版本事实 | typecheck 不是常驻读者，而 `pnpm run gate` 是；`apps/` 对 collector 结构性不可见，本门禁是每次 gate 唯一会看薄壳版本事实的读者。用「另一条不一定被跑的检查」放行就是总账 P-08 |
| 门禁允许空依赖集（「没有 harness 依赖就没有违规」） | 空分母让两道版本守卫同时失去对象却仍报 pass，是教科书级仪器假绿。`scripts/gates/gate-result.mjs:116` 的既有教义就是 pass 要求 `checked > 0`（P-15）；故两侧空 map 一律判违规 |

## 后果

- **正面**
  1. 新壳的**壳层补丁数为 0**：`apps/lute-shell/` 下没有任何 `.patch` 文件，两个
     `pnpm-workspace.yaml` 都没有 `patchedDependencies`。spec §3 的对照表把旧壳壳层补丁记为 12
     个、目标 0 个——目标值在新壳侧兑现，旧壳的 12 个一个未动（P5 才退役）。
  2. spec §6 的更新路径第一段有了作用对象：seed 精确 pin + `lute-shell-pin` 守「range 即红」，
     上游发新 rc 时改一处版本号即可，不再重锚。
  3. P0 的 PARTIAL 收口：`layers: 0` → `layers: 2` 已实测，且根因换成了正确的那个（17 号报告
     §3 已追加更正）。
  4. 无头验收可重复：`pnpm run smoke` 走真管道、真 profile、真二进制往返，10 条断言全 PASS、
     退出码 0，不需要 GUI。
  5. 自有源码 1680 行 / 12 个 `.ts` 文件，其中 390 行（`src/main/host-process.ts`）是上游同名文件
     的逐段移植。
- **负面 / 需跟进**
  1. **`apps/` 暂不受 collector 治理**：`package-identity`、`catalog-fresh`、`scripts-runnable`
     都看不到薄壳；治理三字段由 `lute-shell-pin` 单独守，是第二份实现而非复用 collector 判据。
     P2 起需要重新评估收编还是长期双轨。
  2. **`agent-presets` 系统根注入被跳过**：npm tarball 无 `config/`，包内自带 shipped root。P2
     接真 preset 时必须复验——「现在不报错」不等于「注入路径正确」。
  3. **两个 native directory-picker 未插入**：P2/P3 若有面板需要选目录，要连壳侧 IPC 一起做。
  4. **smoke 不进 CI**（要真 profile 与网络），故「薄壳还能 boot」没有常驻读者。
  5. **`DSH_HOME` 未隔离**：薄壳首屏显示本机 DSH Desktop 的真实会话列表。spec §5 的「空 profile
     正常」定义是零 LUTE 插件，不含会话隔离；隔离属 P4 决策。已入库的首屏截图因此含真实会话
     标题，隐私面由用户裁决（可后续换空态截图）。
  6. **spec §6 的三条新门禁本期一条未上**，是有意裁剪不是遗漏：P1 无任何 pnpm patch，
     `patch-applies-clean` 无对象；`harness-version-pin` 的 P1 等价物即 `lute-shell-pin`；
     `submodule-ref-sync` 等 P3 有运行时补丁后再上。
  7. **一处过时指针**：`scripts/gate.mjs:328` 的 remediation 文案写死 `（ADR-0131）`，那是 Task 9
     派工时计划预判的编号，执行期已被并发的换皮 ADR 占用，本决策实为 ADR-0139。纯提示文本、不
     参与判定，留给最终评审做一处字面量替换。
- **判据射程**：本 ADR 覆盖「薄壳如何持有宿主、profile 落在哪、由哪条门禁守」。**不**为「薄壳
  已经可以出货」背书（那是 P4），也**不**改变 ADR-0008 对 `vendor/**` 只读的判定——本期全程
  未写 `vendor/**`、`~/.dsh/profiles/desktop/`、`/Applications/DSH Desktop.app`。
