# ADR-0224 · 动作级执行前确认：单卡＋一次性凭据＋派发前逐次重验

- 状态：accepted（2026-10-02）
- 日期：2026-10-02
- 决策者：agent（取证并实施；单卡与逐次重验是 FW-023/D-091 已定方向）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-02-action-confirmation-single-card.md)
- 相关：[ADR-0190](ADR-0190.md)（授权路径）、[ADR-0201](ADR-0201.md)（建项由托管侧收取）

## 背景

工单 025（FW-023，US-124~128）：会产生外部效果的动作给出**单张**执行前确认卡（对象/动作/资源/
范围/时间/前提＋可得的费用影响预估）；确认兑现该次派发的必要条件，派发前仍逐次重验；范围外新
动作、前提或版本变化使旧确认失效、需重新确认；确认≠效果已发生（结果仍按三态回执读回）；首版不
做多级审批、代理审批与审批队列。

本仓现状：`/.sage/actions` 是唯一业务派发口（`runCommand` 十步，ADR-0190 步骤 3–10 fail-closed），
但 001~024 期间没有任何东西要求"先给你看一张卡"；草案「确认建项」（create-matter，经托管侧收取）
是首版唯一在页面上真实可达的外部效果动作，此前单步直发。工单验收要求：①范围外动作无法用旧确认
放行（有断言）；②确认卡不伪装成审批流程、不产生多级路由。

## 决策

1. **D1 确认=一次性凭据，绑定精确意图与卡面事实（US-124/125）**：新纯内核
   `appservice/action-confirmations.ts`。`prepare(intent, facts)` 生成单卡并铸 `confirmationId`；
   记录绑定 intent 指纹（matterId/revisionId/actionType/actionScope/payload 的规范化摘要，
   `origin` 是传输元数据不入指纹）＋事实指纹（当前环境的 `environmentRef`）。`consume` 恰好花掉
   一次：未铸过的 id= `confirmation-required`、花过= `confirmation-consumed`、指纹不符=
   `confirmation-stale`。记录仅本运行内存活（上限 64、淘汰最旧）；未铸过的 id 永远不是"猜"。
2. **D2 失效即终局（US-126）**：指纹不符时把记录标死（stale）——即使事实碰巧恢复也不放行；
   "沿用旧页面状态放行"是被点名的反例。
3. **D3 两条派发路径都过同一道门（US-125）**：组合层新增可选 `actionConfirmations`
   （store＋facts 两件套；absent＝本票前形状，保持 011 的可选端口先例）。存在时：`dispatch` 对
   非 retry 意图在环境门（011）之后先 `consume`，失败以 `stage:'confirmation'`、`retryable:false`
   拒绝——任何流水线步骤都不跑；`convertDraft` 在打开 attempt **之前**同样过门（未确认的请求不
   落 attempt 记录）。两条路径共用同一个 store 与同一个 facts 家（main：事项的默认执行环境；
   create-matter 目标 `draft:<id>` 尚无链接→null）。
4. **D4 卡面口径（US-124/127/128）**：卡列对象/动作/范围/资源/时间/前提；费用影响预估在无估计器
   时如实 `unavailable`（不冒充数字）；卡带 `effect:'not-yet-happened'` 机器标记；页面文案明说
   "确认不等于外部效果已发生、结果按回执三态呈现、变化需重新确认"，**不出现审批/队列/代理字样**
   （有断言），卡上恰两枚控件（确认执行/取消确认），一级直连无路由。
5. **D5 草案面改两步（US-124）**：「确认建项」先 POST `/.sage/draft/prepare-confirm`（main 以与
   convert 同一 builder 组装 custody intent）拿卡；转换只在卡自身的「确认执行」点击后携带凭据发出
   （`/.sage/draft/convert` 体放宽为精确的 `{draftId}` 或 `{draftId, confirmationId}`）。卡挂本地
   状态、只属于其草案、跨 2s 轮询存活；stale/consumed/required 转为显式"重新确认"本地提示。
6. **D6 首版不做**：多级审批/再审/回避/用途恢复等审批流（D-106~118 属后置输入）；卡的持久化
   （跨重启需重确认）；费用估计器接线。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 确认放流水线内某一步 | 否决：确认是派发的**前置必要条件**（沿 011 环境门先例），放步内会与 3–10 fail-closed 的步骤语义纠缠。 |
| confirmationId 塞进 SageActionIntentV2 | 否决：该意图形状精确（额外键即拒）；凭据是传输层旁挂物，走 `{intent, confirmationId}` 信封。 |
| 指纹含 origin | 否决：origin 是"哪个渲染路径发的"，非动作身份；同一动作两次来源不同仍是同一动作。 |
| 失效后允许事实回滚复用 | 否决：US-126 点名"不能沿用旧页面状态放行"；标死是保守且可测的读法。 |
| 卡状态投影进 readState | 否决：卡是瞬态交互物，投影会把它伪装成持久事实；本地状态＋跨轮询守卫足够。 |

## 后果

- 五条机器判据（判者 `tools/verify_ticket.mjs`）：本票 8 个 spec 文件全绿；全量 106 文件 997 过/
  1 跳过（既有跳过项）；`pnpm run gate` 25/25、skip=0；10 条突变全部被具名红抓住（含 023 守护
  spec 在射程内）。
- 验收两条各有机器断言：范围外动作（payload/动作/matter/revision/scope 五种变化）携旧卡一律
  `confirmation-stale` 且记录标死、流水线零步；卡面无审批词、恰两控件、文案明说确认≠效果。
- 已知未闭：确认记录不持久（重启即 `confirmation-required`，需重开卡——诚实且保守）；无费用估计
  器（如实 unavailable）；真机未跑；审批路由族（D-106~118）与 041 的权限申请按各自票推进。
- 与既有票的兼容：`convertDraft` 未接线 store 时保持 002 形状（既有测试原样通过）；`.sage/actions`
  裸意图在未接线时保持 001/011/013 形状；接线时新增信封与 prepare 路由为加法式改动。
