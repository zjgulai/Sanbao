# ADR-0288 · 第 9 步 persistence：评估证据入链、域 authored attempt 与同事务原子落盘

- 状态：accepted（2026-10-11）
- 日期：2026-10-11
- 决策者：用户（lute：裁决证据入链方式、同意下一批顺位）＋ agent（取证与实施）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-11-session-prompt-persistence-step.md)
- 相关：[ADR-0287](ADR-0287.md)（preflight 步）、[ADR-0286](ADR-0286.md)（registry 步）、[ADR-0249](ADR-0249.md)（十步链序）、[ADR-0163](ADR-0163.md)（身份治理）、[ADR-0164](ADR-0164.md)（Authority 数据治理）

## 背景

第 8 步闭链后链路停在 persistence 前。落地侦察确认：域 v1 词汇表已含 `attempt-started`（含 `executionSnapshot`/`compatibility` 载荷与完整域构造器 `startAttempt`）；`CompatibilityEvaluationEvidenceV1` 编解码内核与 store 的 `appendWithCompatibilityEvidence`（事件 + 证据同事务）均已存在但从未接线；WT-02B.3 的 runtime AuthoritySnapshot → persistable AuthorityEvidence 转换**未批准**，故本步不写身份/授权证据，只写「本次实际使用的 CompatibilityEvaluationEvidence + attempt 准备事实」。两个既有缺陷被本批暴露：① 兼容事实只携带不透明 evaluationRef，evidence 不能在事后逐字节重建（issuedAt 时钟不可复现）；② 组合层的 intent.requestId = caller correlation，而生产 correlation 恒为常量 `caller:session-core`——同一 caller 的每个请求会铸造同一 attemptId（域重复 id 拒绝）且冒号违反证据 id 词法。用户裁决证据入链方式为「扩兼容事实携带封存证据」。

## 决策

1. **D1 证据入链（用户裁决）**：`EquivalentCompatibilityFact.evidence?: CompatibilityEvaluationEvidenceV1`（可选字段，形状守卫保持宽松；persist 缺证据即 unavailable）。证据在兼容步评估时刻由新模块 `session-prompt-evaluation-evidence.ts` 封存（字段逐项有家：matched rule 的 reasonCode/reason 取自 canonicalMatrix 的匹配规则；matrixArtifact 摘要与 artifactReference 用单一 `matrixBytesReference` forma；inventoryProviderProvenanceDigest = 观测证据的 mainObservationProvenanceDigest；sourceLineageDigest 沿用证据内核 spec 确立的 `{sourceId, supersedesSourceId}` forma）。发布件装载面扩暴露封存 bundle/revocation 同字节；persist 从同一发布件重建 historicalMatrix（不重读文件）。
2. **D2 域 authored attempt + 原子落盘**：persist 用 `startAttempt`（域状态机 + revision policy 校验）取得事件载荷；`executionSnapshot` 取 requirement 声明面、digest 列统一 artifactDigest（字节级执行物身份；契约/行为摘要留在评估证据与稳定对中）；`compatibility` 面取证据的 outcome/matrixId/reason。事件 + 证据经 `appendWithCompatibilityEvidence` 同一事务落 Sage-owned store；appendId = `session-prompt-attempt:${attemptId}` 幂等。`operationRef`/`dispatchRef` = attemptId 重命名空间（同一服务签发身份）。
3. **D3 紧邻写入前的再核验（item 9 的便宜真实子集）**：实时 context 仍等于准入请求 context、identity session 仍匹配、frame 仍 ready 且代不变、store 重读 revisionDigest 仍等于证据值、store 仍 current、live runtime-effective 仍 observed。移动即 `stale`、provider 缺失即 `unavailable`。「以 current inventory 重跑 Compatibility Resolver」需 50–200s 重观测，留在既有 host-lifecycle 失效票（ADR-0284/0286 登记），不在请求路径。
4. **D4 服务签发操作身份的缺陷修复**：组合层 `intent.requestId = randomUUID()`（每请求唯一），caller correlation 保持原义；重新把手写 correlation 当 requestId 由门禁具名拦截。
5. **D5 失败映射与门禁**：`appended`/`replayed` → allowed；`commit-unknown`、版本/幂等冲突、重复 id、存储阻塞、非法请求一律 `unavailable`——没有可证提交绝不进入派发。门禁新增 persistence 事实组（接线、index 开/交/关、身份签发、证据携带与封存、无证据拒绝、再核验三针、域作者、单一写路径、幂等 appendId、事务形态、commit-unknown 拒派发）＋七条具名突变；note 句收敛为「stops at the absent dispatch step」。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 每请求 holder 旁路把证据递到 persist | 否决（用户裁决）：隐式耦合，违背链的显式事实纪律。 |
| persist 事后重建证据 | 否决：targetEvidence 含 issuedAt 墙钟，逐字节不可复现；改动评估时点语义代价更大。 |
| 域外自撰 attempt 载荷直接编码 | 否决：绕开域状态机与 revision policy 校验；事件载荷必须域 authored。 |
| 沿用 `requestId = correlation` | 否决（既有缺陷）：同 caller 每请求同一 attemptId，域必拒。 |
| 只写证据、不写域事件（空 events） | 否决：域词汇表已有 attempt-started，就是「attempt 准备事实」本家；空 append 破坏流语义。 |
| 本批连 WT-02B.3 授权证据一起写 | 否决：转换未批准；raw session/claims 绝不落盘。 |

## 后果

- 十步链真实推进到第 9 步：窗口内 `session.send` 过 persist 后停在 dispatch（第 10 步 absent）；路由级仍 `protected-effect-unavailable`。
- 首次有真实持久副作用：attempt-started 事件 + 评估证据同事务落盘、可重开复核与严格重放（测试闭环）。
- 未闭：dispatch（窄 Adapter port）、WT-02B.3 授权证据持久化、Host 生命周期失效、撤销运营、产品侧「进入 revision」流（persist 需要于 store 已验证 revision digest 的 matter，与 compatibility 步现状天然一致）。
