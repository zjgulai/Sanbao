# ADR-0255 · UI 接线第八批：attachment cancel admission 收口

- 状态：accepted（2026-10-04）
- 日期：2026-10-04
- 决策者：用户（lute，确认执行 AUTH-02E）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-04-attachment-cancel-admission-batch-8.md)
- 相关：[ADR-0174](ADR-0174.md)、[ADR-0253](ADR-0253.md)、[ADR-0254](ADR-0254.md)

## 背景

attachment upload admission 完成后，`POST /.sage/attachments/cancel` 仍直接调用 raw `attachmentsCancel`。该 owner 会按 caller 提交的 `itemId` 修改 run-local record；record 已持有 `uploadId` 时还会调用 Host `attachment/upload-abort`。请求没有可信 matter / object binding，raw owner 也没有 durable operation、idempotency、receipt 或 `outcome-unknown` reconciliation，因此不能作为 production cancel dispatch。

## 决策

1. 本批只关闭 `POST /.sage/attachments/cancel` 的 direct-provider bypass。稳定 operation 为 `session.attachment.cancel`，candidate 固定为 `{ kind: 'active-session' }`，protected intent payload 只包含 `{ itemId: request.itemId }`。
2. `itemId` 只是未来 main-owned object resolver 的 opaque clue，不是对象所有权、matter、workspace、frame、actor 或 authority。`active-session` 只约束当前 session scope，不授予 cancel authority，也不能把 run-local record 或 UI stage 升格为 trusted target。
3. production 当前仍缺真实 Identity / Policy、trusted attachment object resolution、Compatibility、Registry / preflight、durable persistence 与 cancel dispatch，因此保持 unavailable-first。所有拒绝必须发生在 raw owner 前；raw `attachmentsCancel`、run-local record mutation、`abortOpen()` 与 Host `attachment/upload-abort` 调用数均为 0。
4. 真实 cancel 必须另票提供 exact sealed-record resolution、scoped request key、canonical intent digest、durable operation / idempotency identity、dispatch freshness、窄 cancel port、可查询 receipt 与 response loss 后只针对同一 operation 的 `outcome-unknown` reconciliation。transport abort、UI stage 或本地 record 变化都不是远端取消 receipt。
5. protected admission 从 12 条增至 13 条；全部 violation 从 23 条降至 22 条，其中 direct-provider bypass 从 18 条降至 17 条；route 总数与 classification 分母不变。本批不改 `pick`、既有 upload admission、workspace、renderer / UI、main attachment owner、Host、kernel、dependency、package / lockfile，不实现真实 resolver / dispatch / receipt / reconciliation，不跑真实 cancel E2E，不 commit、不 push。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 把 cancel 当作本地 UI 状态变化，继续调用 raw provider | 否决：raw owner 会修改 record，且可能调用 Host abort，属于 protected effect。 |
| active session 存在就直接放行 | 否决：session context 不是 standing authority，也不证明 `itemId` 的对象归属。 |
| 从 `itemId`、run-local record 或 UI stage 推导 trusted target | 否决：候选线索与局部状态不能替代 fresh main-owned object resolution。 |
| 增加 caller-supplied `matterRef` 并复用 upload candidate | 否决：自报 matter 不证明 exact object 绑定或当前 operation 可取消。 |
| 将现有 raw owner 视为合法 dispatch / receipt provider | 否决：它没有 durable operation、idempotency、receipt lookup 或未知结果 reconciliation。 |
| 同批迁移 `pick` 或 attachment UI | 否决：OS picker / candidate minting 与 UI 分别有独立 authority 和验收边界。 |

## 后果

- attachment cancel 不再有合法 direct-provider 路径；缺 production ports 时稳定 refusal，raw mutation 与 Host abort 不可达。
- `itemId` 维持 non-authoritative clue，`active-session` 不证明 object / matter ownership 或 cancel outcome。
- 真实 cancel 仍需 durable operation、exact target、dispatch freshness、receipt 与 reconciliation，不能由本 ADR 的 admission 收口冒充完成。
- authority truth 的目标值为 13 条 protected admission、22 条 violation、其中 17 条 direct-provider bypass；其余接线任务保持显式未完成。
- 本 ADR 不构成 attachment cancel 可用、UI/UX 复刻、真实 provider、发布、commit 或 push 证明；实现与验证结果以本批实际命令证据为准。
