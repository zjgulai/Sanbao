# ADR-0276 · T05 中段：session.prompt 首发 target 的候选生成与发布流程（第一刀）

- 状态：accepted（2026-10-10）
- 日期：2026-10-10
- 决策者：用户（lute：T05 中段卡在治理数据，选定「中段治理决策包（含候选生成线）」）＋ agent（取证与实施）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-10-t05-target-candidate-publication.md)
- 相关：[ADR-0165](ADR-0165.md)、[ADR-0166](ADR-0166.md)（Compatibility Authority 与 stable/full 分层）、[ADR-0172](ADR-0172.md)（target 治理）、[ADR-0174](ADR-0174.md)（Application Service 固定顺序与 unavailable-first）、[ADR-0275](ADR-0275.md)（会话族 Identity）、[C2E.3 记录](../notes/implemented/architecture/2026-10-02-wt02c2e3-runtime-effective-observation.md)（运行时侧稳定对与「矩阵物理重发」登记）

## 背景

T05 的第 5–6 步（target / compatibility）不是「接线缺环」：运行时侧的 descriptor 生产者真实存在（WT-02C.2E 线，稳定对与 goldens 由真机探针固化），真正的缺口是 **target 侧治理数据**——immutable target requirement 快照与按稳定对键控的矩阵物理制品（E.3 已把重发义务登记给「真实 Matrix Authority 发布票」）。requirement 的 `ownerDecision{decisionId,ownerId,decidedAt,reason}` 与矩阵 issuer/有效期是 product/security governance 的裁决字段，不能由 agent 单方面铸造；但其中可机械推导的部分（组件钉、语义摘要、配对）应当先落成**候选字节**，让 owner 的裁决是「审批具体字节」而不是从零构造。用户裁决：本刀落候选生成线 + 发布流程设计。

## 决策

1. **D1 候选=机械推导，不裁决**：四组件（provider/model/agent/preset）与 capabilities 逐字段复制观测 descriptor——`CompatibilityComponentRequirementV2` 与 `RuntimeComponentDescriptorV2` 同形是构造事实，「批准候选」即「批准确实出货的那一代」；`protocol/launch/overlay` 三个策略摘要取自 descriptor（产品线常量，非事项实例事实）；`permission/data-destination` 摘要由调用方提供的策略清单按域分离 canonical JSON 计算（**顺序即声明边界**）；`actionPolicies` 由调用方提供的 actionRequirements 转换（求值时修订必须声明同一元组——解析器会再核）。
2. **D2 候选容器不含 owner 决策**：新容器 `sage.target-requirement-candidate.v1`（`src/main/target-requirement-candidate.ts`，纯函数、零 I/O），显式携带 `observedRuntimeDescriptorDigest`（候选由哪一代真实事实推导）；seal 只在 owner 裁决后经 C2.2T 内核 `sealCompatibilityTargetRequirement` 执行——内核校验是唯一门，模块不重复也不隐藏校验。
3. **D3 发布流程（设计，随本 ADR 固定）**：候选生成（真实输入＝E 线 descriptor + 物化 profile）→ owner 裁决（决策三字段 + 规则 outcome/文案）→ seal requirement + seal matrix artifact（规则=配对候选 `targetSemanticDigest` 与**重观测**的 `runtimeDescriptorDigest`）→ 随壳加载（bundle 位置与加载面属发布票）→ providers 装配接准入 `resolveTarget`/`resolveCompatibility` → 撤销源与有效期管理。**发布必须重观测**：descriptor digest 已移动则候选作废——配对是绑定，不是背书。
4. **D4 首发范围**：`session.prompt`（external-write / 无决定门，与 action 表一致）；capabilities 首发为空（内部阶段无外部能力）；owner 数据裁决清单（requirement 标识与时窗、策略清单、组件与模型面的批准、矩阵文案与有效期、撤销节奏）逐项在 Note 中列出交付——数据裁决属用户。
5. **D5 本刀不接准入端口、不改 route 事实、不宣称 target/compat 已接**：模块是发布工具线（由测试真实跑通），真实数值与接线属后续票；不得用 fixture 或候选冒充已发布快照。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 直接写死首发 requirement 数据（含虚构 ownerDecision） | 否决：owner 决策字段是我方不能铸造的裁决事实；伪造 decisionId/decidedAt 正是本仓反复禁止的失真。 |
| 先接 resolveTarget/resolveCompatibility 端口、数据后补 | 否决：端口接了也恒 unavailable（无快照），且先接后补易滑向 placeholder——P-04 家族。 |
| 用 fixture 快照冒充首发发布 | 否决：fixture 不是发布，等同把测试绿灯冒充产品事实。 |
| 把候选生成做成一次性脚本 | 否决：推导规则需要版本化、被测试咬住、随内核演进（同形复制关系、摘要框架）——放 `src/main/` 纯模块。 |
| 首发即纳入外部 capabilities | 否决：C2C.5 尚未有真实 provider；`capabilities: []` 是内部阶段的诚实声明。 |

## 后果

- 候选→owner 裁决→seal→解析器 `equivalent` 的闭环被测试端到端咬住（fixture descriptor 下）；配对随 descriptor 移动立即失配（`no-matching-rule`，绝不回退）。
- 真实侧只剩两件事：owner 数据裁决（清单已交付）与发布接线（bundle/加载/provider 装配/撤销）；两者都不再需要发明设计。
- E 线的稳定对 goldens 是配对的一半真值；矩阵发布时以**重观测**的 descriptor digest 为准，goldens 漂移即矩阵键事件（E.3 已登记）。
- 未闭：resolveTarget/resolveCompatibility/resolveRegistry/preflight/persist/dispatch 端口、C2D.2A registry provider（descriptor 生产者的前置之一）、真实登录与真机首条消息；T05 不因本刀标记完成。
