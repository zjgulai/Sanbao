# ADR-0172 · Compatibility Target Requirements：revision-bound immutable requirement registry

- 状态：accepted（2026-09-29）
- 日期：2026-09-29
- 决策者：用户（lute）
- 决策记录：[Compatibility Target 治理记录](../notes/proposed/architecture/2026-09-29-compatibility-target-governance.md)
- 相关：[ADR-0165](ADR-0165.md)、[ADR-0166](ADR-0166.md)、[ADR-0171](ADR-0171.md)

## 背景

`BusinessMatter` v1 只保存当前领域所需的 provider、model、agent、preset、capability identity / version / digest 与 `matrixId + outcome + reason`。它没有一份由 Sage 拥有、可被审阅且可被安全内核重算的完整 capability requirement contract。若直接从 goal、自由文本、UI selection、action body 或 SemVer range 猜 target，Compatibility Authority 会把不可信输入抬升为 stable semantic key；若修改 v1 event schema，又会把治理缺口和历史回放迁移混在一起。

WT-02C.2T 的首步必须先固定 target requirement 的唯一事实家。真实 target provider、MatrixV2 provider、Application Service 和产品 UI 可以在没有 OIDC / bridge seam 的情况下继续分批实现，但不能在 schema / owner 未冻结前各自发明一套 requirements。

## 决策

1. **采用 Sage-owned immutable requirement registry。** `CompatibilityTargetProvider` 由 Sage product/security governance 拥有，消费只读、内容寻址的 requirement snapshot；它不接受 renderer、插件、Host、模型或普通 action caller 提交 authoritative target。
2. **不修改 v1 event schema。** 新合同使用独立的 `sage.compatibility-target-requirement.v1` schema、独立 canonicalization version 与 typed digest namespace。v1 event 继续只保存现有领域 DTO；target semantic / evidence 由后续 C2T provider 在编排层产生并由 C3 单独决定是否持久化。
3. **稳定 semantic 与单次 evidence 分层。** stable target material 只包含可跨事项实例复用的精确 action scope / effect、decision requirement、permission / data-boundary 语义和 Provider / Model / Agent / Preset / Capability 的 exact requirements；matter、revision、revision digest、具体资源 / 组织 / 账户、时间与 provider provenance 只进入 full target evidence。
4. **要求 exact requirement，不接受猜测或范围。** requirement 必须使用 Sage identity、exact version / digest、contract reference 与明确 schema；SemVer range、wildcard、mutable alias、自由文本推导、UI 选择、工具名称、package display name 和普通调用方自报 digest 都 fail closed。未分类或无法证明 provenance 的字段不能静默忽略。
5. **target 必须绑定 current revision。** full target evidence 必须绑定 `matterId + revisionId + revisionDigest` 与精确 instance boundary；provider 在 stable lookup 前先验证 current revision / action scope，revision mismatch、过期、撤销、重复、冲突、缺失或 provider unavailable 均返回 unavailable / unknown，不回退到旧 target。
6. **snapshot 只能追加发布。** requirement registry 的 canonical bytes、owner decision、effective / expiry / revoke 与 lineage 形成新的 immutable content-addressed snapshot；禁止可变 `latest`、原地编辑、从 revoked entry 恢复或按 matter / boot 动态铸造长期 stable key。发布、撤销与 retention 由 governance owner 管理，真实 provider 另票实现。
7. **本批只关闭治理合同。** WT-02C.2T revision 26 只新增 ADR、架构 Note、Compatibility Authority 与执行计划事实同步；不实现 provider、不生成 real target、不开 MatrixV2、不开 UI、不开插件、不接真实 identity / MCP / Registry / Adapter，也不修改 v1 event schema、package / lockfile 或产品调用面。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 直接扩展 v1 event schema | 否决；会把 target 治理、历史回放与领域存储迁移绑在一起，且当前没有 schema / retention / atomicity 决策。 |
| 从 goal、自由文本或 action body 推导 capability requirement | 否决；语义不稳定、不可审计，无法区分用户意图和安全约束。 |
| 让 UI / 插件 / Host 提交 target digest 或 requirement | 否决；这些来源没有 authority，最多提供候选 metadata。 |
| 使用 SemVer range、wildcard 或 mutable `latest` | 否决；引入规则优先级、重叠与漂移，破坏 MatrixV2 的唯一 exact lookup。 |
| 先接远端 target service | 延后；会引入网络、签名、bootstrap 与 availability 依赖；首批先冻结 app-owned immutable registry 边界。 |

## 后果

- 正面：后续 target kernel、MatrixV2 与 Application Service 共享同一份 revision-bound requirement contract，不再由各层猜测 target。
- 正面：稳定 semantic digest 与 full evidence digest 的职责继续分离，且不会侵入 v1 event schema。
- 代价：真实 target provider 必须等待 requirement snapshot / owner approval、current revision 与 provenance；本票不会让 Compatibility 变为 available 或 authorized。
- 代价：requirements 必须精确表达 identity、version、digest、contract 与 data boundary，早期候选会更容易返回 unknown。
- 边界：本 ADR 不实现 target provider、MatrixV2 provider、RuntimeInventory、Registry provider、Identity / Policy、Application Service、UI、插件或任何真实动作；C2C.2 formal seam 与 C2C.5 production provider 继续按各自门禁推进。
