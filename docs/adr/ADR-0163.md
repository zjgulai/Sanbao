# ADR-0163 · Identity / Policy Resolver：可信身份、组织授权与 BusinessMatter 决策分层

- 状态：accepted（2026-09-28）
- 日期：2026-09-28
- 决策者：用户（lute）
- 决策记录：[Note](../notes/proposed/architecture/2026-09-28-identity-policy-resolver.md)
- 相关：ADR-0159（Sage 自有产品与数据边界）、ADR-0160（本机活动仓与历史能力隔离）、ADR-0161（BusinessMatter 权威事件存储）

## 背景

现有 `BusinessMatter` 领域模型中的 `HumanRoleRef` 只有结构性的 `roleRef`。它能表达「本次领域命令声称代表哪个责任角色」，领域命令也会继续检查 revision、action scope、decision 生命周期、attempt、receipt actor 与 evidence refs；但这些规则不能证明当前人类主体是谁、属于哪个组织、是否真实持有该岗位、依据哪一版组织政策获得本次操作权限。renderer、HTTP body、插件、Harness connection、macOS uid、文件 owner 或结构相同的对象都不能替代这个证明。

三层责任必须分开：可信身份来源负责 authentication / assertion verification；组织政策负责 authorization；`BusinessMatter` 负责事项内部的审批与状态不变量。NIST SP 800-63-4 将 identity proofing、authentication 与 federation 分开，NIST SP 800-162 以 subject、object、requested operation 和环境属性对政策求值；OpenID Connect 可提供经过验证的认证 claims，但认证结果本身不授予 Sage 的组织岗位或业务操作权限。

仓库当前没有真实 Identity Provider、登录 session、组织目录或 policy authority。若直接把 `HumanRoleRef`、测试 fixture 或 UI 自报字段称为「真实身份」，会让产品表面接通、实际授权 fail-open。因此 WT-02B 必须先建立独立、纯、默认拒绝的 security kernel，同时明确它尚未关闭真实 provider 与产品接线。

## 决策

1. **三层分职。** Identity Provider 只证明 session、subject、audience、organization 与有效期，不拥有岗位或操作授权；Organization Policy Provider 是 subject → role 与 role → operation / action scope 的唯一 authority，并以分离的 `roleAssignments` 与 `grants` 产出有身份、版本、digest 与有效期的组织政策事实；Identity / Policy Resolver 对两者和请求上下文做确定性求值；`BusinessMatter` 领域仍独立执行 revision、decision、attempt 与 receipt 规则。任一层的成功都不能冒充另一层成功。
2. **security kernel 独立。** WT-02B.1 在 `apps/sage-shell/src/security/` 建立独立 kernel，不把认证或组织授权塞进 aggregate，也不提前创建 WT-02D 的 Application Service。kernel 不读写文件、数据库、网络或全局登录态，不执行领域命令，不写事件；外部输入按不可信值处理，形状或语义不完整时 fail closed。
3. **精确匹配、默认拒绝。** 裁决必须同时匹配受信 Identity Provider 给出的 issuer / subject / audience / session / organization，以及组织政策通过 `roleAssignments` 授予的 role、通过 `grants` 授予的 operation、`actionScope`、`effectClass`、`requiresDecision` 和 policy identity / version / digest 与有效期；Policy Snapshot 的 organization 必须与可信 assertion 的 organization 精确相同，重复 role assignment、重复或互相冲突的 grant 直接视为无效快照。未知字段、大小写或前缀近似、audience / session 错配、policy organization 错配、岗位未授权、policy / identity 缺失或过期、请求与 revision action policy 不一致均拒绝。请求中的 `sessionId` 只是让受信 provider 解析既有认证 session 的 opaque handle；固定 audience 由 resolver composition 注入，请求不能自报 audience、organization、subject、actor 或岗位证明。五种 `effectClass` 与 `requiresDecision` 保持正交，resolver 不从 effect class 暗推审批要求。
4. **allowed 不是领域批准。** 成功结果只能输出规范化 actor 与不可变 authority provenance，供未来受信 Application Service 继续调用领域命令。它不生成 `BusinessMatter` decision，不选择 attempt outcome，不接受 receipt，也不能绕过 `requiresDecision`、撤销、过期或责任角色规则。
5. **长期采用可审计 `AuthoritySnapshot`，本批不改 v1。** 长期事实链需要保留最小授权依据，使 decision / receipt 能回答 issuer identity / version / digest、稳定 subject、audience、session、organization、role、policy identity / version / digest、operation、完整 action policy（`actionScope`、`effectClass`、`requiresDecision`）、身份与政策有效期边界及求值时间。但 WT-02B.1 只让 resolver 输出这份不可变 provenance，不修改 v1 event schema；必须先选定真实 identity authority，并决策 PII 最小化、retention、删除传播与审计用途，再另批决定扩展 v1 或升级 schema。
6. **当前边界不扩张。** 本批不选择或接入 OIDC、系统账户、企业目录等真实 provider；不接 product、renderer、Capability Adapter、Host、main process、event store、profile、旧 DSH / Harness 账号、JEV、历史插件或真实业务数据。测试 provider 只验证 kernel 合同，不是真实身份或产品验收证据。

## 备选方案

| 方案 | 为什么未采用 |
| --- | --- |
| 继续把 `HumanRoleRef` 当作登录与授权证明 | 它只是领域角色引用，任何调用者都能构造同形对象；会把结构匹配误报为 authentication / authorization。 |
| 把身份和授权逻辑放进 `BusinessMatter` aggregate | 会让领域层依赖 session、issuer、组织目录和政策生命周期，破坏纯重放与确定性领域规则，也混淆组织授权和事项审批。 |
| 直接放进未来 Application Service | WT-02D 尚未开工；先在 orchestration 层手写判断会形成第二套策略实现，UI 或 adapter 更容易绕过。 |
| 现在选择 OIDC 或某个企业身份产品 | 产品尚未确定 issuer、账户生命周期、组织目录、离线策略与部署边界；过早选型会把外部协议细节钉入领域和事件格式。 |
| 本批立刻把 subject / session 写入 v1 事件 | 追加式事件难以撤回；在 PII、retention、删除传播和 provider 稳定标识未定前持久化，会产生长期隐私和兼容负担。 |
| 只记录 allow / deny，不保留授权依据 | 无法解释历史 decision / receipt 为什么被允许，也无法在 policy 版本变化后审计当时依据；与 AgenticOS 的长期可追溯目标不符。 |

## 后果

- 正面：认证、组织授权与事项审批有清晰 owner，UI、插件或结构化 payload 不能自授岗位和权限。
- 正面：纯 kernel 可用确定性、对抗性测试验证，真实 provider 可后置替换，不污染 aggregate、event store 或 UI 合同。
- 正面：长期 `AuthoritySnapshot` 方向已确定，同时避免在 PII 与 retention 未定时锁死追加式事件 schema。
- 代价：WT-02B.1 完成后仍不能声称 Sage 已有真实登录、组织权限或不可抵赖身份；没有受信 provider 与 WT-02D Application Service 接线时，kernel 只是安全边界和裁决内核。
- 代价：未来接入真实 provider 后，仍需决定 issuer / subject 稳定性、session 与 token 生命周期、组织政策来源、离线与撤销语义、PII 最小化、retention 和删除传播。
- 边界：accepted 只表示上述架构与 WT-02B.1 范围获得确认，不代表源码测试、真实 provider、产品调用链、AuthoritySnapshot 持久化或完整 WT-02B 已验收。
