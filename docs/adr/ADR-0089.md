# ADR-0089 · 全栈线 40 条入库：证据语料必须先于判定，无岗是一等结论，文档不许承诺没被守住的分型

- 状态：accepted
- 日期：2026-09-15
- 决策者：用户（lute）+ agent
- 决策记录：[Note](../notes/implemented/capability/2026-09-15-fullstack-40-role-assignment-and-icon-pipeline.md)
- 相关：ADR-0009（一份事实只有一个家）、ADR-0015（非机械改动必须留痕）、
  ADR-0052（第三方技能入库 SOP §12）、ADR-0085（归位 ≠ 接线）、ADR-0086（第零步独立成层）、
  总账 P-02（仪器假绿）、P-03（「知道」没有变成「拦住」）、P-04（写了但从没跑到）、
  P-11（判据的射程没有定义）

## 背景

方案决策②的 40 条工程技能（Matt Pocock 技能集）走完 P1–P4 并入 AI 全栈线。前四步
（结构体检 → 四件套 → 正文汉译 → 安装 + 来源留底）沿用 §12.9 既有路径即可；
**真正没有被验证过的是后三步**：归位、图标、以及「一批 40 条」这个规模本身。

上手第一条读数就否掉了「照既有脚本跑一遍就行」的假设：归位表的事实源是
`manifest/role-assignments.json`，而它的判据 J2 要求 `evidence.from_skill` 是
**技能原文的连续子串**——原文来自 `manifest/skill-evidence-corpus.json`。**本批 40 条
一条都不在语料里**（语料停在 T0 那批 251 条快照）。后果不是红灯，是**静默降级**：
校验器把覆盖不到的证据记成「不可复核」并单独计数，于是整批判定的可信度变成一句
无法回答的话——「结论对，但我没法证明」。

同一轮还量到三处形状不同、根因相同的问题：

1. **文档跑在实现前面。** SOP §12.5 在 2026-09-14 宣布把 `no_role_kind` 扩到 7 类
   （新增 `GENERIC_OFFICE` / `GENERIC_ANALYTICS` / `DEV_ENGINEERING`），但只改了文档——
   校验器的 `NO_ROLE_KINDS`、`test/role-map.spec.mjs` 的分型集合、manifest 里一条用例都没有。
   **照文档判就会撞红**，而 `J4-NO-ROLE-KIND` 的措辞把责任指向判定人。
   本批 40 条里绝大多数正是「工程能力」那一类，两个独立执行者都独立踩到并各自上报。
2. **能复现的创作决定没有落点。** 40 个技能头像要在本机资产
   `~/.dsh/skills/lute-brand-icons/` 里新增 40 条 `sk-fs-<name>` 条目——**40 个徽章选型
   全在本机、零留档**，重跑管线只能靠记忆复现。既有 `assign_lute_icons.py` 在缺条目时
   直接 `SystemExit`（点名 `sk-fs-git-commit`），这是对的；但它只能报缺，不能补。
3. **手改数字的地方还在长。** `verify-fullstack.mjs` 曾经硬编码「30/30」，SOP 自己标注
   「易漏」。本批要把 30 改成 70，正是它会再次腐烂的时刻。

## 决策

1. **证据语料先于判定，且覆盖率必须能被报出来。** 新增
   `scripts/build-evidence-corpus.mjs`：把目录里尚未收录的技能正文补进语料，
   **既有条目逐字节不动**（出海线 251 条抓自另一份源头，本机已无那份原文；
   用当前已装技能重算它们等于悄悄换掉判据基准）。两条守卫：`--check` 供门禁、
   写盘前证明「零改动往返逐字节相同」（`indent=1` + 末尾换行，不符即拒绝写盘）。
   判据从「我记得补了语料」变成「语料覆盖 = 目录里每一条」。

2. **判定与合并分离，判据只有一份。** 40 条判定分四批并行产出**片段**，
   由 `scripts/apply-role-fragments.py` 单点合并。子代理不得直接写归位表
   （多路写同一文件 = 静默覆盖）。自检器 `check-fragment.py` **直接 import 正式校验器的
   纯函数**（`validate` / `skill_text` / `role_text` / `check_quote_form`）把片段叠加到真表上跑——
   不复制判据，避免「自检绿灯、正式红灯」这种两个读取点口径不一致的老形态。
   合并器同时**重算** `coverage` 四个派生量与 `_meta.purpose` 的线别条数
   （手改一次要同时改五处，漏一处的表现是「门禁报一个和本次改动看不出关系的错」）。

3. **无岗是一等结论，不是失败。** 全栈线 70 条里只有 16 条挂岗；
   本批 40 条新增 8 个挂载、32 条无岗。无岗条目必须给分型 + 一段能独立读懂的理由，
   且理由要点名最近候选岗位并说明**为什么对不上**（含主动否掉的近邻，如
   `observability → AGT-046 溯源监测`是假朋友）。「挂岗率」不是本批的考核量。

4. **文档不许承诺没被守住的东西。** §12.5 改成分型表带**状态列**：
   生效四类与「🕓 未生效」三类分列，并写明照旧表判会撞红、以及真正启用需同改哪三处。
   同时新增门禁测试 `test/role-map.spec.mjs` 的「SOP §12.5 分型表与校验器逐字对账」：
   标为生效的必须与 `NO_ROLE_KINDS` 逐字相等，标为未生效的必须不在其中，
   且**文档举了例子的分型必须真在 manifest 里用过**（否则那是一条没人会发现的空头承诺）。
   这是把「知道」变成「拦住」——文档与实现之间的漂移从此由测试守，不再靠纪律。

5. **创作决定进仓库。** 新增 `scripts/add-fs-brand-icons.py`：40 行 `sk-fs-<name>` 条目
   按 id 归入 lute-brand-icons `catalog.js` 的既有块（保持字母序、不动其余 230 行），
   写盘前预览、`--write` 才落盘。**徽章选型表随脚本进仓库**，本机资产不再是唯一副本。

6. **计数从映射推导。** `verify-fullstack.mjs` 的 `TOTAL` 改为读映射条数；
   SOP §12.9 的「硬编码计数必须同步 +1（易漏）」一行改为记录这次去硬编码。

## 备选方案

- **让子代理直接改 `role-assignments.json`**：四路并行写同一文件，冲突与静默覆盖都无从拦；
  且覆盖率与 `_meta` 会在四次写之间互相打架。否决。
- **自检器各写一份判据**：本仓库最熟悉的失效形态（两个读取点口径不一致）。
  否决——直接 import 正式判据。
- **语料按「当前已装技能」全量重算**：会让 251 条既有证据的基准整体位移，
  而没有任何输出会提示这件事。否决。
- **直接实现 7 类分型**：会改变页面在场景组头聚合显示的分组（`buildOrgTree` 按
  `no_role_kind` 分组，客户端把分型原文打印出来），且需要重判既有 68 条无岗条目——
  产品可见的分组变化，未获明确决定前不做。**本次只把文档改成不再承诺它。**
- **把 `observability-and-instrumentation` 挂 AGT-049「运行监测」**：有正当先例
  （`analytics → AGT-046 数据管道 medium`，埋点判为管道前端实现），一度挂了；
  但 §12.5 的**分型表按名**把它列为「不服务出海业务的某一岗」，而 AGT-049 的监测对象是
  **Agent 平台任务的运行状态**、本技能的埋点对象是通用生产代码，两者之间要一层重定向。
  按「按名裁定 > 类推先例」改判无岗，并把反方口径原文记进 `no_role_reason` 备查。

## 后果

- 归位表 253 → **293 条**；有岗 225 / 无岗 68；挂载 **338** 条。
  **技能证据 338/338、岗位证据 338/338 全部可机械复核**。
- 复核覆盖 **1012/1014**（未达 100%）：两处 `responsibility` 留空但写明理由
  （`handoff/AGT-049` 既有 + 本批 `incident-retrospective/AGT-049`），
  校验器按「诚实标注，不判失败」记为 🟡。**这个数字要照实报，不得说成 100%。**
- 全栈线 70 条：`lib/catalog.js` 8 组 / 70 行；`skill-icons-fs.json` 30 → **70 枚**；
  `verify-fullstack` **70/70**；仓库门禁 **59/59**；包内测试 71 → **72 项全绿**。
- **顺带刷新（非本次意图，但必须说明）**：跑 `assign_lute_icons.py` 会把
  `category-icons-gn.json` / `skill-icons-gn.json` 重新导出——这两份仓库清单此前是**陈旧导出**
  （其内容与 lute-brand-icons 当前 catalog 不一致：`gn-cat-gn-data` 的徽章已由柱状图改为仪表盘、
  `sk-gn-chart-gen` 的衬衫已由 `G` 改为 `GD`）。枚数与键序不变，本提交把它一并对齐，
  否则仓库清单与生成器会继续各说一套。
- **运行层验收只取到一半，两半要分开说**。接口读数（`/api/dsh-overseas-skills/fullstack-list`）
  **仍是旧值 30**——宿主进程内存持有 catalog，生效需重启 DSH，而重启会中断当时会话，
  故这一项**未运行**，不写成通过。但「数据对不对」与「进程换没换」是两个问题，
  前者拿到了读数：进程外直接 import 宿主实际装载的 `lib/catalog.js`，按
  `handleFullstackList → buildGroupsLegacy` 的同一条分组语义（`skill.category === cat.key`）跑一遍，
  得 clarify 7 / spec 7 / architecture 10 / implement 5 / quality 12 / infra 17 / collab 7 /
  writing 5 = **70**，**与由映射推导的期望值逐组相等**；同轮读数为
  缺图标 0 / 未安装 0 / frontmatter 缺 description 0 / 未被任何分组收纳 0。
  ⇒ **重启后接口应当直接对上这组数字**；若对不上，问题在进程而不在数据。
- **已知未修（另立决策）**：lute-brand-icons 的 `lib/generator.js` 把**衬衫名**当颜色传进
  `shoulders()`（`shoulders(shirt, …)`，而 `COLLARS` 同一段用的是 `${W}`/`${G}` 值），
  `fill="W"` / `fill="GD"` 都不是合法颜色值 ⇒ **全部 310 枚图标的肩带渲染成纯黑**。
  实测读数：`sk-fs-tdd` 栅格化后肩带带 y=0.88 处采样 `(0,0,0)`（不只本批 40 枚，
  既有 270 枚同此）。修法是一行（加衬衫色表并传值）。**未修**：它会让 270 枚已验收图标的
  外观整体改变，属产品可见的品牌呈现变更，须用户明确决定后单独一次提交。
