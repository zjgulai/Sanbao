# ADR-0127 · 启动健康上报必须确认送达，不能赌"路由已就绪"

- 状态：accepted（2026-09-18）
- 决策者：用户（lute）+ DSH 基座迁移轮
- 决策记录：[Note](../notes/implemented/packaging/2026-09-18-boot-health-report-retry.md)
- 相关：ADR-0008（基座只 pin 不改）、ADR-0014（门禁硬门槛）、ADR-0114（补丁里的环境常量必须随基座形态一起判定）、ADR-0042（出货面契约）

## 背景

2026-09-18，DSH Desktop 2.5.0（基座 2.0.10）启动后**停在加载页**。宿主日志：

```
dsh-plugin-desktop: renderer boot failed (plugins: Unknown client plugin):
  The Renderer did not report boot health within 30000ms.
```

生命周期末尾 `event=renderer.boot.timeout`。而渲染器本身**完全健康**（探针实测：
`loader.await()` 120ms settle、entries=83 未激活=0、服务全在、进程采样显示主线程
99.7% 空闲待命）。

**机制**：宿主放行界面要求 `phase==="monitoring" && nativeMounted && rendererHealthy`
三者同时成立；`rendererHealthy` 只能由渲染器 POST `/_dsh/desktop/renderer-boot` 得到，
而**该路由由 `dsh-plugin-desktop` 宿主插件在自己的 `ctx.effect` 里注册**——effect 必然
晚于 `renderer.boot.started` 就绪。

实测同一端点在启动后 **+6s 返回 404**（路由未注册）、**+10s 返回 401**（已注册）；
同一套配置**连续两次启动结果相反**（一次 healthy、一次 timeout）。渲染器只发**一次**
POST，落在路由就绪之前就永久失败。

## 决策

**把一次性上报改成确认式重试**：退避重试直到拿到 2xx 或窗口耗尽（40 × 500ms，落在
宿主 30s 窗口内），网络异常同样计入重试。宿主判定逻辑**一行不动**。

补丁落到 `dsh-patches/boot-health-retry/apply-fixes.sh`（幂等 + 锚点唯一 + `node --check`
把关 + `.orig` 可回滚），并在 `patches-manifest-v3.md` §A（宿主壳层）登记。

**同时承认一条残差并记录在案**：按 §A 的既有声明，宿主壳层改动应由 **vendor LUTE 源码
提交**承载，而本次未改 vendor 源码 —— 因此**下次按来源重建会覆盖本补丁**。永久修复 =
在 vendor 的 `postRendererBootReport` 源实现里加重试并提交。

## 备选方案

| 方案 | 为什么未采用 |
|---|---|
| 宿主侧把超时从致命改为降级放行 | 能立刻解冻，但**掩盖**根因：上报通道坏了也会被判健康，等于删掉启动自检 |
| 去掉 `connection` 共用 entry 上的 `inject: [webRuntime, webServer]` | 实测**两面都坏**：删掉后宿主直接 `startup-failed`（`loopx-goalbar: cannot get property "webServer" without inject`）；该 entry 同时服务宿主与客户端组合，删任一半炸另一半 |
| 在 `/plugins` 组合层给 `connection` 拆第二条 entry（B2） | 机制未验证（既有经验：桌面组合层会**静默忽略 insert**），且改动面远大于一处竞态修复 |
| 改 vendor 源码并重建（§A 正统路径） | 是**正确的最终形态**，但需要 electron-builder 全量重建；本轮先以装配期补丁解绑事故，残差已登记 |
| 让渲染器"等 load 事件后再上报" | 实测无效（`readyState` 停在 `interactive`，`load` 不触发与本案无关）；且把成功寄托在另一个不确定事件上，不是修复 |

## 后果

- **正面**：启动页一直转的事故解除；连跑 3 次全部 `startup.run.completed` / `healthy`
  （各约 9s）。握手从"赌时序"变成"确认送达"，且失败时日志会给出重试次数与最后状态码。
- **负面/需跟进**：
  1. 残差 #1（来源未修）→ 需补 vendor 源码提交，否则重建即失效。
  2. 本补丁属装配期重放，**未进 NM 层**（NM 目标空间是 app `node_modules`，`lib/` 不在其中）。
  3. 这是**上游 2.0.10 的握手竞态**，值得作为上游 issue 上报：渲染器一次性上报 vs 宿主
     effect 迟到注册路由。
- **判据射程**：本 ADR 只覆盖"上报确认送达"这一条；**不**为"所有宿主端点都该被重试"背书
  ——其它端点（settings/picker 等）的调用点在用户交互路径上，本来就允许失败重试。
