# ADR-0173 · CompatibilityEvaluationEvidence：不可变旁路证据、历史矩阵与严格回放

- 状态：accepted（2026-09-29）
- 日期：2026-09-29
- 决策者：用户（lute）
- 决策记录：[Compatibility Authority](../notes/proposed/architecture/2026-09-28-compatibility-authority.md#25-wt-02c30-compatibilityevaluationevidence-治理合同revision-29)
- 相关：[ADR-0161](ADR-0161.md)、[ADR-0165](ADR-0165.md)、[ADR-0166](ADR-0166.md)、[ADR-0171](ADR-0171.md)、[ADR-0172](ADR-0172.md)

## 背景

`BusinessMatter` v1 的事件只保存当前领域需要的 compatibility DTO；它不能承载完整的 target、runtime、matrix provenance、revocation lineage 或严格回放所需的历史字节。若把这些字段直接塞进 v1 event，会把已经冻结的领域 schema、事件 hash 链、迁移和 retention 同时改写；若只记录 `equivalent + matrixId`，又无法证明一次 evaluation 当时看到了什么，或解释后来 matrix / runtime 漂移。

WT-02C.3.0 必须在实现 codec 或 persistence 之前固定唯一证据事实家、原子性边界、历史矩阵取证、retention / legal hold、purge / export / restore 和失败恢复。此 ADR 只做治理决定，不代表任何生产数据已经持久化。

## 决策

### 1. 独立旁路 evidence schema，v1 event 保持冻结

采用独立的 `sage.compatibility-evaluation-evidence.v1` 旁路证据记录及独立的 `sage.compatibility-evaluation-evidence-canonical-json.v1` canonicalization / digest namespace。证据记录与 `BusinessMatter` v1 event 分开建模、分开回放，但由同一个 Sage main-owned persistence boundary 管理；本 ADR 不修改 v1 event、v1 codec 或现有 event hash 链。

最小完整记录必须绑定以下事实：

- `evaluationId`、`attemptId`、`matterId`、`revisionId`、`revisionDigest` 与精确 `actionScope` / `actionIntentDigest`；
- `targetSemanticDigest`、`targetEvidenceDigest`、`runtimeDescriptorDigest`、`inventoryEvidenceDigest`；
- `matrixId`、`matchedRuleId`、`outcome`、稳定 `reasonCode` / `reason`、`evaluatedAt` 与 resolver contract version；
- 当时的 target / inventory / matrix provider provenance reference；
- matrix canonical artifact reference（内容寻址的 matrix ID / canonical bytes digest / immutable artifact reference）；
- 独立 revocation source ID、source provenance digest 与当时适用的 revocation lineage；
- evidence schema、canonicalization、digest namespace 与生命周期状态。

raw token、claim、secret、机器绝对路径、完整请求体和未分类的 caller / plugin 自报字段不得进入 evidence。content digest 只证明 bytes 身份，不自动证明 provenance、authorization 或可执行性。

### 2. 历史矩阵与 provenance 必须可独立取证

evaluation evidence 保存当次 matrix 的不可变 artifact reference；MatrixV2 provider 的当前 `latest`、当前 bundle 或当前 revocation source 不能替代历史引用。C3.2 的持久化实现必须能按 reference 取回当时的 canonical bytes / verified artifact，校验其 digest、matrix ID、bundle lineage 与 revocation source；取回失败或 bytes 被篡改时必须返回 `historical-artifact-unavailable` / `evidence-corrupt`，不得使用今天的 matrix 重新求值。

历史 artifact、revocation source、provider provenance 与 evidence envelope 必须作为可审计的关联集合管理；任一部分无法证明时，strict replay 只能失败闭锁，不能把原来的 outcome 改写为新的 outcome。

### 3. Strict replay 是历史验证，不是重新授权

strict replay 只读取封存的 evidence、当时的 canonical subject / matrix artifact 和 lineage，重算 digest、验证 schema / binding / integrity，并返回原始 `outcome`、`reasonCode`、`reason` 与不可变 provenance。它禁止调用当前 target、runtime、MatrixV2、Registry、Identity / Policy provider，禁止依赖当前时间重新判断有效性，也不能产生新的 action authorization。

历史证据过期、撤销、被 purge 或 artifact 不可取回时，replay 返回明确的 unavailable / corrupt 结果；这不改变历史记录本身，也不把历史 `equivalent` 变成当前可执行。

### 4. 原子性采用 main-owned 同一事务，失败闭锁

对需要 compatibility gate 的 attempt，`CompatibilityEvaluationEvidence` 的 durable append 与 attempt / decision receipt 必须位于同一个 Sage main-owned SQLite transaction / adapter boundary 中；新增旁路表或 stream 不等于修改 v1 event schema。只有 evidence append、digest 校验和 attempt append 全部成功，attempt 才能进入下一状态或产生任何外部副作用。

若未来 evidence store 与 attempt store 不能共享同一事务，必须先另立 outbox / prepare-commit / compensation ADR；不得用“先写 attempt、再 best-effort 写 evidence”或“先执行、最后补审计”替代原子性。任一 append、commit、恢复或校验失败都返回 `compatibility-evidence-unavailable`，阻断 action；若已经写入 prepare 记录，则只能通过显式、幂等的 compensation / recovery receipt 收口，不能删除或覆盖原始失败事实。

### 5. Retention、legal hold、purge、export 与 restore 作为同一治理边界

证据、历史 matrix bytes、revocation source、provenance reference 与 purge / export / restore receipt 分成可审计的数据类，但共享 lineage 和 retention policy。没有产品 / 法律确认前不预设全局 TTL；policy 必须能表达 `active`、`retention-expired`、`legal-hold`、`deletion-pending`、`purged` 五种生命周期。

- legal hold 只暂停允许的 purge，不修改 evidence bytes，不原地延长或重写事件；解除 hold 后重新评估 retention。
- purge 必须是幂等、可重试、可审计的操作，覆盖 envelope、matrix artifact、revocation / provenance 索引和导出副本，生成独立 purge receipt；不得改写 append-only event hash 链。
- export 必须携带 schema、digest、lineage、hold 状态和“不可作为当前授权”的声明；restore 必须重算并验证所有 content IDs，缺失或冲突时 fail closed，不能静默恢复为 active。
- 删除传播不清楚、备份未确认、存在 legal hold 或任一关联 artifact 仍不可定位时，状态保持 `deletion-pending`，不得报告 purge 完成。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 直接扩展 `BusinessMatter` v1 event | 否决；会把领域 schema、hash 链、迁移与 evidence retention 绑定，超出本票且破坏 v1 冻结。 |
| 只存 `matrixId + outcome + reason` | 否决；无法解释当时 target、runtime、matched rule、provenance、revocation 或历史 bytes。 |
| 单独最佳努力 audit DB | 否决；与 attempt 分裂时会产生“动作有了、证据没有”的不可审计窗口。 |
| strict replay 调当前 MatrixV2 重新计算 | 否决；当前 provider 漂移会改写历史事实，且把 replay 偷换成重新授权。 |
| purge 时直接改写 / 删除 event hash 链 | 否决；破坏 append-only 完整性；删除必须通过独立、可验证的 purge receipt。 |
| 把 raw token、claim 或机器路径放进 evidence | 否决；扩大泄漏面，且不属于 compatibility authority。 |

## 后果

- 正面：v1 event 保持兼容，evaluation 的完整事实、历史矩阵和 strict replay 有唯一治理边界。
- 正面：evidence append 失败会在副作用发生前 fail closed，后续 Application Service 可以只消费已验证的 receipt。
- 代价：C3.1 必须实现更严格的 exact codec / canonical bytes，C3.2 必须处理同事务、补偿、retention、hold、purge、export 和 restore；单纯写一条 JSON 日志不合格。
- 代价：历史 artifact 被 purge、损坏或 provenance 缺失时，strict replay 可能只能返回 unavailable / corrupt；这比猜测或当前重算更安全。
- 边界：本票不实现 codec、store、schema migration、真实 provider、trusted clock、Application Service、UI、插件或任何真实 action；C3.1、C3.2 与 WT-02D 仍需独立确认和验收。
