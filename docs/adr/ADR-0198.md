# ADR-0198 · 只读基座事实的消费家：Cordis 宿主进程按登记消费，其余 src/ 保持词法禁 `ctx.get`

- 状态：accepted（2026-10-02）
- 日期：2026-10-02
- 决策者：用户（lute：选定 boundary 路线，授权在"等门绕开／缩窄射程／换承载位置"三条中落一条）+ agent（取证与实施）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-02-host-readonly-consumption-scope.md)
- 相关：[ADR-0174](ADR-0174.md)（Application Service 唯一编排入口）、[ADR-0179](ADR-0179.md)/[ADR-0184](ADR-0184.md)（`/.sage/*` 恒由 main 终止）、[ADR-0011](ADR-0011.md)（能力五组归位）、[ADR-0014](ADR-0014.md)（门禁硬门槛）

## 背景

接线工单 050（Host 窄桥只读基座方法刀）被 `gate:sage-product-boundary` 判红：该门禁对 `apps/sage-shell/src/**` 一律词法禁 `ctx.get(`。050 的实现本身不碰渲染面，但要在 booted 的 Cordis 容器里读 `settingsController`，于是必然撞上这条。

取证把三条候选路线的可行性逐条钉死：

- **换承载位置（把 provider 放进 `packages/` 插件）不足以免改门禁**：`gate:sage-service-consumption` 的 selftest 明写"Sage 扫描不得进入 packages/"（包可以消费、壳不行是本来的设计意图），但**组合进来的插件没有任何现成通道把结果送进 Electron main**——壳的 host 路由表是自建常量（`src/host/index.ts` 的 `handlers: Record<RouteTarget, FetchHandler>`），`handler.ts` 只是接口；`COMPOSED_PACKAGES` 装载机制完整但恒为空。新造端口/文件/旁路通道＝写一条从没跑过的管道（P-20），不取。
- **`src/host/` 是 Cordis 宿主进程本身**：`src/host/index.ts` 导入 `Context` 并 `boot()` 整个 profile，"不消费 Cordis 服务"对它并不是安全边界，而是把宿主进程逼成不会读自己容器的空壳。WT-02D.1 真正要退场的是 **P0-2 产品适配层**（`composer-adapter`/`composer-view`/`streams`/`product/state.ts`），这些仍在 `RETIRED_FILES` 里逐条守着。
- **仓里已有放行机制**：`scripts/gates/sage-service-consumption.json` 是"新消费点随提交登记"的登记处，判据四向对账（未登记文件／未登记服务／陈旧条目／陈旧文件全判红）并带 selftest。此前它对本壳是**空转**的——词法禁令让登记毫无意义。

## 决策

1. **D1 射程收窄到"宿主进程 + 登记"**：`gate:sage-product-boundary` 的 `ctx.get(` 词法禁改为跳过 `apps/sage-shell/src/host/**`；`src/product/**`、`src/main/**`、`src/appservice/**`、`src/profile/**` 等其余子树**照旧一律禁**，渲染面与编排面不因本 ADR 获得任何新能力。
2. **D2 放行的代价是登记**：`src/host/**` 的每个消费点必须在 `scripts/gates/sage-service-consumption.json` 登记（服务名全集、多算少算都红；`dynamic:true` 用于非字面量）。本票登记 `host/readonly-bridge.ts → settingsController`。这条由 `gate:sage-service-consumption` 与其 selftest 双面守着，不靠自觉。
3. **D3 反向自测同步改，且不得只测绿**：`sage-product-boundary.test.mjs` 里"host 侧 ctx.get 判红"那条钉子改为**双向**：`src/host/**` 的消费**不再**是边界红（改由登记把关），而 `src/main/**`、`src/appservice/**`、`src/profile/**` 的 `ctx.get` **仍须判红**；`sage-service-consumption.test.mjs` 里"0 个消费文件"的钉子改成"登记条数必须等于实际消费文件数"，另加"真实登记处必须能在严格模式（无 `allowEmptyRegistry`）下通过"。
4. **D4 只读、窄面、不碰写侧**：050 的桥只允许 `READONLY_BRIDGE_ENDPOINTS` 里的端点（当前仅 `settings/describe`）；两端各判一次 allowlist；结果必须通过纯数据判定（拒绝函数/符号/`undefined`/非有限数/稀疏数组等 JSON 会静默削掉的东西），否则以 `bridge-result-not-plain-data` 拒绝而不是降级呈现。写侧 RPC 一个都不开。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 把 provider 装进 `packages/` 插件，壳零改动 | 否决：没有现成 carrier；新造通道是没跑过的管道（P-20），且会把"谁读基座"这个事实拆到两个家。 |
| 维持禁令，改由 fixture 提供基座事实 | 否决：那是"归位不等于接线"——生产仍读不到，票做了也不成立。 |
| 直接删除 `ctx.get(` 检查 | 否决：D1 只跳过 `src/host/**`；其余子树的词法禁与 `RETIRED_FILES`、上游 token 检查全部保留，渲染面能力不变。 |
| 一次把写侧需要的动作权限也顺带登记 | 否决：写侧属 §7 治理面（`ACTION_AUTHORITY_TABLE` 与步骤 3–10 端口），与"读基座事实"是两件事，本 ADR 不夹带。 |

## 后果

- **解封范围**：050 与依赖只读基座事实的读侧票（010/012/013/017/026/030/031 等）不再被词法禁令挡住。
- **不放宽的部分**：ADR-0190 的步骤 3–10 fail-closed 端口未动；写侧动作仍须先登记 `ACTION_AUTHORITY_TABLE`；渲染面 `src/product/**` 的 `ctx.get`/`localStorage`/`/api` 等 token 禁令逐条保留。
- **可审计性**：任一新增 host 侧消费若不登记，`sage-service-consumption` 当场判红；登记的消费若被删除，陈旧条目同样判红——放行与守卫是同一条判据的两个方向。
- **风险与边界**：`src/host/**` 从"零消费"变成"登记消费"，其信任建立在"登记处被认真评审"上；登记处目前不由人审批流程守着，只有对账判据。若日后 host 侧消费膨胀，应收紧到按端点白名单逐条登记（本票的 `READONLY_BRIDGE_ENDPOINTS` 已是该形态的最小样本）。
