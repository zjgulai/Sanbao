# ADR-0217 · 附件上传链：候选即封存版本、流式过宿主 uploadStream、回执摘要核验、receipt 同会话

- 状态：accepted（2026-10-02）
- 日期：2026-10-02
- 决策者：agent（取证并实施；桥的形状与失败语义是取舍）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-02-attachment-upload-chain.md)
- 相关：[ADR-0205](ADR-0205.md)（基座声明取证）、[ADR-0212](ADR-0212.md)（会话通道）、[ADR-0213](ADR-0213.md)（停止/待继续——本票暂停期附件发送整体拒绝）

## 背景

工单 014（FW-010/011，US-071~076/083）要求：选择文件只产生候选；确认后经 main **流式**上传取得 receipt；
上传回执区分传输中/内容完整性核验/附件关联生效；部分失败**续传同一封存版本**；附件随消息发送并在历史
内回看；机器路径不进跨端数据；重开不重跑上传。核验项：receipt 的"同一会话"绑定与事项隔离。

基座声明取证（逐字）：`@deepseek-ai/dsh-client-file-upload` 的 `fileUploads.uploadStream({sessionId,
data: AsyncIterable<Uint8Array>, signal?, name?})`（"Persist raw chunks … without aggregating the
upload"）；`@deepseek-ai/dsh-attachment` 的 `FileAttachmentRef{attachmentId=sha256(存储字节), name
(sanitized leaf), bytes}`（"never a filesystem path or bearer URL"）；`@deepseek-ai/dsh-api-session-
controller` 的 `PromptContentPart` file 分支只带 `receiptId`（"the opaque receipt returned by a
preceding uploadFile call on the same Session"），`resolvePromptFileReceipts` 在同会话 Agent 作用域用
`fileUploads.resolve(agent, receiptId)` 解析，取不到即抛 `session/attachment-invalid`（reason
`FILE_NOT_STAGED`）。`stagedFiles` 是宿主进程内 WeakMap：receipt 是**运行内**凭据，不跨重启。

## 决策

1. **D1 候选＝封存版本（US-071/072）**：`pick` 只产生候选——main 对所选文件做一次有界封存
   （sha256＋字节数，64 MiB 上限），对话框取消是事实；非普通文件/超限/不可读各自成拒绝码。
   投影只带 `name/bytes/stage`：**机器路径不进任何跨端数据**（候选与记录都是）。
2. **D2 上传过桥到宿主自己的 `uploadStream`（US-072/073）**：桥新增四个 write 端点
   `attachment/upload-begin|chunk|commit|abort`；宿主侧注册表按序收 **128 KiB 有界分块**、终块校验
   声明长度（一致才放行）、失败/取消唤醒消费者；`commit` **先于**后续分块发出，让 store 边到边拉——
   队列不聚合整文件。主侧 commit 单列 120s 时限（其余桥调用仍 10s，ADR-0205 的时限不动）。
3. **D3 内容核验＝回执摘要对封存摘要（US-073/074）**：回执 `file.attachmentId`（存储字节的内容地址）
   与本地封存 sha256 逐位一致才算 `stored`；不一致＝`source-changed`——"源内容在选取与上传间变化，
   需重新选择"，且同一 item 的再次上传被拒（不把旧封存套到新内容上）。**部分失败重试同一封存版本**：
   重读的字节必须仍是封存摘要（测试断言两次尝试字节逐位相同），"不重新生成内容"是结构事实。
4. **D4 receipt 的同一会话绑定（US-083 核验结论）**：receipt 由基座在**会话/Agent 作用域**内解析，
   跨会话即 `session/attachment-invalid`（本桥映射 `bridge-attachment-invalid`）。上传前与 send/resume
   走**同一条显式建会话路径**（`sessionChannel.ensureSession`）；桥端拒绝未知 upload id、乱序/越界/
   非规范 base64 分块；`session/prompt` 的 receipts 列表空/非串/超 16 一律不转发。本地记录只活本次运行，
   持久记录是**会话日志本身**——重开沿历史回看（US-076），不重跑上传、不重发。
5. **D5 随消息发送与历史回看（US-075/076）**：发送时该事项 `stored` 附件随下一条消息带上 receipts
   （text 可为空——基座要求"非空白文本或附件"至少其一）；仅受理回执把记录标 `sent`。**暂停期带附件
   发送整体拒绝**（`session-paused-attachments`）：receipt 只活本次运行，待继续记录跨运行——拆半承诺
   是不诚实的配对。历史折叠**只补带附件的 `user/message` 行**（005 的 echo 模型不动），按 rpcId 去重。
6. **D6 呈现纪律**：传输中/内容核验通过/已随消息发送各自成句；上传成功**不写**"已读取/已使用/已解析"；
   不做独立事项附件列表面板、不做跨消息复用（工单 §7 明确不做）。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 走基座 HTTP 上传路由 `/api/session/uploadFileBinary` | 否决：`routeRequest` 明确拒绝 `/api*` 面，且 renderer 无本机文件读取权——上传只能由 main 经桥服务做。 |
| `commit` 放在全部 chunk 之后 | 否决：宿主需整文件入队再消费，违背 uploadStream"不聚合"的注解；改为 commit 先行、边到边拉。 |
| 单次桥调用携带 base64 全量文件 | 否决：消息与内存都被整文件撑大；有界分块是 US-072 点名要求。 |
| 上传前把文件复制成本地快照 | 否决：D-093 受控快照机制后置（US-082），本票用"封存摘要＋回执摘要核验"达成同版本语义，不引入复制。 |
| 暂停时把附件挂进待继续记录 | 否决：receipt 运行内有效、待继续跨运行——拆半承诺。 |

## 后果

- 三条验收各有机器断言：回执不冒充"已读取"（词表扫描）、部分失败同版本重试（字节逐位）＋源变必重选、
  机器路径零出现（投影与桥载荷双向断言）。
- 桥面 17→21 端点；`sage-service-consumption.json` 登记 `fileUploads`；宿主 lib 清单加
  `host/attachment-uploads.js`（materialize 不漏文件）。
- 顺手删除 `bridge-endpoints.ts` 流式分支里两段不可达的重复块（此前编辑碰撞残留）。
- 已知未闭：真机 E2E 未跑（不启 Host）；图片专用通道（inline base64 + imageLimits 准入）不在本票，
  文件一律走 upload 链；缓传（回到断点续传字节位）按"同一封存版本重传"读，基座无分块断点协议。
