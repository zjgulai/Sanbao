# ADR-0201 · 建项是托管侧动作：独立分支、不写本地、没有托管方就报未就绪

- 状态：accepted（2026-10-02）
- 日期：2026-10-02
- 决策者：用户（lute：全量授权接线 UI/UX 与后端，写侧按主链推进）+ agent（取证与实施）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-02-create-matter-custody-branch.md)
- 相关：仓外设计集的 ADR-0005（所有正式事项统一托管；路径 `Sage-ui-wiring-design/docs/adr/0005-all-formal-matters-hosted.md`，不在本仓）、[ADR-0200](ADR-0200.md)（步骤 3 接执行侧存储）、[ADR-0174](ADR-0174.md)、[ADR-0190](ADR-0190.md)

## 背景

写侧主链的第一颗示踪弹要从"建项"开始，而现有 10 步管线**前提就有事项**：第 3 步按 `matterId/revisionId` 严格重放当前事项，第 4–8 步围绕"当前修订"判目标/兼容/注册/预检。建项时事项还不存在，这条链一步都走不通——它要么被第 3 步的 `not-found` 判成 `policy-denied`（把"还没有这条事项"说成"你没有权限"，是假话），要么被误当成"往本地执行库写一条"。

仓外设计稿把边界写死了（ADR-0005）：**所有正式事项统一由托管服务保存与裁决**；"服务端不可用时不得在本机偷偷创建一条同身份的正式事项再事后合并"。也就是说本地那条执行侧事件库（ADR-0200 接的）**不是**建项的落点。

## 决策

1. **D1 建项走独立分支，不走 3–10**：`runCommand` 在第 2 步（身份/策略）之后判定 `actionType === 'create-matter'`，走创建分支；第 3–10 步对它一概不适用，也就不会被误用。
2. **D2 托管方缺席＝可重试的"未就绪"**：创建端口 `createMatter` 缺席（或缺席式拒绝）时返回 `persistence-unavailable@create`（`retryable: true`）。渲染面据此归入 `not-ready`，只给缺项说明、**不给重试**（沿用 001 的三态纪律）。
3. **D3 不写本地、也不读本地**：创建分支不触碰执行侧事件库——既不 append（禁止本机私自铸号），也不 rehydrate（避免"读过一次就当作存在"）。有断言同时钉住两点：`strictRehydrate` 未被调用、本地库目录未被创建。
4. **D4 登记动作＝让请求能到达托管方**：`ACTION_AUTHORITY_TABLE` 增 `create-matter`（`operation: create-matter`、`actionScope: matter.create`、`effectClass: external-write`、`requiresDecision: false`）。登记的作用是让第 2 步组装出可评估的请求（否则 `invalid` → `invalid-request`，永远走不到托管方），**不是**授予任何执行权：真正放行仍要组织策略里有对应 grant。
5. **D5 成功路径以回执为准**：托管方端口返回 `{receiptRef}` 时，管线按既有形状返回 `CommandAccepted`；没有回执就没有"已建项"。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 把建项塞进第 3 步（用 draft id 当 matterId 去 rehydrate） | 否决：会把"事项不存在"说成"无权限"，且把草案与正式事项混成一个对象（002 明确要求两者是不同的后端对象）。 |
| 本机先在执行库里建一条，等托管服务可用再合并 | 否决：正是 ADR-0005 明文禁止的做法（双主与事后合并风险）。 |
| 不登记、让它继续以 `invalid-request` 结束 | 否决：那是"本票还没做"的码，用户看到的是"动作类型未登记授权范围"，与真实原因（托管方未接）不符。 |
| 现在就造一个本地托管实现 | 否决：托管是服务端职责，本机实现等于把 ADR-0005 反过来做。 |

## 后果

- 建项请求第一次有**真实**的终态语义：要么托管方回执（`CommandAccepted`），要么"托管方还没接"的可重试未就绪；不再伪装成权限失败，也不再有可能被误接成本地写。
- 写侧注册表从 1 条变 2 条；后续动作（enter-evidence/approve/…）按同一纪律逐条登记，每条都必须先说清它在哪一步落、由谁落。
- 已知未闭：托管方端口在 production 仍缺席（服务端尚未存在），所以本票的验收是"以正确的码、在正确的阶段、用正确的方式失败"；真正建项要等托管服务与该端口的真实实现。
