# ADR-0328 · failed-retry 再授权：选择时 ensure 为失败修订再落工作修订

- 状态：accepted（2026-10-12）
- 日期：2026-10-12
- 决策者：用户（授权修复实测问题）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-12-failed-retry-rearm.md)
- 相关：[ADR-0291](ADR-0291.md)（选择时 ensure）、[ADR-0296](ADR-0296.md)（回合收口）、[ADR-0327](ADR-0327.md)（v9 实测发现）

## 背景

v9 生产实测：回合失败（`MISSING_CREDENTIAL`）→ 事项落 `failed-retry`。域内核规定 attempt 只能从 `evidence/clarification` 起步（`business-matter.ts`），出口有二：`reconfirmRevision`（同修订再确认）与 `enterEvidence`（新修订）。实测发现：

- `reconfirmRevision` 在**全产品零调用**（main/route/UI 全缺）；
- 选择时 ensure 的 `decideRunRevision` 见「当前修订已声明 session.prompt」即 `not-needed` → 不落新修订 → **失败事项永久不可再发**（`persist` 步 `session-prepare-declined`→ 实际为域拒 `An attempt may start only from evidence or clarification`）。

## 决策

1. **D1 再授权走选择时 ensure**：`decideRunRevision` 在投影 `stage === 'failed-retry'` 时跳过「策略已声明即 not-needed」短路，返回 `needed`——选择时（用户显式选择/输入为见证）经既有五步面**落新工作修订**（`enterEvidence`；域允许从 failed-retry 进入），事项回 `evidence` 可再发。
2. **D2 文案诚实**：再授权写入的 `changeReason = '失败修订后的再次确认：用户显式选择/输入即见证。'`（由写入端重投影 stage 决定），不冒充「首个工作修订」。
3. **D3 零新面**：不新增路由/UI/门禁分母；复用既有「选择事项」与发送前 ensure 路径。`reconfirmRevision`（同修订出口）保持未接线，作为富交互（卡面「重新确认」）的将来票登记。
4. **D4 验证**：spec 覆盖（新用例：seed → ensure 落首修订 → start+fail attempt → 断言 failed-retry → 二次 ensure 落新修订 + 再确认文案 + 策略在位）；域约束（事件时间单调）由 spec 时间序列满足。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 接线 `reconfirmRevision`（同修订再确认 + 新路由 + 新 op + UI） | 本轮不做：面大（路由/族/门禁/UI 全套）；ensure 再授权已达到可用出口。 |
| 失败后自动落新修订 | 否决：再授权必须带用户见证；自动重试语义危险。 |
| 放宽域 stage 守卫 | 否决：域不变量是证据链的一部分。 |

## 后果

- 失败事项经「重新选择事项」（或直接再发）自动再授权新工作修订；不再死锁。
- 发送链在 failed-retry 后的首次再发多写一条 `revision-entered`（可审计）。
- spec 增量 1；门禁分母不变。
