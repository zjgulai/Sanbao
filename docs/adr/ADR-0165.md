# ADR-0165 · Compatibility Authority：revision-bound target、可信 runtime inventory 与 immutable matrix

- 状态：accepted（2026-09-28）
- 日期：2026-09-28
- 决策者：用户（lute）
- 决策记录：[Note](../notes/proposed/architecture/2026-09-28-compatibility-authority.md)
- 相关：ADR-0159（Sage 自有产品与能力运行时边界）、ADR-0161（BusinessMatter 权威事件存储）、ADR-0162（外部能力装配；本 ADR 部分修订其 D2）、ADR-0163（Identity / Policy Resolver）、ADR-0164（真实身份与 Authority 数据治理）
- 后继细化：[ADR-0166](ADR-0166.md) 细化 D2～D5、D10 的 full evidence / stable semantic matching 合同；本文 D1～D10 原文保留，状态不变

## 背景

`BusinessMatter` 已要求每次 attempt 保存 Provider、Model、Agent、Preset、Capability 的 `identity + version + digest` 和 `matrixId + outcome + reason`，但当前领域 API 只能校验结构、非空、去重和 `equivalent` 枚举；它不能证明这些值来自谁。Host `ready`、Cordis service presence、profile receipt、Loader 条目、MCP 工具名、进程存在和 package version 也只覆盖局部观测，不能共同证明当前 runtime 与某个 revision 的语义等价。

真实 OIDC 与组织授权接线仍在等待部署输入。Sage 需要让新 UI、Compatibility kernel 和插件 inventory 工作继续并行，同时保证任何 fixture、Host 自报或插件自报都不能提前获得真实业务执行权。

## 决策

1. **四个责任分离。** `CompatibilityTargetProvider` 由 Sage product/security governance 拥有；`RuntimeInventoryProvider` 由 Electron main 拥有；`CompatibilityMatrixProvider` 由 `Sage Compatibility Authority` 拥有；`CompatibilityResolver` 是只消费前三者已验证输出的纯、确定性、无 I/O kernel。Application Service 只按固定顺序编排，不拥有或改写 authority 内容。
2. **Target 绑定 revision。** target 至少绑定 `matterId`、`revisionId`、canonical revision digest、精确 action scopes / policies、permission / data-boundary 摘要、Provider / Model / Agent / Preset / Capability requirements、schema version 与 canonical target digest。renderer、插件、Host、模型和 action body 都不能提交 target。本批不修改 v1 event schema。
3. **Inventory 采用复合证据。** main-owned provider 将 active generation / receipt、安装后 artifact attestation、影响行为的配置摘要、Host/Harness identity、Provider / Model / Agent / Preset / Capability identity、外部 MCP contract、boot/runtime generation 与新鲜 observation 组合成 canonical inventory。artifact attestation 与 boot-scoped live observation 缺一不可；自报 version、进程存在、工具数量、service ready 或单次 probe 都不是完整 authority。
4. **Matrix 不可变且内容寻址。** 首版使用 app-bundled immutable provider。matrix canonical bytes 产生 `urn:sage:compatibility-matrix:sha256:<64-hex>` 形式的 `matrixId`；发布后不可原地修改，修正生成新 ID。撤销使用独立、可追溯记录；被撤销 matrix 不授权新动作，但历史 matrix bytes 必须保留到相关审计 retention 到期。
5. **Outcome 唯一命中、默认拒绝。** 只有 target、inventory、matrix 的 shape 与 provenance 全部可信，matrix 未过期或撤销，且恰好命中一条覆盖全部 identity、version、digest、contract、scope、effect、permission 和 data-boundary 的规则，才返回 `equivalent`。已知语义变化返回 `requires-new-revision`；缺失、未知、未登记、未验证、重复、冲突、歧义、多个规则命中、provider 不可用、过期或撤销均返回 `unknown`。后二者都阻断。
6. **Compatibility 与 availability 分层。** compatibility 回答已验证 artifact / contract 是否满足 revision-bound target；availability 回答服务此刻是否在线、健康且可执行。历史 `equivalent` 不是当前健康或当前权限，每个真实外部副作用、持久写入和 privileged 边界前仍须重新取得新鲜 identity / policy、inventory、matrix 状态和 capability preflight。
7. **UI、插件、Host 与模型没有裁决权。** 它们只能提交 intent、selection preference、候选 metadata、liveness 或受控结果；不得提交 `outcome`、`matrixId`、`reason`、`executionSnapshot`、`targetDigest`、`inventoryDigest` 或“兼容”布尔值。只有进入 Sage-owned Capability Registry allowlist 且具有明确 Adapter mapping 的能力，才可能成为产品 capability；继承的 DSH entry 默认只是 runtime implementation。
8. **产品只有一个编排入口。** WT-02D Application Service 固定执行 `ActionIntent → identity / policy → strict rehydrate/current revision → target → fresh identity/policy evaluation → runtime inventory → matrix/resolver → BusinessMatter → event store → Capability Adapter → artifact/failure/receipt`。当前 v1 strict replay 只重放持久化的 `ExecutionSnapshot` / `CompatibilityDecision` DTO，不查询 matrix，也不证明 target / inventory / matched rule 的 provenance；未来审计可以按 `matrixId` 取回历史 immutable matrix，但必须另以 `CompatibilityEvaluationEvidence` 绑定当时 target、inventory、matched rule 与 outcome，且不得拿当前 matrix 改写历史。`reconfirmRevision()` 也不是后续 attempt 的 standing compatibility。
9. **真实登录等待期间只开放无副作用并行面。** WT-02C.1 的纯 kernel、UI fixture / blocked projection 和插件 inventory / descriptor 开发可以并行；真实业务 mutation、真实敏感数据、外部副作用与产品动作仍等待 WT-02B、WT-02C 和 WT-02D 各自门关闭。
10. **校准 ADR-0162 D2。** 每一侧出现的 `@deepseek-ai/*` 都必须精确 pin；两侧同名重叠包必须同版。只有同时被 shell 编译期和 runtime seed 消费的包才要求双侧登记；runtime-only 包可以 seed-only，但必须进入 lock 与未来可信 runtime inventory 证据。该校准部分修订 ADR-0162 原 D2 的“任何新依赖均双侧登记”表述。

## 备选方案

| 方案 | 为什么未采用 |
| --- | --- |
| 继续由调用方提交 `equivalent + matrixId` | 对纯领域 fixture 尚可，但生产调用方可以构造同形对象，无法证明来源与 revision 绑定。 |
| 由 Host、插件或 MCP server 自报版本和工具列表后放行 | 只能形成 observation；不能证明 artifact、配置、contract、权限与数据边界。 |
| package pin 或 SemVer 相同即视为兼容 | 版本只描述发布身份或声明的 API 变化，不能覆盖远端模型、配置、local patch、工具合同与业务语义。 |
| live probe 成功即视为兼容 | probe 证明一条路径在某一时刻可用，不能证明全部 action policy、permission / data boundary 或未探测差异。 |
| 把 resolver 放入 `BusinessMatter` | 会让纯领域重放依赖运行时、插件目录和 Host 状态，破坏确定性和历史重放。 |
| 首版使用远端 matrix service | 提前引入网络、签名、bootstrap 与运营依赖；app-bundled immutable provider 足以先建立正确边界。 |
| `unknown` 时允许“只读插件”运行 | `external-read` 仍可能造成数据出境；只有另行批准的 public / local-only projection 才能离线只读。 |

## 后果

- 正面：新 UI 可以安全展示兼容状态、缺失证据和拒绝原因，但不能把按钮、fixture 或插件声明变成 authority。
- 正面：真实登录线路不阻塞纯 kernel、UI fixture 和 capability inventory 开发，同时真实副作用保持 fail-closed。
- 正面：revision、runtime identity、matrix、attempt 与历史 replay 获得可审计的职责链。
- 代价：Provider、Model、Agent、Preset、Capability、配置或 contract 变化都可能使旧 evaluation 失效。
- 代价：插件“能够启动”到“可以用于某个 revision”之间增加显式登记、证明和裁决门。
- 风险：当前 profile receipt、Host ready 和 Jev 装配都不足以生成可信 inventory；在 WT-02C.2A～2C 完成前必须保持 `mounted / runtime-observed / compatibility-unproven`。
- 风险：当前 v1 event 只保存 `matrixId + outcome + reason`；`matrixId` 只标识 matrix bytes，不标识某次 evaluation。完整历史 provenance、retention 与 schema 仍需 WT-02C.3 / WT-02D 单独确认。
- 边界：本 ADR 只完成治理决策，不实现 Registry、resolver、可信 inventory、Application Service、插件授权、真实登录或产品调用链。
