# ADR-0164 · 真实身份与 Authority 数据治理：OIDC、最小证据与删除传播

- 状态：accepted（2026-09-28）
- 日期：2026-09-28
- 决策者：用户（lute）
- 决策记录：[Note](../notes/proposed/architecture/2026-09-28-real-identity-and-authority-data-governance.md)
- 相关：ADR-0160（活动仓与历史能力隔离）、ADR-0161（BusinessMatter 权威事件存储）、ADR-0163（Identity / Policy Resolver）
- 修订关系：本 ADR 细化并部分修订 ADR-0163 的 D1、D3、D5；Identity Provider 不再证明 organization，WT-02B.1 现有 assertion organization 只视为过渡接口；内存 `AuthoritySnapshot` 不再被直接视为可持久化事实，长期事实改为最小 `AuthorityEvidence`

## 背景

WT-02B.1 已建立 provider-neutral、fail-closed 的 Identity / Policy Resolver，但仓库仍没有真实 Identity Provider、OIDC callback、token vault、session broker、组织目录或 Policy Provider。当前 resolver 输出的内存 `AuthoritySnapshot` 含原始 provider subject 与 `sessionId`；如果把它原样写入追加式事件，会把可关联身份与会话信息锁进长期事实链。

现有 v1 事件没有专门的真实身份字段，却允许 `goal`、`reason`、`source`、`locator`、`roleRef` 等自由文本，因此仍可能承载 PII 或敏感经营数据。当前 event store 也没有 retention、purge、export、backup、删除传播或恢复后防数据复活的合同。真实登录方向、运行时凭证、长期审计证据和删除生命周期必须先分层，不能用「已经有 kernel」替代生产数据治理。

## 决策

1. **真实登录采用标准 native OIDC。** Sage 第一阶段采用系统浏览器中的 OpenID Connect Authorization Code + PKCE，桌面端作为 public client；不使用嵌入式 WebView 登录，不在客户端内置 secret，也不在当前阶段自建 Sage Identity Broker。真实 adapter 必须验证精确 issuer、audience、redirect、state、nonce、PKCE、签名和有效期，并支持 refresh rotation、撤销与失败即拒绝。
2. **认证、主体映射与组织授权继续分权。** Identity Provider 只证明 `(issuer, subject)` 与认证状态；Sage-owned identity mapping 只提供内部 identity handle、候选 organization ref 与后续可持久化的 scoped `subjectRef`，候选关系本身不是成员资格证明；Organization Policy Provider 是 active organization membership、role 与 grant 的唯一 authority。email、display name、tenant domain、group claim、UI、Host、Harness 或插件均不得直接授予组织、岗位或操作权限。WT-02B.1 现有 assertion organization 仅是测试 kernel 的过渡接口；WT-02B.2B 在接真实 provider 前必须迁移该接口，产品调用链不得把 IdP organization claim 当作 authority。
3. **凭证只属于 Electron main 的短生命周期运行面。** access token 与 ID token 仅驻留 main process 内存；refresh token 仅进入 main-owned、OS-backed encrypted vault。token、cookie、refresh token、raw provider subject 和 bearer session secret 不得进入 renderer、Chromium `sessionData`、profile、Host、Harness、插件、BusinessMatter event、SQLite、日志、artifact、导出或备份。Sage session reference 必须非 bearer、非秘密，仅凭引用不能登录或访问远端资源。
4. **首版 offline 是只读上限，authority-scoped 数据默认拒绝。** 任何领域 mutation、decision、attempt、receipt、`local-write`、`external-read`、`external-write` 或 `privileged` 意图都必须在线取得新鲜 identity 与 policy；provider / policy 不可达、过期、撤销或无效时 fail closed。authority-scoped projection 在 offline、logout、账户禁用、organization / role 撤销或 policy 失效时一律拒绝读取；只有后续独立决策登记为 public / local-only 的 projection 才能离线只读，并必须固定数据分类、organization scope、最大陈旧时间、logout / revoke 清理、UI 提示与 owner。本批不开启任何例外，因此当前有效规则是默认拒绝。长任务在每个持久写入、外部副作用与 privileged 边界前重新求值；历史证据不得重放为当前权限。
5. **运行时快照与持久审计是两个合同。** `Runtime AuthoritySnapshot` 只在一次 main-process 授权调用链内存在，可以含本次求值必需的 provider subject 与 session reference，但不得持久化。未来 `Persistable AuthorityEvidence` 只允许保存 `authorityEvaluationId`、opaque `subjectRef`、issuer / audience / organization / role、operation / action policy、policy identity / version / digest、有效期边界、`evaluatedAt`、非秘密 `authenticationEventRef` 与最小 policy evaluation evidence；它不能用于重新授权。`sessionId`、token、raw provider subject、姓名、邮箱、完整 claims、完整组织目录、可重放 assertion / policy cache 和原始 provider error 永不进入长期事实。
6. **pseudonym 仍按个人数据治理且必须可真正去关联。** scoped `subjectRef` 必须由 identity vault 在 Policy Provider 已证明的 organization / audience scope 内产生高熵随机 surrogate，并做 scope 内唯一性检查；禁止从 raw subject 做无密钥、可重算的 deterministic hash。rotation / migration 必须原子迁移引用或保留具名映射版本，旧 ref 与映射在迁移完成前继续受同一 retention / deletion 约束。`(issuer, subject) → subjectRef` 映射只存在于可删除的 identity vault。`subjectRef` 不是匿名化；只要可借映射或外部数据关联个人，就继续受最小化、访问、retention、legal hold、export 与删除规则约束。policy evidence 与对应 authority evidence 采用相同 retention、legal-hold 与 purge 边界，不能只保留不可解释的 `allowed` 或 digest。
7. **没有 retention matrix 就不写真实数据；legal hold 只暂停允许暂停的数据。** 产品 / 合规 owner 必须按数据类别批准处理目的、owner、起算点、期限、legal hold、purge、export、backup 期限和删除目标；在此之前，不得把真实身份或敏感经营数据写入当前事件流。账户删除始终立即撤销并清除 token、runtime session 与授权缓存，它们不受 legal hold 保留。identity mapping、evidence 或 artifact 没有有效 hold 时按批准合同删除；存在具名、合法、限定范围且未到期的 hold 时，必须从产品访问面隔离、禁止用于认证 / 授权、记录 pending deletion，hold 解除或到期后立即进入幂等 purge。删除传播必须覆盖 projection、索引、cache、artifact、export、vault 与 backup catalog，restore 在开放数据前先应用 deletion ledger / tombstone。自由文本或 locator 已含 PII 时，只能经另行授权的幂等 whole-stream purge / crypto-shredding 处置，不得静默改写 hash chain。
8. **WT-02B.2A 只落治理文档。** 本批不修改 v1 event schema、domain、codec、store、security source、main、product、Host、profile、package、lockfile、UI、插件或真实数据。真实 OIDC adapter 与 vault 属于 WT-02B.2B；`Runtime AuthoritySnapshot → Persistable AuthorityEvidence`、schema 与 maintenance lifecycle 属于 WT-02B.3；compatibility registry 与 Application Service 分别留给 WT-02C、WT-02D。

## 备选方案

| 方案 | 为什么未采用 |
| --- | --- |
| 自建 Sage 账号密码或 Identity Broker | 长期可统一多 IdP 和账户生命周期，但当前会立刻引入后端、凭证处理、运维与安全责任，不适合裸底座首批。 |
| 以 macOS uid、Keychain 随机 secret 或本地 profile 作为真实人类身份 | 只能证明设备或本机数据存在，不能证明企业主体、组织成员资格或岗位授权；不得在 OIDC 不可用时静默降级。 |
| 直接持久化 provider `(issuer, subject)` | 实现较短，但加强 provider 锁定与跨事项关联；可删除的 Sage-owned `subjectRef` 映射更符合最小化与迁移边界。 |
| 原样持久化 `AuthoritySnapshot` | 会把 raw subject、`sessionId` 和运行时字段带入追加式事实；运行时与审计生命周期不相同。 |
| offline 继续使用缓存 assertion / policy 执行写入 | 撤销、账号禁用或岗位移除后仍可能产生副作用；首版风险不可接受。 |
| 给所有数据先定统一 90 天期限 | 缺少处理目的、法定义务、legal hold、backup 与业务 owner 证据；一个数字无法覆盖不同数据类别。 |
| 删除时逐行改写追加事件 | 会破坏事件 hash chain 与可解释性；含 PII 的流必须走显式 whole-stream purge 或 crypto-shredding。 |

## 后果

- 正面：真实登录、组织授权、业务审批、运行时凭证与长期审计各有唯一 owner；新 UI 和插件不能获得 token 或自授岗位。
- 正面：真实 IdP 可以后置选择，`BusinessMatter` 和 resolver kernel 保持 provider-neutral；未来换 provider 时由可删除 mapping 承担迁移。
- 正面：长期审计能解释当时的授权依据，同时避免把 session secret、原始 claims 或组织目录复制进事件链。
- 代价：在 issuer/client registration、Policy Provider、vault capability 和 retention matrix 未齐备前，Sage 只能保持无真实登录、无真实敏感数据的开发模式。
- 代价：删除传播、backup restore、whole-stream purge、policy evidence archive 与 legal hold 都需要后续独立 maintenance port 和演练。
- 代价：WT-02B.1 当前 assertion organization 接口不能进入真实产品；WT-02B.2B 必须先迁移到 Policy Provider 独占 organization membership 的目标模型，并补齐 offline projection registry 的产品 enforcement。
- 边界：accepted 只表示上述架构与治理选择生效，不证明真实 provider、token vault、`AuthorityEvidence` schema / persistence、compatibility registry、Application Service、UI 或 P0-5 产品闭环已经完成。
