# ADR-0078 · 运行中的字节不是磁盘上的字节：客户端 bundle 只有「重启」一条生效路径，且空射程的仪器必须自己报出来

- 日期：2026-09-13
- 决策者：用户（lute）+ agent
- 决策记录：[Note](../notes/implemented/contract/2026-09-13-running-bytes-are-not-disk-bytes.md)
- 相关：ADR-0009（一份事实一个家——仓库路径的来源只能是包清单）、ADR-0014（门禁硬门槛）、
  ADR-0061（本机装配走 profile 本地装配）、ADR-0063/0069（TCC 判据）、

## 背景

2026-09-13 修侧边栏两处缺陷（技能中心文字居中、岗位矩阵被排到技能中心下方）。
源码改完、构建产物核对过、装载点按 tmp+mv 推送过、两份副本逐字节一致——
**刷新页面后屏幕毫无变化**，AX 几何读数与刷新前逐位相同。

追下去发现三个各自独立的问题。

### 一、打包应用里，客户端 bundle 的磁盘变更被**主动丢弃**

`@deepseek-ai/dsh-client-modules` 在激活时把每个包的 `client.js` 读成**不可变字节**
（`initialBundleSnapshot` → `record.bundle`），`compose()` 预先算好 `URL → body` 的 Map，
HTTP 直接吐这份内存副本。改写内存的唯一入口是 `rebuilt(id)`，其注释自称是
「bundle 内容变更进入 graph 的**唯一**入口」。

`@deepseek-ai/dsh-client-hmr` 里有一道 production guard：
`process.defaultApp !== true && process.env.DSH_DEV !== "1"` 时，watcher 只推进 mtime/size 基线
并 `return`，**不调用** `rebuilt(id)`。源码注释：「下一次完整重启才会从新字节重新组合」。

本机实测：`DSH_DEV` 未设置、主进程非 `defaultApp` → 守卫生效。
所以**刷新页面在原理上就不可能是生效路径**；而且基线被推进意味着这个变更不会再被注意到。

### 二、两处「拦住它」的仪器**空射程**，恒绿

`scripts/sync-profile.mjs` 的 `loadPointPairs()` 与 `scripts/gate.mjs` 的
`gate:profile-bundle-sync` 有同一个 bug：

```js
const sourceDir = spec.slice('file:'.length)                 // './vendor/packages/surfaces/…'
if (!existsSync(join(sourceDir, 'package.json'))) continue   // ← 基准是 cwd，不是 profile
```

`file:` 的基准是**声明它的 package.json 所在目录**（profile），而被当成了 cwd：

| 运行位置 | 实际比的是什么 | 读数 |
| --- | --- | --- |
| 仓库根（门禁与常用情形） | **什么都没比**（23 个依赖全部 `existsSync` 失败被跳过） | `ok` |
| profile 目录 | profile 自己的 **vendor 副本 ↔ node_modules** | `ok` |

实测：profile 声明 23 个 `file:` 依赖，门禁实际对比 **0** 个。
而**这条门禁的 remediation 原文就是「否则应用重启后仍跑旧字节」**——
它存在的唯一理由正是拦住此刻发生的这件事。

## 决策

**1. 「运行中的字节」与「磁盘上的字节」是两个事实，不得混用。**
客户端 bundle 的生效路径只有一条：**改 → 构建 → tmp+mv 推到装载点 → 重启应用**。
刷新页面不是生效路径，不要再把「刷新试试」当作验收动作。

**2. 仓库源的路径只能由包清单给出。** `file:` spec 的路径基准是它所在的
package.json，与 cwd 无关，因此**不得**用它推导仓库源目录；两处都改为按包名反查
仓库受管包目录（`entry.dir` / `managedPackages().relPath`）。

**3. 空射程必须自己报出来，且与「全一致」在读数上不同形**（沿用 ADR-0075）：
- 门禁：`fileDeps > 0 && pairs.length === 0` 判红；`note` 常显 `对比 N/M 个 file: 依赖`。
- CLI：同样判红；`ok` 行常显 `（对比 N 个包）`。

**4. 修正射程后量出的真实漂移立即处理**：`dsh-overseas-skills` 的
`lib/client.js` / `lib/org-tree.js` / `lib/preset-roles.js` 装载点比仓库旧，已按 tmp+mv 同步。

## 备选方案

- **用 `DSH_DEV=1` 启动以走 HMR**：仍是重启，且会把 rebuilt 帧推给 renderer——
  而 production guard 的注释明确说那会让页面白屏。收益为零、风险为正。
- **找一条「强制重新组合」的 HTTP 路由**：`dsh-client-hmr` 只注册 `/plugins/events`
  SSE（**只读**），没有任何触发重建的路由；`rebuilt` 只能被 host 内部调用。
  「不重启而让新字节生效」在本版**不存在**。
- **只修 CLI 不修门禁**：门禁才是「拦住」的那个人。只修 CLI 是把「知道」写进文档、
  把「拦住」留空（P-03）。
- **空射程只打警告不判红**：警告会被忽略，而「一个包都没比」与「全都一致」必须
  不可能同形——那正是 P-02 的成因。

## 后果

**正面**

- 生效路径写清楚了，少掉一整类「我改了、刷新了、怎么没变」的时间黑洞。
- `gate:profile-bundle-sync` 射程 **0/23 → 23/23**，读数常显分母；将来若再退化，
  读数上不再与全绿同形。
- 修正射程当场量出一条此前不可见的真实漂移（`dsh-overseas-skills` 三个文件）并已修复——
  它本来会在下一次重启后表现为「改过的胶囊又回来了」。

**负面**

- 客户端 bundle 生效仍需**人工重启**，无自动化路径。
- 门禁变红是正确行为：任何「改了仓库忘了推装载点」都会当场红。

**诚实划界（判不出的部分）**

- **「运行中的字节」无法从磁盘判定。** 本次能确认是因为改的是可见几何（AX 读数）；
  若改的是不可见行为，磁盘侧全绿、应用侧仍旧，**没有任何静态判据会发现**。
  这一条在总账 P-15 里明写为「判不出」，不假装被拦住了（P-03）。
- 两处判据只覆盖**磁盘 ↔ 磁盘**（仓库源 ↔ 装载点），能回答「装载点是不是最新」，
  **不能**回答「跑着的那个进程读的是不是装载点」。
