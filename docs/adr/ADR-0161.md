# ADR-0161 · BusinessMatter 权威事件存储：Sage 主进程、node:sqlite 与严格重放

- 状态：accepted（2026-09-27）
- 日期：2026-09-27
- 决策者：用户（lute）
- 决策记录：[Note](../notes/proposed/architecture/2026-09-27-business-matter-event-store.md)
- 相关：ADR-0008（基座只 pin 不改）、ADR-0015（ADR / Note 双向留痕）、ADR-0159（Sage 自有产品与数据边界）、ADR-0160（本机活动仓基线）

## 背景

WT-01 已建立纯内存 `BusinessMatter` 事件链与投影，但没有持久化、并发或恢复边界。对抗探针进一步证明，当前 `projectBusinessMatter()` 只适合投影由受信命令路径产生的事件：伪造带内部 brand 的 `accepted` receipt，即使没有 artifact、责任角色错误且时间字段非法，仍可形成 `completed`；因此把磁盘 JSON 直接交给 projector 会 fail-open。

Sage 需要 app-owned 的本机权威事件存储，同时继续隔离旧 DSH session、profile generation、renderer 状态与 P0-3B 资料迁移。当前已钉住的 Electron 43.3.0 运行时提供 Node 24.18.1、SQLite 3.53.1 与可加载的 `node:sqlite`，可以在不新增 dependency 或修改 lockfile 的前提下使用数据库事务和唯一约束；代价是 `node:sqlite` API 仍需隔离在内部 adapter 后面。

## 决策

1. **Sage 拥有权威库。** `BusinessMatter` 数据库属于 Sage 独立数据根；Electron main process 是唯一正常业务写入口。renderer、Harness / DSH session persistence、active profile generation、Host 与 Capability Adapter 均不得直接拥有或修改该数据库。
2. **采用隔离的 `node:sqlite` adapter。** 首版使用随已钉住 Electron 提供的 `node:sqlite`，不新增第三方数据库 dependency。adapter 不向领域层泄露 SQLite API，并在启动时验证所需 runtime、PRAGMA 与事务能力；不满足时 fail closed，不静默降级为 JSON 整体覆盖。
3. **事件追加由数据库事务线性化。** 每次 append 必须携带 `expectedVersion`、`appendId`、稳定 request fingerprint 与有序事件批次；stream head、连续 `streamVersion`、事件行和幂等记录在同一事务中提交。创建只接受 `not-exists`，既有 stream 只接受 `exact(N)`；禁止 blind append、last-write-wins、`save`、`upsert`、`replaceEvents` 和 `forceAppend`。
4. **严格重放是持久化信任边界。** load 必须先验证 envelope、schema、连续版本、身份、唯一性、原始 payload bytes 的 digest chain，再按完整领域转换规则逐事件重放。未知 schema、缺口、乱序、引用错配、非法时间、伪造 decision / artifact / receipt 或完整性失败均返回具名阻断状态；不得跳过坏事件、截断坏尾或回退为空事项。
5. **完整性不冒充真实性。** digest chain 只用于检测损坏和提供 tamper evidence；没有独立密钥、authenticated encryption、签名或外部 anchor 时，不宣称防恶意篡改。应用级加密、Keychain、retention、purge、export、backup / 删除传播、多设备同步与 artifact blob 一致性是后续生产门；关闭前不得写入真实敏感经营数据。
6. **WT-02A 分三步实现。** WT-02A.0 只固化 ADR、合同、计划和 handoff；WT-02A.1 实现 strict codec / rehydrator；WT-02A.2 实现 SQLite event store；WT-02A.3 执行双连接并发、幂等、故障注入、kill / reopen、损坏隔离和范围回归。每一步使用独立 Birdview 文件范围与证据，不以本 ADR 的 accepted 状态冒充源码或运行验收。

首版数据库默认采用 rollback journal（`journal_mode=DELETE`）、`synchronous=EXTRA`、`BEGIN IMMEDIATE`、`foreign_keys=ON`、`trusted_schema=OFF`、defensive mode、禁用 extension loading 与有界 busy timeout。macOS 的 `fullfsync=ON` 在实现批中做能力和性能实测；若运行时不支持或代价不可接受，必须以新的证据和 ADR 更新本决策，不能静默降低 durability 语义。

## 备选方案

| 方案 | 为什么未采用 |
| --- | --- |
| 每个事项一个 JSON / JSONL 加自研 lock、journal、fsync 与 recovery | 仓库已有 atomic write 和 durable journal 范式可借鉴，但它们不提供事件流 CAS、批次幂等、唯一约束或两个独立连接的事务语义；直接复用会把脚本目录替换协议误当业务事实存储，自研则等价于重新实现数据库。 |
| 复用 DSH session persistence | 它属于 Harness session 与 seed dependency graph，不是 Sage `BusinessMatter` 的数据 owner；复用会破坏 ADR-0159 的产品 / 数据边界并绕过 P0-3B 阻断。 |
| 引入 `better-sqlite3` 或其他原生数据库模块 | API 成熟，但会新增 dependency、lockfile、Electron ABI rebuild、打包和签名风险；当前固定运行时已经提供所需 SQLite 能力。 |
| 首版使用 WAL | WAL 能提高读写并发，但当前只有一个正常写入口且没有吞吐证据；它增加 sidecar、checkpoint、备份与恢复表面积。后续只有在基准证明 rollback journal 不满足需求时再单独决策。 |
| 只依赖私有 `Symbol` brand 和 TypeScript 类型 | brand 可在运行时枚举，TypeScript 类型不验证磁盘字节；只靠二者会让不可信事件绕过命令不变量。 |

## 后果

- 正面：Sage 获得独立、可事务化、可并发判冲突且可重放的事实边界，不把 DSH、profile 或 projection 误作业务数据库。
- 正面：不新增 dependency 或 lockfile 变更；后端 API 风险被限制在单一 adapter 内。
- 正面：commit 后 ACK 丢失可通过原 `appendId` 安全确认；损坏与“不存在”不再同形。
- 代价：实现必须增加 runtime codec、完整领域 reducer、schema version、digest chain、typed load / append 结果与进程级故障测试，不能只做数据库表和 CRUD。
- 代价：`DatabaseSync` 是同步 API；事务必须短小，projection 在事务外完成。若真实读数显示阻塞主进程，再将 adapter 迁入 dedicated worker，而不是预先引入第二套存储。
- 风险：`node:sqlite` 在当前 Node 文档中仍是 Stability 1.2。通过 pin、启动 capability probe、内部 adapter、契约测试与后续升级矩阵控制；不得让其类型扩散到领域 / application API。
- 边界：本 ADR 只接受架构和实施门，不证明 WT-02A.1～02A.3 已实现，也不解除 P0-3B、真实身份、加密、删除、导出、artifact blob 或产品闭环阻断。
