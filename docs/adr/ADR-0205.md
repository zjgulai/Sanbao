# ADR-0205 · 桥的服务面取自基座自己的声明：服务名、方法形状、取消信号

- 状态：accepted（2026-10-02）
- 日期：2026-10-02
- 决策者：agent（取证并实施；缺陷由基座声明逐字对照发现，属纠正而非取舍）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-02-bridge-service-surface.md)
- 相关：[ADR-0203](ADR-0203.md)（受控方法桥）、[ADR-0204](ADR-0204.md)（流式调用）、[ADR-0198](ADR-0198.md)（host 侧消费与登记）

## 背景

工单 012 写入半边要接 `rename/delete/insertBefore`，按 ADR-0203 的做法先读基座声明再写适配。逐字对照
`@deepseek-ai/dsh-api-workspace-controller`、`@deepseek-ai/dsh-api-settings-controller` 的
`declare module '@deepseek-ai/cordis'` 与 `lib/types/*.d.ts` 时发现：桥此前消费的服务名**不存在于任何基座声明**。

| 桥写的名字 | 基座声明的真实 owner | 后果 |
| --- | --- | --- |
| `workspaceRegistry` | `workspaceController` | `@deepseek-ai/dsh-workspace` 的 `WorkspaceRegistry` 有 `create(path, title?)` `/` `list` `/` `delete` `/` `insertBefore`，但**没有** `follow`，且 `create` 是位置参数——桥的 `create({path})` 打不到它 |
| `directoryPicker` | `directoryPickerController` | `pick(signal)` 是取消参数方法，不传 signal 直接抛 |

一个"名字只是听着像"的消费点，在**单元替身里永远是绿的**（替身不看名字），在生产里**每个端点都答
`bridge-provider-unavailable`**。010/012 两票的浏览器读数用的是真实 payload，但走 fetch 桩，因此这一类
"名字对不上"在五条机器判据与 §1.6 里都不会显形。

## 决策

1. **D1 名字取自声明**：`bridge-endpoints.ts` 只消费基座各包 `declare module '@deepseek-ai/cordis'` 里写的
   owner 名——当前为 `settingsController`、`workspaceController`、`directoryPickerController`。`ctx.get` 的
   参数清单与消费登记（`sage-service-consumption.json`）同步更新，四向对账守着"写一个不存在的名字"。
2. **D2 形状按声明写**：方法签名逐字对齐 `lib/types/*.d.ts`——`create({path})` / `rename({workspaceId,title})` /
   `delete({workspaceId})` / `insertBefore({workspaceId,beforeWorkspaceId?})` / `pick(signal)` / `follow(signal)`
   / `describe()`。请求对象多一个成员即拒（`readWorkspaceRequest`），不"顺手忽略"。
3. **D3 取消参数由桥持有**：`pick` 与 `follow` 收到桥自己创建的 `AbortSignal`，并在**同一个 `finally`** 里
   `abort()`——订阅不得比它的桥调用活得更久；等待期间不取消（picker 可以阻塞在一个真人身上）。
4. **D4 拒绝码只认结构性远程错**：基座抛的 `RemoteError` 以 `isDSHRemoteError === true` 且 `code` 为串结构性识别，
   再把**已知**码翻成 Sage 自己的码（`workspace/name-conflict` → `bridge-workspace-name-conflict` 等）；
   未标记的普通 `Error` 即使带 `code` 也只得 `bridge-provider-failed`。基座的**消息文本**（含标题/路径）不过桥。
5. **D5 名字错配是回归对象**：本票新增断言——把替身挂到近名（`workspaceRegistry` / `directoryPicker`）上时
   必须答 `bridge-provider-unavailable`，把 owner 名挂对才允许通过。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 保留旧名，写一层别名适配 | 否决：别名会把"名字对不上"变成常态，每个端点两个名字、两张家谱（P-07）。 |
| 直接用 `ctx.workspaceRegistry`（域名册）并自己实现 follow/pick | 否决：等于 Sage 自建一份工作区订阅与目录选择，基座已有 owner（含去重、排序、隐档语义）。 |
| 把 signal 做成可选参数（`pick?.(signal)` 失败再退回无参） | 否决：把契约错误咽成运行时降级，缺陷会以"偶尔不可用"的形式长期存在。 |
| 把基座 code 原样透传 | 否决：那是别人的词表，界面无法负责地翻译；已知码映射、未知码落到自家通用码，界面只认自家表。 |

## 后果

- 桥的**每个**消费点都必须能指名基座声明文件；"听着像"的名字现在有断言挡（D5），近名会在测试里当场红。
- 消费登记表从 `workspaceRegistry, directoryPicker` 改为真实 owner 名——这是门禁对账的输入，漂移即红。
- 已知未闭：真实 Host 端到端尚未跑（本票不含启动 Host）；本 ADR 只把服务面钉到声明上，**不等于**真机验证过。
- 后续票（013 的 `workspaceFiles/*`、026/031）继续按 D1/D2 先读声明再接线。
