# ADR-0157 · 深度开发前置基线：发布物保全、生产隔离与可核验执行

- 状态：accepted（2026-09-23）
- 日期：2026-09-23
- 决策者：用户（lute）——已同意“先完成前置盘点与增强，再进入深度开发”的顺序；Codex 负责将边界和执行证据固化
- 决策记录：[Note](../notes/implemented/process/2026-09-23-deep-development-readiness-baseline.md)
- 相关：[ADR-0015](ADR-0015.md)、[ADR-0067](ADR-0067.md)、[ADR-0139](ADR-0139.md)、[ADR-0148](ADR-0148.md)

## 背景

当前主线同时承载既有 DSH Desktop、尚未成为可发布替代的 Lute Shell、两份适用范围不同的 handoff、历史发布归档，以及生产恢复工作。深度盘点已证明三个风险同时存在：归档发布清单位于子目录而清场工具只扫顶层；`2.5.0` 有本地制品但其正式发布状态未由完整发布链证明；DA-25 的最小恢复不等于生产恢复结案。

此前用户对历史发布物的保护决定仍由 ADR-0067 约束。当前用户批准的是前置顺序，不是对 `2.5.0` 定位、历史制品留存策略或生产环境权限的替代性结论。

## 决策

**D1：先建立可核验基线，再开始深开发。** 本轮先建立方案、执行 Todo、ADR/Note 和文件级变更记录；每个代码批在实施前展示 Birdview 范围，完成后记录实际命令、退出码和未验证项。计划、历史证据与当前实跑结果必须分开表述。

**D2：前置阶段禁止删除发布证据与生产改动。** `packaging/release/`、`.archive/`、仓库外发布归档、未知来源的未跟踪项和生产 profile 不属于本轮可写/可删范围。清场工具必须把嵌套发布清单识别为承诺证据；它只产生读数，绝不构成删除授权。

**D3：发布状态与留存策略分为显式决策门。** `2.5.0` 在用户确认正式发布、内部制品或继续取证前保持未决；不得补 tag、改 feed、重打同号或删除。任何改变历史发布物保留规则的提案，必须另立 ADR 明确修订/取代 ADR-0067，并先证明可恢复副本与回滚路径。

**D4：生产恢复与功能开发隔离。** DA-25 继续作为活动安全边界；它只能在用户指定的非生产、可丢弃环境中进行后续验证。Role Presets handoff 先对当前生成器的 50 AGT + 3 MGT 结果完成只读 H0 rebase，不能沿用旧基线把后续事项标为已完成。

## 备选方案

- **立刻按体积或当前清场输出删除历史版本**：否决。嵌套清单盲区会把回滚证据误判为候选，而且尚未取得对 ADR-0067 的替代性授权。
- **先把 `2.5.0` 当正式发布补 tag 或重打包**：否决。当前只能证明本地制品存在；正式发布需要完整分发链证据和用户定位。
- **复用生产 profile 验证新功能与 DA-25**：否决。恢复事件、真实用户状态和功能试验会互相污染，失败也无法归因。
- **直接按 handoff 路线图继续开发**：否决。两份 handoff 的时间基线与适用宿主不同，必须先重放当前可验证事实。

## 后果

- 首个实施批次被收窄为“递归识别归档发布清单 + 回归测试”，不改变任何运行时产品行为或发布物。
- 深开发前多出发布/未跟踪项/交接/隔离环境四道明确门；这会延后功能实现，但消除误删、误发布和误触生产的高风险路径。
- 用户仍需决定 `2.5.0`、历史留存、深开发主线与 DA-25 隔离环境；这些未决事项不会被本 ADR 伪装为已结案。
