# ADR-0126 · 更新安装闸按**行为结构**判，不按文案判（P0-1v2 从「补丁在不在」升级为「闸还成不成立」）

- 状态：accepted（2026-09-18）
- 日期：2026-09-18
- 决策者：用户（lute，2026-09-18 批准「T-08a 建 update-guard 判据」）+ agent（判据与射程设计）
- 决策记录：[Note](../notes/implemented/security/2026-09-18-update-guard-behavioural-judgement.md)
- 相关：ADR-0075（判据只量待发布对象、射程为空报跳过）、ADR-0009（一份事实只有一个家）、ADR-0015（决策记录双轨）、ADR-0122（机器可读决策块）、[13 号升级方案 §4](../research/13-upgrade-2.0.10-execution-plan.md)（T-08a 的出处）

## 背景

T-08a 是 2.0.10 升级方案 §4 里标为**必做**的一项，原文是：把「`DSH_DISABLE_UPDATE_INSTALL` 可解除下载执行」变成 gate，对已装 app 的 `electron-runtime-*.js` 断言 **throw 路径存在**，变异验证红。

2026-09-18 版本升级任务盘点实测：全仓 grep `update-guard` / `updateGuard` **零命中**——这条「必做」从未建立。它守的那条闸长这样（装机真实字节，`electron-runtime-IsgfTki1.js`，守卫命中位置 110553）：

```js
async downloadAndOpenUpdate(version, signal, channel = "stable") {
    if (process.env.DSH_DISABLE_UPDATE_INSTALL !== "0") throw new Error("Update installation is disabled for security (unsigned payload risk). …");
    …
    const artifactPath = await downloadDesktopUpdate({ … });
    const openError = await shell.openPath(artifactPath);
```

**已有的守卫是按消息串判的**：`packaging/verify-patches-v2.sh:66`

```bash
ck "P0-1v2 更新守卫" "$LIB_ER" "Update installation is disabled for security"
```

串在 ≠ 闸在。2026-09-18 对**装机真实字节**做突变，实测两种「串还在、闸已废」的形态：

| 突变 | 消息串是否仍在 | 按串判（`ck` 形态） | 说明 |
| --- | --- | --- | --- |
| M2 闸整句挪到 `downloadDesktopUpdate(` **之后** | 在 | **绿（假绿）** | 下载已经发生才判，拦不拦都没有意义 |
| M3 条件抽成 `if (false)` | 在 | **绿（假绿）** | 闸永不拦；且紧跟的 platform 检查也带 `throw`，连「判后有 throw」都照样成立 |

两条都是**静态文本合规、行为上不设防**。这是 P-03 的形状：没有判据能说「不」的东西，等于没有守住。而这条闸的实际后果不对称——官方载荷未签名，失去它等于允许未签名字节被交给系统安装器。

## 决策

1. **新增门禁 `update-guard`** + 反向自测 `update-guard-selftest`；判据是纯函数 `checkUpdateGuard(text)`，住在 `scripts/gates/update-guard.mjs`（可被反向自测与恒真桩突变）。
2. **断言四条结构关系，不判文案**：
   - ① 闸用 `DSH_DISABLE_UPDATE_INSTALL`，且**紧跟与 `0` 的比较**；
   - ② 判完**紧跟 `throw`**（判而不断等于没判）；
   - ③ 闸**排在副作用之前**（`downloadDesktopUpdate(` / `shell.openPath(` 都在它后面）；
   - ④ `downloadAndOpenUpdate` **仍有调用点**（否则闸是死代码，真正的安装路径在别处）。
3. **射程复用 `gates/patch-anchor-scope.mjs` 的 `selectAnchorTargets`**（本机 `/Applications` ∪ **未打 tag** 的 staging 树），本处只做它的磁盘读取面——射程规则不立第二个家（ADR-0075 / ADR-0009）。
4. **已知副作用全部找不到时判红**：上游换了下载/安装的调用形态时必须人工重锚，不得静默通过。
5. **读不到正文或方法体不可解析时报 `unverifiable`，并计入失败**。它包含了实测的 mode 000 → `EACCES` 形态：把「读不到」读成「补丁丢了」会把人送去重锚一个根本没坏的东西（仪器假红）。
6. **与 `patch-anchors` 分工，不合并**：那条管**补丁在不在**（含消息串），这条只管**它在行为上还成不成立**。两条都绿才算闸真的在。

## 备选方案

- **甲：复用 `patch-anchors`，不新增判据。** 否决。它的锚**就是那条消息串**，而本项要拦的两种形态（M2/M3）消息串都还在——把结构断言塞进同一条判据，只会让它看起来更全，实际仍看不见那两种。
- **乙：并入 `plugin-entry-contract` 族。** 否决。那一族的对象是**插件入口契约**（profile 侧），本项的对象是**壳层 bundle 里的安全守卫**；射程与失效方式都不同，并进去会让 remediation 指错地方。
- **丙：只断言消息串 + 顺序，不管条件。** **曾实现成这样，被自己的突变推翻**：M3（条件抽成 `false`）实测**判绿**——因为 env 只剩消息串里那一次出现，而紧跟的 platform 检查也带 `throw`，落在判定窗口内。补上「条件必须还在跟 `0` 比」之后才转红。这一条是本 ADR 里最值得复用的教训：**判据的边界只能靠突变找出来，不能靠推想**。
- **丁：改用运行时探针（真调一次）。** 本版否决。`downloadAndOpenUpdate` 需要真实 update artifact 与平台策略，探针成本远高于收益；而它一旦真的走到 `shell.openPath`，**探针自己就成了那次未授权安装**。
- **戊：钉死闸的完整字面量。** 否决。上游换引号或改文案就会造出一条与缺陷无关的红，而噪声规则的结局是被关掉（P-02 的死法）。只钉「有没有在跟 `0` 比」，不钉写法。

## 后果

- 正面：P0-1v2 第一次有了**能说「不」**的判据；实测突变 M2/M3 由「判绿」转为「判红」，且测试里显式证明「按串判的天真实现会在这两处判绿」——判据存在的理由被写进断言本身。
- 正面：`unverifiable` 单独计数且**计入失败**，仪器坏了不会伪装成通过。
- 负面/代价：这是**静态文本**断言，不做控制流分析。它**拦不住**「闸还在原位、但上游在别处新开了一条未受保护的下载路径」。已在模块头、remediation 与 Note 里如实划界。
- 负面/代价：只认 `downloadAndOpenUpdate` 这一个方法名；上游改名会让本项**响亮判红**并要求人工重锚。这是有意的方向选择——宁可响亮红，不静默绿。
- 后续：`packaging/verify-patches-v2.sh:66` 的按串 `ck` **保留**（它是补丁登记面的一部分，且射程含未打 tag 的树）。两条判据的分工写进了 `update-guard` 的 remediation，避免下一个人误以为它们是重复的而删掉一条。
