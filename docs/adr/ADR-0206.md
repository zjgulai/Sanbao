# ADR-0206 · 流式读以静默窗口收束：基座的 follow 世代永不自己结束

- 状态：accepted（2026-10-02）
- 日期：2026-10-02
- 决策者：agent（取证并实施；终止语义是取舍，见备选）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-02-bridge-service-surface.md)
- 相关：[ADR-0204](ADR-0204.md)（流式调用与帧上限）、[ADR-0205](ADR-0205.md)（服务面与 signal）

## 背景

ADR-0204 让 `bridgeStream` 一直迭代到 provider 的异步可迭代结束。取证基座实现
（`dsh-api-workspace-controller/lib/types/feed.js`）：`follow(signal)` 是
`while (!this.closed && !signal.aborted)` 的世代——**只在 signal 中止或服务销毁时结束**。

而消费链是同步等待终局应答的：`readWorkspaceList` 等 `bridgeStream` 的 promise，`main` 侧 10s 超时。
两件事叠起来：真实链路上每次 `/.sage/state` 读取都要等满 10 秒，然后以 `bridge-result-unknown` 收场；
列表**永远显示"未核验"**。010/012 的单元与浏览器读数都用有限生成器，所以这条从未显形。

## 决策

1. **D1 有界静默窗口**：host 侧每等一帧最多 `BRIDGE_STREAM_QUIET_MS = 150`；窗口内没有新帧就以 `ok:true`
   报告已折叠的帧数（`{frames}`）。窗口是**每次等待重开**的，因此连续到达的帧不会因为窗口而丢。
2. **D2 窗口不是超时错误**：窗口到点收束是**正常结束**，不是 `bridge-result-unknown`；"读到几帧"是结果的一部分。
3. **D3 世代随调用结束**：收束（含越上限、consumer 提前关闭）后同一 `finally` 里 `abort()`——基座的 `finally`
   会 `followers.delete(follower)`，订阅不泄漏。
4. **D4 语义交给上层**：窗口收束只表示"这段时间内基座没有再推帧"。每读一次都是一次新世代（ADR-0204 D4），
   所以下次轮询会用新 baseline 对账——**不引入长期订阅缓存**，也就没有"缓存何时失效"的第二个问题。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 只读第一帧（baseline 快照），把增量折叠留给单元测试 | 否决：增量分支在生产里成死代码（"写了但从没跑到"），而且验收"增量不乱"没有真实对象。 |
| 长开订阅 + main 侧缓存 + 失效规则 | 否决：引入订阅生命周期（重连、断线、runtime-invalidated 后重建），超出本票；且缓存会成为列表的第二个家（P-07）。 |
| 让 main 侧用超时收场（现行 10s） | 否决：把正常读取做成 10 秒延迟 + `bridge-result-unknown`，界面永远"未核验"——症状消失≠可用。 |
| 让基座在 baseline 后主动 close | 做不到：`follow` 只由 signal/销毁结束，Sage 不改基座（ADR-0008）。 |

## 后果

- 一次列表读取的正常耗时 ≈（帧间隔之和 + 150ms）；轮询周期 2s 足够，且读取不再可能挂满超时。
- 窗口是**读的边界**，不是数据完整性边界：窗口内到达的增量会被折叠，之后的由下一次读取的 baseline 对账。
- 已知未闭：真实 Host 上的时限实测未做（本票不启动 Host）；150ms 是取值不是实测标定，日后真机核验时复核。
