# ADR-0151 · 更新 feed `latest.json` 定为派生契约（10 字段 / 每版本快照 / 与入库清单逐字段核对）

- 状态：accepted（2026-09-21）
- 决策者：用户（lute）——在「自动更新路线下一轮做什么」的选择器里拍板「先做结构两步（② 更新器骨架留待随后）」
- 决策记录：[Note](../notes/implemented/contract/2026-09-21-update-feed-contract.md)
- 相关：ADR-0058（入库清单——feed 的唯一事实源）、ADR-0056/0057（DMG 打包与发布 SOP）、
  ADR-0067（已发布产物不可删除——每版本快照与回滚的前提）、ADR-0014（门禁硬门槛）、
  ADR-0068（签名身份与 TCC 重授代价——D5 边界的由来）

## 背景

自动更新计划 `docs/plans/2026-09-13-auto-update-route.md` §5 把运动序列排成八步，其中「现在」行是
**与签名身份无关、不白做**的两步：① `latest.json` 生成 + 归档 + 门禁核对；② 更新器骨架
（只做「检查 + 提示有新版」）。本轮落地 ①（DA-10①）并留下 ② 的输入契约。

现状缺口：入库清单 `release/<版本>.sha256` 已存在，但**没有机器可读的「最新版本」读数**，
也没有任何判据保证这类读数与清单不分家。计划 §3 已定 feed 内容 = 清单字段 + `min_os`/`notes`/`channel`，
但**形状、字段名、派生方式、判据射程、签名的留位方式**都未决定——不决定就实现，等于把
「随便一个 JSON」钉进出货面（P-11 形态）。

## 决策

**D1：契约 = `schema_version` + 10 个固定字段、固定顺序、snake_case、未知字段判违规。**
键序：`schema_version, version, dmg, sha256, build, source_commit, profile_snapshot, min_os, channel, notes`。
前六个逐字段派生自 `release/<版本>.sha256`；`min_os` 由打包脚本从产物
`Info.plist` 的 `LSMinimumSystemVersion` 读（缺该键则打包中止）；`channel ∈ {stable, canary}`
（默认 `stable`）；`notes` 默认空串。未知字段判违规的用意有二：Ed25519 签名字段将来必须经
**一次公开的 schema 变更**进来，而不是被谁悄悄塞一个键；消费方可以按 `schema_version` 分派。

**D2：feed 是派生面，禁止手写。** 派生器 `scripts/lib/update-feed.mjs`
（`parseReleaseManifest` → `buildUpdateFeed` → `validateUpdateFeed`），发布脚本 §7.5 调用生成、
`cp` 进归档（外 + 版本目录内两份），§8 与其他元文件同批 `uchg` 锁 + 回读；生成器**写前自校验**。
对照侧 `checkFeedAgainstManifest()` 六字段逐字段比对，消息中两个读数都点名（`feed=…，清单=…`）。

**D3：判据两条进 quick 门禁，射程 = `release/` 全版本。** `update-feed`：最新版本必须已有 feed
快照（更老版本没有则豁免——机制引入前的历史，不设豁免文件），有 feed 的版本做六字段核对；
其余形态（射程为空、读不到清单/feed 正文、JSON 读不成）一律判红并点名。
`update-feed-selftest` = 22 用例含恒真桩突变证明。「缺失」与「空内容」在判据里必须是两个读数
（`readRepoText` 返回 `null`，`readIfExists` 返回 `''`）——本切片实现期实际踩过一次，见 Note。

**D4：档案侧同批接上。** `release-verify.sh` 有 feed 则核对 sha256/dmg/version，不符 FAIL 并点名，
无 feed 记 `无 feed（机制引入前）`（如实分类，不冒充通过）；`release-verify-test.sh` 增 F1/F2/F3
三例（14/14 过）；`release-restore.sh` 元文件循环纳入 `latest.json`；SOP 的产物清单、`git add`
与 `gh release create` 附件列表同批更新。

**D5：边界——本轮不含签名、不含自动下载/安装。** 不加 Ed25519 字段（空壳会被读成「已签名」），
不加任何下载/安装路径（撞 Gatekeeper 的「更新完打不开」比不自动更新更坏，计划 §5 已写明）。
② 更新器骨架只做「检查 + 提示有新版」，其决策另立。

**回填**：机制引入时用真实清单对已发布的 2.5.0 跑一次派生器生成 `release/2.5.0.latest.json`
（与清单逐字段一致，`notes` 明示为回填快照），使「最新版本有 feed」这条判据自落地起就有真射程。

## 备选方案

- **单文件 `latest.json`、无每版本快照。** 否决：回滚（计划 §4）要求旧版读数仍在场；
  「某版当时对外宣告了什么」也是可审计事实，覆盖写等于销毁证据。
- **手写维护 feed（写在发布说明/文档里）。** 否决：P-48 的形态，且与清单分家的概率随时间单调上升。
- **判据要求「所有版本都必须有 feed」。** 否决：历史版本没有 feed 是事实，全量要求只会逼出
  回填或豁免登记；「最新版本必须有」的语义是「从现在起每版都带」，冷启动只需要一次回填。
- **现在就加 Ed25519 空壳字段。** 否决：空壳会被下游读成「已签名」；私钥管理是独立决策
  （计划 §3 排在 Developer ID 之后）。

## 后果

- 正面：消费方（更新器/官网/人工）读一个文件即得「最新版本 + 哈希 + 最低系统 + 通道」，
  且与入库清单的一致性是**机器判据**而非纪律；给 ② 提供了稳定输入契约；签名与自动安装留有明确接入位。
- 代价（如实保留）：`min_os` 依赖打包机读产物 Info.plist，缺键即中止打包；`channel`/`notes`
  走环境变量，取值正确性归发布动作（SOP 已更新）。
- 后续：DA-10②（更新器骨架，只读不装）；Developer ID 到位后按计划 §5 加签名（③④ 身份与 TCC）
  与自动安装（⑤），以及通道/回滚（⑥）。
