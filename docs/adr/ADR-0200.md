# ADR-0200 · 步骤 3 接真存储：matter 事件库成为 rehydrate 的生产 provider

- 状态：accepted（2026-10-02）
- 日期：2026-10-02
- 决策者：用户（lute：全量授权接线 UI/UX 与后端，写侧按主链推进）+ agent（取证与实施）
- 决策记录：[Note](../notes/implemented/architecture/2026-10-02-step3-matter-store-wiring.md)
- 相关：[ADR-0174](ADR-0174.md)（Application Service 唯一编排入口）、[ADR-0190](ADR-0190.md)（步骤 3–10 fail-closed 的组装内核）、[business-matter 事件库记录](../notes/proposed/architecture/2026-09-27-business-matter-event-store.md)

## 背景

仓里有一个 3461 行的 Sage 自有 SQLite 事件库（append-only、摘要链、幂等 append、崩溃恢复——20 条进程级测试），但 **`src/` 里没有任何东西 import 它**，只有测试在用。这正是 P-04「写了但从没跑到」的形状：组件齐全，生产路径为零。

同时管线第 3 步 `strictRehydrate` 一直由 fail-closed 默认值回答 `undefined`，被管线映射成 `identity-unavailable@rehydrate`（可重试）。这个码**在说假话**：缺的不是身份，而是"没有存储 provider"。任何写侧动作（哪怕只是 `start-attempt`）都会停在这里，而 UI 会照着这个码显示成身份问题。

## 决策

1. **D1 只接步骤 3，其余不动**：新增 `src/main/matter-rehydrate-port.ts`，把 `openBusinessMatterEventStore().load(matterId)` 映射成管线的 step-3 答案（`{matter,current}` / `{denied:'not-found'|'stale-revision'}` / `undefined`）。`app-service.ts` 在组装 step-2 端口时按同一形状合并它；**步骤 4–10 仍是 fail-closed 默认值**，本 ADR 不开任何后续步骤。
2. **D2 不确定一律 fail closed**：库打不开、`load` 抛错、`blocked`（corrupt / unsupported-schema / key-unavailable / io-unavailable…）、投影抛错，全部返回 `undefined`（＝provider 不可用），**绝不映射成"空历史"**。已关闭的端口同样返回 `undefined`。
3. **D3 生产限额在接线处显式选定**（库刻意不提供默认值）：`maxStreamEvents 4096`（一个事项的事件流是有界工作史，不是日志池）、`maxPayloadBytes 1 MiB`（与宿主控制帧上限对齐，保证已存事件一定能过同一条边界）、`busyTimeoutMs 2000`（够别的进程提交完，也够一次用户请求内失败）。
4. **D4 存在性不外泄**：`not-found` 在管线里落到 `policy-denied@rehydrate`（与既有约定一致：找不到与无权限对渲染面不可区分）。
5. **D5 生命周期**：库在首次命令时惰性打开（坏库不阻塞启动），`app.on('will-quit')` 关闭。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 同时把步骤 9（persistPreparation）也接上 | 否决：那需要 dispatch/回执的真实语义（002 的后半），先接一半会造出"能写不能回"的中间态。 |
| 库打不开时返回空历史 | 否决：把"读不到"伪装成"没有"，正是本仓反复禁止的失真（P-57 同族）。 |
| 把限额写进库作为默认值 | 否决：库的架构记录明写"不提供隐式生产默认值"，调用方必须显式给出；默认值应当由接线方负责并被评审。 |
| 在端口里做权限/身份判断 | 否决：那是步骤 2 的职责，端口只回答"存储里有没有这条流"。 |

## 后果

- 写侧动作的失败位置第一次**说真话**：不存在的事项在 `rehydrate` 阶段以 `policy-denied` 结束（不再冒充身份问题）；存在的事项会顺利过第 3 步，然后停在**真正**没接的下一步（`compatibility-unknown@target`），后续步骤仍无一被打开。
- 那条"存在但从未被生产使用"的组件第一次进入生产路径；它的运行期行为（打开、读、关闭）由新测试在真库上验证。
- 风险：端口在主进程内持有 SQLite 句柄；崩溃/断电场景由库自身的进程级测试覆盖（WAL + 幂等 append），本 ADR 不重复证明。
