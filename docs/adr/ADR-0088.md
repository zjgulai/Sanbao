# ADR-0088 · profile 清单漂移必须在 vendor 与装载点两侧都有射程；「比了 0 个包」不得读作「都一致」

- 状态：accepted
- 日期：2026-09-15
- 决策者：用户（lute）+ agent
- 决策记录：[Note](../notes/implemented/surface/2026-09-15-settings-shell-reachability-and-grouping.md)
- 相关：ADR-0008（基座只 pin 不改）、ADR-0009（一份事实只有一个家）、
  ADR-0014（豁免只减不增）、ADR-0015（非机械改动必须留痕）、
  总账 P-02（仪器假绿）、P-07（一条事实多个家）、P-15（写进磁盘 ≠ 已经生效）

## 背景

本轮要给 `dsh-settings-shell` 删掉一条**假声明**：`dsh.client.inject: ["@deepseek-ai/dsh-client-ui-slots"]`
连同同名 `peerDependencies`。它之所以长期没被发现，是因为读官方装载器
（`dsh-client-modules` 的 `arriveGraphRow`）才看得见它的语义是**失败即降级**——
`row.inject` 里解析不到的包名直接跳过（`if (dependency !== void 0)`），
于是它**既不报错也不生效**：产物里一个 `require` 都没有（`react` 出现 0 次，整包自足），
而那个包在本机任何地方都解析不到。

删掉之后才暴露出第二个问题：**这条清单改动传不进运行时会读到的地方**。
`sync-profile.mjs --apply --only-metadata` 与门禁 `profile-metadata-sync` **都把 vendor 路径
写成了扁平的 `vendor/<包名>`**，而实际布局是 `vendor/packages/<组>/<包>`。
25 个受管包**一个都命中不了**，`checkProfileMetadata` 里的 `existsSync` 把每个包都
`continue` 掉——门禁**永远绿**，它自己开出的 remediation 同样恒绿，两边都从未比过任何字节。
归组重构之后一直是这个状态。

第三个问题在修复过程中显形：vendor 副本与 `node_modules/<包>` 本是**同一个 inode**
（`links=2`）；`applySync` 按红线用 tmp+mv 写 vendor，**新 inode 落在 vendor、
`node_modules` 那份留在旧 inode**——于是「同步成功」与「运行时读得到它」再次分家。
而 `loadPointFiles` **刻意把 `package.json` 排除在断言面外**（注释理由是「pnpm 在装载点
重写它」；实测本机 pnpm **并没有**重写，装载点那份与仓库逐字节相同），
所以这次分家没有任何仪器看得见。

## 决策

**一、路径一律用**归组后的 repo 相对路径**，不取 basename。**
`vendorPairs` 与门禁 `profile-metadata-sync` 都改用 `entry.dir` / `relPath`
（`packages/<组>/<包>`），与 vendor 的实际布局对齐。取 basename 是把「当前的目录布局」
当成了常量——而布局恰好是这个仓库自己重构过的东西。

**二、「比了 0 个包」必须与「逐字节都一致」在读数上长得不一样。**
`sync-profile.mjs` 两侧（vendor 与装载点）都加零命中护栏：受管包数 > 0 而命中 0 个时
输出 `warn … 一个都没对上` 并以退出码 1 结束，**不是 `ok`**；门禁侧同样断言
`compared.length > 0`，否则判红并写明「路径布局可能又变了，这不是『都一致』」。
护栏必须覆盖**每一条**分支：这条护栏原先只挂在装载点分支上，
所以它保护的恰好只有自己那条，vendor 那条绿得毫无射程。

**三、清单改动的生效路径写进包契约。**
`package.json` 改动要三处到位：仓库 → `--apply --only-metadata` 写 vendor →
按同一 tmp+mv 语义补写 `<profile>/node_modules/<包>/package.json` → 重启。
写进 `dsh-settings-shell-local/README.local.md`「修改同步」一节。

**四、装载点的 `package.json` 按「装载字段子集」对账。**
把**整个** `package.json` 纳入 `loadPointFiles` 断言面的前提是「pnpm 会在装载点重写它」——
本机实测该前提**不成立**（装载点那份含 `scripts` 与 `devDependencies`、与仓库逐字节相同）。
但整文件比对也不可取：pnpm 若真去剥 `scripts`/`devDependencies`，它会**误红**。
故取**装载相关字段子集**：`main` / `exports` / `dsh`（即 `bundle.patch` 与 `client`）——
这三项是「应用按什么声明加载这个包」的全部内容，且是 pnpm 不会动的。
`files` 不在其中：交付形态已由 `checkProfileFilesSync` 管，同一事实不设两个家（ADR-0009）。
这样处理之后，「清单漂移」在装载点一侧**第一次有了仪器**——上面那条假声明若再出现，
门禁会当场判红。

## 备选方案

1. **只修 CLI、不修门禁。** 否决：门禁是硬门槛、CLI 是它开出的补救手段，
   两者是同一个事实的两个家（P-07）。只修一处，下一轮还会从另一处复发。
2. **在门禁里直接放宽为「vendor 不存在该包就跳过」。** 这正是当前的失效形态
   （`existsSync` 静默 `continue`）。否决：跳过与通过必须不同形（P-02）。
3. **把 vendor 路径改成扫目录发现，而不是由受管包清单推导。** 否决：
   那会让「仓库里新加的包没被物化」也变成一个静默跳过，等于换一个方向失去射程。
4. **顺手把整个 `package.json` 纳入装载点断言面。** 否决，理由见决策四：
   前提（pnpm 会重写它）在本机不成立，而整文件比对会在 pnpm 真去剥
   `scripts`/`devDependencies` 时误红。改用装载字段子集，两头都不丢。
5. **只改仓库清单、不管 profile 副本。** 否决：那就回到
   「写进磁盘 ≠ 已经生效」（P-15）——仓库是对的，应用读的是旧的。

## 后果

- **两台空射程仪器恢复射程**：`sync-profile.mjs --only-metadata` 与
  `profile-metadata-sync` 从「比 0 个包恒绿」变成真的比对 **24 个包**；
  阳性对照（故意拿别的包当源）确认判红。
- **开启真比较无连带影响**：全量实测漂移恰好只有本包 1 个，其余 23 个逐字节一致。
- **三处一致可复核**：仓库 / vendor / `node_modules` 的 `package.json` sha256 一致
  （`1d048187…`）；`lib/client.js` 仍是 `585bbdb2…`，构建前后字节相同
  （本次只动声明、未动产物）。
- **代价**：改 `package.json` 比改源码多一步（决策三）。这一步目前靠文档而非脚本，
  但**漏掉的后果已经被门禁接住**（决策四）——步骤仍是手工的，探针不是。
- **装载点的清单漂移第一次有了仪器**：`main`/`exports`/`dsh` 三项与仓库不一致即判红，
  阳性对照确认有射程。上面那条假声明若再被写回，不会再一路无阻地活到运行时。
