# ADR-0119 · 第三方技能入库必须走机制而不是走笔：登记由安装器产生，重跑安装后必须重新占位化

- 状态：accepted（2026-09-18）
- 决策者：用户（lute）
- 决策记录：[Note](../notes/implemented/capability/2026-09-18-kami-intake-registration-and-preset-wiring.md)
- 相关：ADR-0009（一份事实只有一个家）、ADR-0014（豁免只减不增）、ADR-0056（机器路径只减不增）、ADR-0085（归位 ≠ 接线）、ADR-0086（来源留底与运行时前提层）、ADR-0095（分类守恒与原子写入）、ADR-0102（门禁的分母）

## 背景

`kami`（纸感排版系统，`github.com/tw93/Kami` 的 `skills/kami/`，MIT，v1.15.0 @ `6b39d04`）
在本机先以**手装**形态存在：111 个文件齐全、字体已下到 `~/.local/share/fonts/kami/`、
断网渲染实测通过。手装意味着三处它读不到自己：

| 事实源 | 手装的后果 |
| --- | --- |
| `manifest/intake-provenance.json` | 逐文件 sha256 / 许可证结论 / 已应用修补在它身上不存在，上游升级与回滚没有比对基准 |
| `manifest/runtime-deps.json` | `gate:skill-runtime-preconditions` 的射程是「清单里有声明 ∩ 已接线」——清单里没有就**静默**不查（P-11：读数只显示总数小一，不显示漏了一条） |
| 各 `agt-*` preset 的 `skill-subset` | 对 50 个岗位会话等于不存在 |

补这三处的路径有两条：**照着已有条目的形状手写**，或**把来件放回 `~/Downloads/skills/` 走
`intake-install.mjs`**。这一条 ADR 定的是这两条之间怎么选，以及选了后者之后实测踩到的两个缺陷。

## 决策

1. **登记由安装器产生，不由人填写。** 新增/补登任何第三方技能，**必须**让
   `scripts/intake-install.mjs` 写 `manifest/intake-provenance.json`。理由不是形式：
   该文件的 `repairs`（丢了几份、改写了几处、重新生成了哪些）与 `lintWarnings` 是安装器
   **量**出来的读数，人只能**断言**；而「未经验证的事实被钉进出事面」是本仓库最贵的一类缺陷（P-02）。
   手写条目还会制造该文件的**第二个写入者**——判据一旦可以被绕过，下一个人就不知道该信谁。

2. **本地偏离走管线既有的两条通道，不为单条技能新开机制。**
   正文偏离 → `staging/translations/<name>.body.md`（覆盖通道）；文件级修补 →
   `staging/intake-repairs.json` 的 `dropFiles` / `writeFiles` / `rewritePaths`（修补必须声明，
   匹配不到缺陷的豁免报错，沿用 ADR-0014）。修补能用**恒等替换**表达时，不用 `writeFiles`
   冻结整份文件。

3. **新增来件批次要在 `scripts/intake-lib.mjs` 的 `BATCHES` 里登记，`source` 写得上游可读。**
   批次名会流到技能 frontmatter 的 `metadata.batch`、provenance 的 `batch` 与设置页的来源标签，
   所以它必须能回答「从哪个仓库/哪一批来的」，不能写成 `github` 这种没有信息量的值。

4. **重跑安装或扫描之后，必须重新占位化机器路径，然后才允许提交。**
   `intake-install.mjs` 与 `scan-runtime-deps.mjs` 每次都用 `FROM` / `VENV_PY` 重写两份 manifest
   的 `_meta`，而入库形态是发布期 `packaging/scripts/rewrite-build-paths.mjs` 处理过的
   `__SKILL_INTAKE_SOURCE__` / `__DSH_HOME__`。实测：`_meta.from` 会从占位符变回
   `/Users/lute/…/Downloads/skills`，`sourceUnit` 与 `venvPython` 同样（ADR-0056）。
   提交前用 `grep -c "$HOME" <两份 manifest>` 自查（期望 0）。

5. **判据的射程缺口要写清楚，不许并进「已覆盖」。** `runtime-deps.json` 的 schema 只有
   `python` / `cli` / `node` 三类，Kami 的中文字体（4 个，不在技能单元里，由
   `scripts/ensure-fonts.sh` 下到用户字体目录）表达不进去；缺字体的症状是「退出码 0、PDF 也
   生成了，坏在交付物里」。本版把这条缺口写进 SOP §12.13 与 provenance 的 `knownGaps`，
   并**明确它没有门禁在读**。

## 备选方案与否决理由

- **手写 provenance 条目。** 否决。见决策 1：两个写入者 + 把断言当读数。代价也不对称——
  走管线只多三条声明（一条 `BATCHES`、一条 `intake-repairs`、一份正文覆盖）。
- **改造 `intake-install.mjs` 支持「就地登记已装技能」**（直接读 `~/.dsh/skills/<name>` 算 sha256）。
  否决。它把「来源单元」换成「当前落盘的副本」，而 sha256 的意义正是**相对来件**的比对基准；
  改完之后上游升级就没有参照物，provenance 这份留底也就不再回答它要回答的问题。
- **不登记 provenance，只在 `runtime-deps` 与 T0 里加名字。** 否决。门禁会绿，但「从哪来、
  被改过什么、上游升到哪一版」三个问题都没有家——绿灯会被相信，而它保护的东西不存在。
- **为一类技能新增 `fonts` 声明并配判据。** 本轮未做。它要同时改扫描器、`--check` 分支与
  门禁三处，属**新增机制**而不是登记；本轮先把缺口写在 SOP 与 `knownGaps` 里，下一版单独处置。

## 后果

**正面**

- `kami` 的三处隐藏状态一次补齐：provenance（111 条 sha256 + MIT 结论 + 1 处修补 + 2 条 knownGaps）、
  runtime-deps（3 条 required + 3 条 optional + 1 条 optional node）、T0 第 16 条。
- 门禁射程实际扩大且有读数：`verify_static` 的「已接线 / 需探测」由 296 / 5 变为 **297 / 6**；
  `scan-runtime-deps --check --subset kami` 报 `red 0`。
- 安装**可复现**：来件形状、批次登记、修补声明三条都在，另一台机器按 SOP §12.13 可重跑。
- 接线是确定性的：50 个 `agt-*` 每个恰好 +1、移除 0、新增并集恰为 `{kami}`、总条目 1189 → 1239；
  `verify-generic` 16/16、保真校验 L1–L12 断言 5106 → 5156。
- 判据被证明能说「不」：清单改到 16 条而 preset 未重生成时，`verify-generic` 逐岗点名
  `agt-001…agt-050 缺 kami` 并 `exit 1`。

**负面 / 已知欠账**

- **机器路径的占位化仍是流程性的**。当前没有任何判据在读这两份 manifest 里的路径
  （`gate:resource-path-reachability` 扫的是出货产物里的 `app.asar` 路径）。把它变成机制
  （让写入者直接写占位符，或让门禁读它）是下一版的活。
- **「字体在不在」没有判据**。见决策 5。
- **`staging/` 不入库**（`.gitignore:44`），本次三条声明在仓库里只留下一组新 sha256，
  没有可评审的内容 diff；另一台机器重跑安装会得到上游英文正文而不是 DSH 正文。
  这与库内其余 60 余条技能同构，不是本条的特殊取舍。
- T0 常挂成本随之上升：每会话技能目录约 +130 tok（16 条约 2,000 tok）。
- `scripts/promote-intake-batch.mjs` 的 `WRITERS` 缺尾随换行导致该工具的写盘前自检**对任何
  输入都失败**（自检挡住的是它自己），自那两份 manifest 成形起就没成功跑过。本版已修；
  它同时是一类更普遍的风险：**一个没有调用方的工具，它的自检坏了也没人会发现**。
