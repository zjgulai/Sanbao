# ADR-0158 · 右栏远程内容采用受控原生 WebContentsView

## 背景

右栏内直接嵌入远程页面的 iframe 不能可靠约束页面后续导航、跳转或私网请求；它同时与宿主的隔离、权限和可观测边界混在同一个渲染面。用户选择以受控原生内容替代这条路线，并要求每次变更都能显示准确的代码影响范围。

## 决策

1. 远程页面只由 Electron 主进程创建的独立 `WebContentsView` 承载；右栏 React 包只提供地址输入、状态、占位几何与经过 feature detection 的窄桥接。不得把远程 URL 交给 iframe、`webview` 或 DSH 主渲染器加载。
2. 控制面固定为 `window.dshControlledBrowser` 的 `open`、`navigate`、`setViewport`、`hide`、`dispose` 五个命令。preload 仅对 DSH 主窗口主 frame 暴露它；主进程再次校验 IPC sender、frame、参数和视图归属。
3. 独立非持久 session 默认拒绝所有权限、popup、webview、下载、证书和认证交互；只允许 HTTPS，拒绝 URL 凭证、本机/`.local` 名称和非公网字面量 IP。初始导航、frame 导航、redirect 及请求层都复用同一策略。
4. 宿主改动以独立 `dsh-patches/controlled-browser` 重放在 fixture 或 packaging staging app 上；它在 `runtime-guards` 之后、codesign 之前执行，使用专属 `.orig-controlled-browser` 备份。不得改 `vendor/dsh-desktop`、pin、运行中的 `/Applications` app 或 desktop profile。

## 备选方案

- **A：保留 iframe 并做初始 URL 校验**：否决。后续导航、服务端重定向与内容内请求不能由初始校验可靠约束。
- **B：使用 Electron `<webview>`**：否决。它扩大渲染器侧嵌入面，且 Electron 本身建议优先考虑 `WebContentsView` 等替代方案。
- **C：让外部系统浏览器处理全部 URL**：否决。会失去用户要求的右栏连续工作流；需要时仍可在后续单独设计受控外跳。

## 后果

- 正面：远程内容与 DSH UI 隔离，权限和导航策略集中在宿主侧；右栏切换时原生视图可被隐藏而不销毁会话。
- 代价：该能力依赖宿主补丁，需要在上游 runtime 更新后重验锚点；它不是纯前端包功能。
- 明确边界：首批不支持内网访问、OAuth popup、下载或当前安装 App/profile 的直接部署。URL/DNS 预检不能证明连接建立瞬间的最终 socket 仍为公网地址，因此 DNS rebinding 防护状态必须保留为 `UNVERIFIABLE`，不得报绿。
