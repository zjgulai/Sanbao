# 待办 · 发布版本缺 git tag（SOP 无此环节）

状态：**未处理**。公开仓 `origin`（`github.com/zjgulai/Sanbao`）历史未做任何补造 tag 的动作。
记录时间 2026-09-19，由远端迁移过程中顺带发现。

## 事实

`release/` 里有 8 份版本归档清单，其中两份**没有对应的 git tag**：

| 版本 | `release/<v>.sha256` | `v<v` tag |
| --- | --- | --- |
| 2.2.0 / 2.3.0 / 2.3.1 / 2.3.3 / 2.4.0 / 2.4.1 | ✓ | ✓ |
| **2.3.2** | ✓ | **✗** |
| **2.5.0** | ✓ | **✗** |

后果：这两个已发货版本**追不到产出它们的代码状态**。`release/2.5.0.sha256` 记着一个 652 MB DMG 的
哈希，但没有任何 ref 指向当时的树——「同号归档」这条红线（ADR-0057）只完成了一半：
号归了，锚没钉。

## 根因不是「忘了」

`docs/sop/dmg-release.md` 全文（§0 检查清单 → §9 版本号规则）**没有任何一步要求打 git tag**——
grep `tag` 只命中 `staging` 子串。所以缺 tag 不是执行疏漏，是**SOP 里没有这个环节**，
那 6 个存在的 tag 是历次手工随手打的、不可复现的例外。

这正是复发故障总账里「用纪律守只有机制能守住的东西」的形状：一件事没进 SOP 也没进门禁，
它就靠某个人的记性活着，而记性不跨会话。

## 反推候选（质量不等，勿直接照用）

引入这两份归档清单的提交：

- `cffef32` — **`release: 2.5.0 dmg manifest`**。提交主题就是发布本身，作为 `v2.5.0` 的候选点**较强**。
- `22473d9` — `fix(packaging): 向导版本必须与载荷一致——「版本消歧」此前从未生效（ADR-0066 实测回归）`。
  它**顺带**加入了 `release/2.3.2.sha256`，主题与发布无关。作为 `v2.3.2` 的候选点**较弱**，
  且这本身是个额外的味道：**发布归档清单搭车在无关 fix 提交里**，说明 §6 发布步骤的边界也没守住。

## 建议的处置（待拍板）

1. **先补机制再补锚**：在 `docs/sop/dmg-release.md` §6 发布里加一步 `git tag -a v$VERSION` + 推送，
   并加一条门禁断言「`release/*.sha256` 的每个版本号都存在同名 tag」——缺则判红。
   没有第 2 步的话，第 1 步会在下一次发布时同样失守。
2. 机制立住后，再决定是否为 2.3.2 / 2.5.0 补造历史 tag。**注意这是在公开仓上留下推断产物**，
   需要显式接受；若接受，tag 注释里必须写明「事后按 `<sha>` 反推，非发布当时所打」。
3. 顺带处理：`package.json` 的 `version` 是 `2.0.0`，而发布已到 `2.5.0`——若 ADR-0003
   要求版本对齐，这个偏差要么是真过期，要么是根 package 不参与版本叙事，需查清后写进 SOP。
